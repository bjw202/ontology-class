# SPEC-ENHANCE-P2P3 Acceptance Criteria

## REQ-P2P3-001: 공리 추론 체인 단계별 시연

### AC-001-1: Bachelor 예제 완전성

**Given** `03-axioms.mdx`의 "공리가 추론을 가능하게 하는 방법" 섹션에 보강 내용이 삽입되었을 때,
**When** 학습자가 해당 섹션을 읽으면,
**Then** 다음 내용이 모두 포함되어야 한다:
- `Bachelor == Adult & Male & ~Married` 동치클래스 공리와 `Adult(:John)`, `Male(:John)` ABox 사실이 명시됨
- TBox와 ABox의 구분이 이 예제의 맥락에서 설명됨
- 추론기가 각 조건(Adult, Male, ~Married)을 체크하는 과정이 순서대로 설명됨

### AC-001-2: OWA 영향 대비

**Given** 공리 추론 체인 예제가 완성되었을 때,
**When** OWA/CWA 비교 설명을 읽으면,
**Then** 다음이 명확히 구분되어야 한다:
- CWA에서의 결론: "Married 정보 없음 -> 결혼 안 함 -> Bachelor"
- OWA에서의 결론: "Married 정보 없음 -> 알 수 없음 -> Bachelor 여부 알 수 없음"
- 두 결론의 차이가 왜 발생하는지 설명됨

### AC-001-3: 부정 시나리오

**Given** 추론 체인 각 단계가 설명되었을 때,
**When** "이 단계가 없으면?" 섹션을 읽으면,
**Then** 최소 2개의 부정 시나리오가 포함되어야 한다:
- 교집합 체크를 빼면 발생하는 문제
- 보수 체크를 빼면 발생하는 문제

### AC-001-4: 시각화

**Given** 추론 체인 설명이 완성되었을 때,
**When** Mermaid 다이어그램을 확인하면,
**Then** TBox 공리에서 ABox 사실 대조를 거쳐 결론에 도달하는 흐름이 시각화되어야 한다.

### AC-001-5: 분량 제한

**Given** `03-axioms.mdx`에 보강 내용이 삽입되었을 때,
**When** 추가된 줄 수를 측정하면,
**Then** 70~120줄 범위 내여야 한다.

## REQ-P2P3-002: 추론기 내부 동작 직관적 설명

### AC-002-1: 테이블로 알고리즘 직관적 설명

**Given** `01-description-logic.mdx`에 추론기 동작 섹션이 삽입되었을 때,
**When** 학습자가 해당 섹션을 읽으면,
**Then** 다음이 포함되어야 한다:
- 비유를 사용한 도입부 (예: "탐정" 비유)
- 테이블로 알고리즘의 핵심 단계가 자연어로 설명됨 (최소 4단계)
- 형식 수학 표기가 최소화되어 있음 (기존 본문에서 소개된 DL 표기만 사용)

### AC-002-2: 모순 탐지 메커니즘

**Given** 추론기 동작 설명이 완성되었을 때,
**When** 모순 탐지 부분을 읽으면,
**Then** 다음이 설명되어야 한다:
- `Person & ~Person`이 왜 빈 집합인지
- disjointWith 공리가 모순 탐지에 어떻게 활용되는지

### AC-002-3: 추론 실패 시나리오

**Given** 추론기 동작 설명이 완성되었을 때,
**When** 추론 실패 섹션을 읽으면,
**Then** 최소 2가지 실패 유형이 설명되어야 한다:
- Unsatisfiable class 예시 (예: disjointWith 위반)
- Inconsistency 예시 (온톨로지 전체가 모순인 경우)

### AC-002-4: Protege 연결

**Given** 추론기 동작 설명이 완성되었을 때,
**When** Protege 관련 내용을 읽으면,
**Then** 다음이 포함되어야 한다:
- 추론 후 추론된 사실(노란색)과 비일관성(빨간색)의 의미
- "Explain" 기능에 대한 언급

### AC-002-5: 초급자 접근성

**Given** 추론기 동작 설명 전체를 읽었을 때,
**When** 형식 수학 표기의 비율을 측정하면,
**Then** 설명의 80% 이상이 자연어와 비유로 구성되어야 하며, DL 표기는 이미 본문에서 소개된 것만 사용해야 한다.

### AC-002-6: 분량 제한

**Given** `01-description-logic.mdx`에 보강 내용이 삽입되었을 때,
**When** 추가된 줄 수를 측정하면,
**Then** 80~120줄 범위 내여야 한다.

## REQ-P2P3-003: OWA/CWA Protege 실험 워크스루

### AC-003-1: 실험 설정

**Given** `02-owa-cwa.mdx`에 실험 워크스루가 삽입되었을 때,
**When** 실험 시작 부분을 읽으면,
**Then** 다음이 명시되어야 한다:
- 사용되는 클래스: Person, Male, Female
- 개체: `:John rdf:type :Male`
- 초기 상태: disjointWith 공리 없음

### AC-003-2: OWA 응답 체험

**Given** 실험이 설정되었을 때,
**When** OWA 하 추론 결과를 읽으면,
**Then** 다음이 설명되어야 한다:
- 추론기가 `:John`을 `Female`이 아니라고 결론 내리지 않는 이유
- 학습자의 직관적 예상("Male이면 Female이 아니지 않나?")과의 차이

### AC-003-3: disjointWith 추가 효과

**Given** OWA 응답이 설명되었을 때,
**When** disjointWith 추가 단계를 읽으면,
**Then** 다음이 포함되어야 한다:
- `Male owl:disjointWith Female` 공리 추가
- 추론기 재실행 후 변화된 결과
- 명시적 선언의 필요성 강조

### AC-003-4: 재현 가능한 코드/조작

**Given** 워크스루 전체가 완성되었을 때,
**When** 코드 또는 UI 단계를 확인하면,
**Then** 학습자가 직접 재현할 수 있는 RDFLib Python 코드 또는 Protege UI 조작 단계 중 하나가 제공되어야 한다.

### AC-003-5: CWA 대비

**Given** OWA 실험이 완성되었을 때,
**When** CWA 대비 설명을 읽으면,
**Then** 동일한 상황에서 CWA(데이터베이스)의 결론이 명시되어야 한다.

### AC-003-6: 분량 제한

**Given** `02-owa-cwa.mdx`에 보강 내용이 삽입되었을 때,
**When** 추가된 줄 수를 측정하면,
**Then** 60~100줄 범위 내여야 한다.

## REQ-P2P3-004: OWL 2 프로파일 트레이드오프 연결 다리

### AC-004-1: 포기 사항 구체화

**Given** `05-owl2-profiles.mdx`에 트레이드오프 섹션이 삽입되었을 때,
**When** "무엇을 포기하는가" 부분을 읽으면,
**Then** EL, QL, RL 각각에 대해 다음이 명시되어야 한다:
- 포기하는 OWL 2 기능 목록
- 해당 포기가 실제로 무엇을 표현할 수 없게 만드는지 구체적 예시

### AC-004-2: 시나리오 매핑

**Given** 포기 사항이 구체화되었을 때,
**When** 적합 시나리오 부분을 읽으면,
**Then** 각 프로파일에 최소 1개의 실제 산업/학술 시나리오가 매핑되어야 한다:
- EL: 바이오인포매틱스 (예: SNOMED CT, Gene Ontology)
- QL: 데이터 통합 (예: 정부 공공데이터, 기업 데이터 웨어하우스)
- RL: 규칙 엔진 (예: 보험 심사, 제조 품질)

### AC-004-3: 판단 기준 표

**Given** 시나리오 매핑이 완성되었을 때,
**When** 판단 기준 표를 확인하면,
**Then** 최소 3개 이상의 판단 축(예: 클래스 규모, 데이터 저장소, 추론 유형)에 따라 각 프로파일의 적합성이 표로 정리되어야 한다.

### AC-004-4: 독립 실행 시나리오

**Given** 트레이드오프 분석이 완성되었을 때,
**When** "이것을 알면 할 수 있는 것" 섹션을 읽으면,
**Then** 프로파일 선택 후 해당 추론기로 첫 온톨로지를 실행하는 최소한의 시나리오가 1개 이상 포함되어야 한다.

### AC-004-5: 기존 내용과의 비중복

**Given** 트레이드오프 섹션이 삽입되었을 때,
**When** 기존 "어떤 프로파일을 선택할까?" 섹션과 비교하면,
**Then** 내용이 중복되지 않아야 한다. 기존은 "언제 선택?" 중심, 보강은 "무엇을 잃는가? + 실제 영향" 중심이어야 한다.

### AC-004-6: 분량 제한

**Given** `05-owl2-profiles.mdx`에 보강 내용이 삽입되었을 때,
**When** 추가된 줄 수를 측정하면,
**Then** 70~120줄 범위 내여야 한다.

## 공통 검증 기준

### CC-001: Additive 변경 확인

**Given** 모든 보강이 완료되었을 때,
**When** git diff로 변경 사항을 확인하면,
**Then** 기존 내용의 삭제나 수정이 없고, 순수 추가만 이루어져야 한다.

### CC-002: Mermaid 렌더링

**Given** Mermaid 다이어그램이 포함된 파일이 보강되었을 때,
**When** Nextra 빌드를 실행하면,
**Then** 모든 Mermaid 다이어그램이 오류 없이 렌더링되어야 한다.

### CC-003: 품질 표준 준수

**Given** 모든 보강이 완료되었을 때,
**When** 각 보강 파일을 검토하면,
**Then** 다음이 충족되어야 한다:
- 파일당 최소 1개의 "왜 필요한가?" blockquote
- 파일당 최소 1개의 "연결 포인트" callout
- 존댓말 + 친근한 멘토 톤 유지

### CC-004: 개념 범위 준수

**Given** 모든 보강이 완료되었을 때,
**When** 사용된 개념을 검토하면,
**Then** Phase 2 보강은 Phase 1~2 개념만, Phase 3 보강은 Phase 1~3 해당 파일까지의 개념만 사용해야 한다.

### CC-005: JSX Import 부재

**Given** 모든 보강이 완료되었을 때,
**When** 보강된 파일에서 import 문을 검색하면,
**Then** 새로 추가된 import 문이 없어야 한다.
