# Acceptance Criteria: SPEC-ENHANCE-P4P8

## REQ-P4P8-001: 동일 Triple의 RDF/RDFS/OWL 3계층 비교 시연

### AC-001-1: 동일 트리플 세트 사용

**Given** `content/phase-4/01-rdf.mdx`에 3계층 비교 섹션이 삽입되었을 때,
**When** 학습자가 RDF, RDFS, OWL 각 계층의 코드 블록을 확인하면,
**Then** 3개 계층 모두 동일한 기본 트리플 세트(주어, 술어, 목적어 동일)를 사용하고 있어야 한다.

검증 방법: 3개 코드 블록의 기본 트리플이 문자열 수준에서 동일함을 수동 확인

### AC-001-2: 계층별 "새롭게 알 수 있는 것" 명시

**Given** 3계층 비교 섹션이 존재할 때,
**When** 각 계층(RDF, RDFS, OWL)의 설명을 확인하면,
**Then** 각 계층에서 "이 시점에서 컴퓨터가 아는 것" 또는 "추가로 알 수 있는 것"이 명시적 목록으로 제공되어야 한다.

검증 방법: 각 계층 하위 섹션에 목록(bullet list) 형태의 추론 결과 존재 확인

### AC-001-3: 비교 요약 표 존재

**Given** 3계층 비교 섹션이 존재할 때,
**When** 섹션의 끝 부분을 확인하면,
**Then** "계층 | 표현 가능한 것 | 추론 가능한 것 | 복잡도" 형태의 비교 표가 존재해야 한다.

검증 방법: Markdown 테이블 존재 및 3개 행(RDF, RDFS, OWL) 포함 확인

### AC-001-4: 삽입 위치 정확성

**Given** 보강 내용이 삽입되었을 때,
**When** `01-rdf.mdx`의 전체 구조를 확인하면,
**Then** 3계층 비교 섹션은 "흔한 오해" 섹션 뒤, "실습" 섹션 전에 위치해야 한다.

검증 방법: 파일 내 섹션 순서 확인 (Heading 기반)

### AC-001-5: RDFS/OWL 개념의 적절한 도입

**Given** Phase 4의 01-rdf.mdx는 RDF를 다루는 첫 번째 파일일 때,
**When** RDFS와 OWL 개념을 사용하면,
**Then** "뒤에서 자세히 배울 내용"임을 명시하고, 간소화된 수준의 설명만 제공해야 한다.

검증 방법: "뒤에서 자세히", "맛보기", "간소화" 등의 안내 문구 존재 확인

### AC-001-6: 분량 제한 준수

**Given** 보강 내용이 삽입되었을 때,
**When** 추가된 줄 수를 측정하면,
**Then** 60~120줄 범위 내여야 한다.

검증 방법: `git diff --stat` 또는 줄 수 카운트

## REQ-P4P8-002: 온톨로지 매핑 도구 실전 워크스루

### AC-002-1: 두 온톨로지 Turtle 표현 존재

**Given** `content/phase-8/02-mapping-problems.mdx`에 워크스루 섹션이 삽입되었을 때,
**When** 시나리오 설정 부분을 확인하면,
**Then** 두 개의 서로 다른 온톨로지가 각각 Turtle 코드 블록으로 표현되어 있어야 한다.

검증 방법: 2개의 ```turtle``` 코드 블록 존재 확인

### AC-002-2: 4단계 워크스루 구조

**Given** 워크스루 섹션이 존재할 때,
**When** 전체 구조를 확인하면,
**Then** 최소 4개의 단계(클래스명 유사도, 구조적 유사도, 전문가 판단, 결과 표현)가 순서대로 제시되어야 한다.

검증 방법: "단계 1", "단계 2", "단계 3", "단계 4" 또는 동등한 순차 구조 확인

### AC-002-3: 매핑 표현 방법 비교

**Given** 워크스루의 결과 표현 단계를 확인할 때,
**When** 매핑 결과의 OWL/SKOS 표현을 확인하면,
**Then** `owl:equivalentClass`, `skos:exactMatch`, `rdfs:subClassOf` 중 최소 2가지의 사용 기준이 설명되어야 한다.

검증 방법: 해당 OWL/SKOS 어휘의 언급 및 사용 기준 설명 존재 확인

### AC-002-4: 자동 매핑 실패 사례

**Given** 워크스루 섹션이 존재할 때,
**When** 자동 매핑 실패에 대한 부분을 확인하면,
**Then** 자동 도구가 실패하는 구체적 사례와 수동 개입이 필요한 시점이 명시되어야 한다.

검증 방법: "실패", "수동", "전문가 개입" 등의 키워드와 구체적 사례 존재 확인

### AC-002-5: 삽입 위치 정확성

**Given** 보강 내용이 삽입되었을 때,
**When** `02-mapping-problems.mdx`의 전체 구조를 확인하면,
**Then** 워크스루 섹션은 "자동 매핑의 현실적 성능" 섹션 뒤, "반자동 매핑의 현실적 프로세스" 섹션 전에 위치해야 한다.

검증 방법: 파일 내 섹션 순서 확인 (Heading 기반)

### AC-002-6: 기존 본문과의 연결

**Given** 워크스루에서 이질성 유형을 다룰 때,
**When** 본문의 "이질성 문제의 세 가지 유형" 섹션과 비교하면,
**Then** 워크스루의 사례가 기존 본문의 이질성 유형(명명, 구조, 의미) 중 최소 2가지를 실증해야 한다.

검증 방법: 워크스루 내 이질성 유형 매핑 확인

## REQ-P4P8-003: 기술 비교 연결 다리

### AC-003-1: 기술별 적합/부적합 표

**Given** `content/phase-8/04-technology-comparison.mdx`에 연결 다리 섹션이 삽입되었을 때,
**When** 기술별 시나리오 부분을 확인하면,
**Then** 4가지 기술(온톨로지, 속성 그래프, RDBMS, SKOS) 각각에 대해 적합한 문제 유형과 부적합한 문제 유형이 명시되어야 한다.

검증 방법: 4가지 기술 x 적합/부적합 내용 존재 확인

### AC-003-2: 판단 체크리스트

**Given** 연결 다리 섹션이 존재할 때,
**When** 체크리스트 부분을 확인하면,
**Then** 5~7개의 Yes/No 질문으로 구성된 기술 선택 가이드가 존재해야 한다.

검증 방법: 체크리스트 형태의 질문 목록 존재 및 수량 확인 (5~7개)

### AC-003-3: Hybrid 패턴 설명

**Given** 연결 다리 섹션이 존재할 때,
**When** Hybrid 패턴 부분을 확인하면,
**Then** 혼합 사용이 필요한 패턴이 최소 2가지 이상 제시되고, 추가 비용/복잡성이 언급되어야 한다.

검증 방법: Hybrid 패턴 수량 및 비용/복잡성 관련 내용 확인

### AC-003-4: 도입 신호와 위험 신호

**Given** 연결 다리 섹션이 존재할 때,
**When** 도입 신호 부분을 확인하면,
**Then** 각 기술에 대해 도입 신호(green flag)와 위험 신호(red flag)가 표 또는 목록으로 제시되어야 한다.

검증 방법: Green/Red flag 내용 및 4가지 기술에 대한 커버리지 확인

### AC-003-5: 삽입 위치 정확성

**Given** 보강 내용이 삽입되었을 때,
**When** `04-technology-comparison.mdx`의 전체 구조를 확인하면,
**Then** 연결 다리 섹션은 "종합 비교 매트릭스" 섹션 뒤, "연결 포인트" 섹션 전에 위치해야 한다.

검증 방법: 파일 내 섹션 순서 확인 (Heading 기반)

### AC-003-6: 기존 폴리글롯 섹션과 비중복

**Given** 연결 다리 섹션이 존재할 때,
**When** 기존 "폴리글롯 아키텍처" 섹션과 비교하면,
**Then** 새 섹션은 "판단 기준"에 초점을 맞추고, 기존 폴리글롯 섹션의 사례 나열과 역할이 구분되어야 한다.

검증 방법: 두 섹션의 내용 비교, 중복 단락 부재 확인

## 공통 수락 기준

### AC-COMMON-1: Additive 변경 원칙

**Given** 모든 보강이 완료되었을 때,
**When** git diff로 변경 내용을 확인하면,
**Then** 기존 내용의 삭제나 수정이 없고, 새로운 섹션 추가만 존재해야 한다.

검증 방법: `git diff`에서 `-` 라인이 없거나 최소(삽입 지점 조정용)인지 확인

### AC-COMMON-2: Mermaid 안전 구문

**Given** Mermaid 다이어그램이 포함된 경우,
**When** 다이어그램 코드를 확인하면,
**Then** 아포스트로피(`'`), `stateDiagram-v2`에서의 `+` 연산자가 사용되지 않아야 한다.

검증 방법: Mermaid 코드 내 금지 문자 검색

### AC-COMMON-3: JSX Import 부재

**Given** 모든 보강이 완료되었을 때,
**When** 추가된 코드에서 import 문을 검색하면,
**Then** JSX import 문이 존재하지 않아야 한다.

검증 방법: 추가된 줄에서 `import` 키워드 검색

### AC-COMMON-4: 한국어 문체 일관성

**Given** 모든 보강이 완료되었을 때,
**When** 보강된 텍스트의 문체를 확인하면,
**Then** 존댓말 + 친근한 멘토 톤이 기존 파일과 일관되어야 한다.

검증 방법: 무작위 단락 3개 선택, 기존 톤과 비교

### AC-COMMON-5: "왜 필요한가?" 및 "연결 포인트" 존재

**Given** 모든 보강이 완료되었을 때,
**When** 각 보강 파일을 확인하면,
**Then** 파일당 최소 1개의 "왜 필요한가?" blockquote와 1개의 "연결 포인트" callout이 존재해야 한다.

검증 방법: `왜 필요한가?` 및 `연결 포인트` 키워드 검색

### AC-COMMON-6: 빌드 성공

**Given** 모든 보강이 완료되었을 때,
**When** `npm run build` 또는 동등한 빌드 명령을 실행하면,
**Then** 빌드가 오류 없이 완료되어야 한다.

검증 방법: 빌드 명령 실행 및 exit code 0 확인
