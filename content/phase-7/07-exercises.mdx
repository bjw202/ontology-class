# 7단계: 종합 실습

이번 실습은 7단계에서 배운 온톨로지의 실전 응용 지식을 직접 적용해보는 시간입니다. 기본 실습과 도전 실습으로 나누어져 있으며, 각 실습에서 배운 개념을 확인하고 심화할 수 있습니다.

## 기본 실습

### 기본 실습 1: Graph RAG vs. 기본 RAG 비교 분석

**목표**: Graph RAG와 벡터 기반 RAG의 핵심 차이점을 깊이 이해합니다.

**과제**: 다음 질문에 대해 두 가지 RAG 방식이 어떻게 다르게 작동하는지 비교하고 각각의 장단점을 분석하세요.

질문 시나리오: "삼성전자와 같은 메모리 반도체를 생산하는 기업들 중, AI 가속기 관련 특허를 가장 많이 보유한 경쟁사는 어디인가?"

**비교 분석 프레임워크**:

| 항목 | 벡터 RAG | Graph RAG |
|------|----------|-----------|
| 검색 방식 | 텍스트 임베딩 유사도 | 그래프 관계 탐색 |
| 다단계 추론 | 제한적 | 가능 (hop 탐색) |
| 설명 가능성 | 낮음 (유사 문서 목록) | 높음 (경로 제시) |
| 구축 비용 | 낮음 | 높음 |
| 최신성 | 문서 업데이트로 반영 | 그래프 업데이트 필요 |

위 질문에서 Graph RAG가 유리한 이유를 다음 관점에서 서술하세요:
1. 이 질문이 몇 단계의 추론을 필요로 하는가?
2. 어떤 엔티티와 관계 타입이 필요한가?
3. 벡터 RAG만으로 이 질문에 답하는 것이 왜 어려운가?

**예상 답변의 핵심 포인트**:
- 이 질문은 "메모리 반도체 생산 기업" → "삼성전자의 경쟁사" → "AI 가속기 특허 보유량 순위"라는 3단계 추론이 필요합니다.
- 필요한 관계: `produces`, `competitorOf`, `holdsPatent`, `relatedToDomain`
- 벡터 RAG는 "삼성전자 반도체 경쟁사"와 "AI 가속기 특허"를 개별적으로 검색할 수는 있지만, 두 조건을 구조적으로 결합하기 어렵습니다.

### 기본 실습 2: Wikidata SPARQL 실습 - 한국 도시 정보

**목표**: Wikidata의 공개 SPARQL 엔드포인트를 사용하여 링크드 데이터를 직접 쿼리해봅니다.

**준비**: 웹 브라우저에서 `https://query.wikidata.org/` 에 접속합니다. (별도 로그인 불필요)

**실습 A: 한국의 광역시 목록 조회**

Wikidata에서 한국(Q884)의 광역시를 조회하는 SPARQL 쿼리를 작성하세요.

힌트:
- 한국 광역시의 Wikidata 클래스: "metropolitan city of South Korea" (Q271609)
- 행정 구역 간 관계: `wdt:P131` (행정 구역 내에 위치)
- 인구: `wdt:P1082`
- 한국어 레이블: `@ko`

기본 쿼리 템플릿:
```sparql
SELECT ?city ?cityLabel ?population WHERE {
  ?city wdt:P31 wd:Q271609 .
  OPTIONAL { ?city wdt:P1082 ?population . }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "ko,en" . }
}
ORDER BY DESC(?population)
```

이 쿼리를 실행하고 결과를 확인한 후 다음을 답하세요:
1. 현재 Wikidata에 등록된 한국 광역시는 몇 개인가?
2. 인구가 가장 많은 광역시는 어디인가?
3. Wikidata의 인구 데이터와 실제 최신 통계가 차이가 있다면 왜 그럴까? (5스타 링크드 데이터 관점에서)

**실습 B: SPARQL 결과에서 5스타 링크드 데이터 평가**

Wikidata의 한국 도시 데이터를 5스타 기준으로 평가해보세요:
- 어떤 외부 데이터셋과 `owl:sameAs`로 연결되어 있는가?
- 데이터 출처(Reference)가 얼마나 제공되어 있는가?
- 한국 공공데이터포털(data.go.kr)의 도시 데이터와 비교할 때 어떤 차이가 있는가?

## 도전 실습

### 도전 실습 1: 간단한 제조 공정 온톨로지 설계

**목표**: 실제 제조 환경의 일부를 온톨로지로 모델링하는 능력을 기릅니다.

**시나리오**: 가상의 한국 자동차 부품 제조사 "K-Parts Co."의 생산 라인을 온톨로지로 설계합니다.

이 회사는 다음과 같은 공정으로 금속 부품을 생산합니다:
1. 원자재 입고 (철판, 알루미늄)
2. 프레스 가공 (형태 성형)
3. 용접 (부품 결합)
4. 표면 처리 (도금, 코팅)
5. 품질 검사 (비전 검사, 치수 측정)
6. 완제품 출하

**과제**: Turtle 형식으로 다음을 표현하는 온톨로지를 작성하세요.

(1) 클래스 계층 구조 (최소 10개 클래스):
- 자원(Resource): 기계, 작업자, 재료
- 공정(Process): 각 생산 단계
- 제품(Product): 반제품, 완성품
- 품질(Quality): 합격, 불합격, 결함 유형

(2) 핵심 속성 (최소 5개 객체 속성, 3개 데이터 속성):
- `usesResource`: 공정이 사용하는 자원
- `produces`: 공정이 생산하는 산출물
- `requires`: 공정이 필요로 하는 입력
- `hasQualitySpec`: 제품의 품질 기준
- `cycleTime`: 공정당 소요 시간(데이터 속성)

(3) 적어도 하나의 OWL 제약 조건:
- 예: "품질 검사 공정은 반드시 완제품을 산출물로 가져야 한다"

**시작점 예시**:

```turtle
@prefix kp: <http://kparts.co.kr/ontology#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# 클래스 정의 예시
kp:ManufacturingResource a owl:Class ;
    rdfs:label "제조 자원"@ko ;
    rdfs:comment "생산에 사용되는 모든 자원"@ko .

kp:Machine a owl:Class ;
    rdfs:subClassOf kp:ManufacturingResource ;
    rdfs:label "기계"@ko .

# 여기에 나머지 클래스와 속성을 추가하세요
```

**평가 기준**:
- 실제 제조 도메인 지식이 반영되어 있는가?
- 클래스 계층이 논리적으로 구성되어 있는가?
- 속성의 도메인(domain)과 치역(range)이 적절히 정의되어 있는가?
- OWL 제약 조건이 의미 있게 사용되었는가?

### 도전 실습 2: LLM 환각 문제를 온톨로지로 해결하는 방안 설계

**목표**: LLM의 환각 문제를 온톨로지 기반 Graph RAG로 해결하는 시스템 아키텍처를 설계합니다.

**시나리오**: 한국의 의약품 안전 정보 Q&A 서비스를 구축합니다. 이 서비스는 의약품 간 상호작용, 금기 사항, 부작용 정보를 정확하게 제공해야 합니다. LLM만 사용할 경우 환각으로 인한 잘못된 의약품 정보가 심각한 문제를 일으킬 수 있습니다.

**과제 A: 의약품 온톨로지 설계**

다음 엔티티와 관계를 포함하는 의약품 온톨로지 스키마를 설계하세요:

필요한 클래스:
- `의약품(Drug)`: 활성 성분명, 상품명, 제조사
- `활성성분(ActiveIngredient)`: 화학 구조, 계열
- `치료적응증(TherapeuticIndication)`: 치료하는 질환
- `부작용(AdverseEffect)`: 심각도, 빈도
- `금기증(Contraindication)`: 금기 조건
- `약물상호작용(DrugInteraction)`: 상호작용 유형, 위험도

필요한 관계:
- `contains` (Drug → ActiveIngredient)
- `treatedBy` (질환 → Drug)
- `hasAdverseEffect` (Drug → AdverseEffect)
- `contraindictedFor` (Drug → 환자 상태)
- `interactsWith` (Drug → Drug, 대칭 관계)

**과제 B: Graph RAG 파이프라인 설계**

다음 사용자 질문에 대한 Graph RAG 처리 파이프라인을 설계하세요:

질문: "아스피린과 혈액 희석제를 같이 먹어도 되나요? 고혈압 환자인데 괜찮을까요?"

파이프라인에 포함되어야 할 단계:
1. **엔티티 추출 및 분류**:
   - 추출된 엔티티: "아스피린", "혈액 희석제", "고혈압 환자"
   - 온톨로지 클래스 매핑: 각각 어떤 클래스에 해당하는가?

2. **서브그래프 검색 전략**:
   - 어떤 관계 경로를 탐색해야 하는가?
   - 몇 단계 hop까지 검색해야 하는가?
   - 우선순위가 높은 정보는 무엇인가?

3. **컨텍스트 생성 우선순위**:
   - 검색된 정보 중 어떤 것을 LLM에 제공할 것인가?
   - 위험도에 따른 정보 우선순위를 어떻게 설정할 것인가?

4. **LLM 프롬프트 설계**:
   - 환각을 방지하기 위한 프롬프트 구조를 작성하세요
   - "컨텍스트에 없는 내용은 답변하지 말 것"을 어떻게 강제할 것인가?

5. **안전장치 설계**:
   - 고위험 의약품 정보에 대한 특별 처리
   - "전문 의료진 상담 권고" 메시지를 언제 자동 삽입할 것인가?
   - 답변의 근거 법적 면책 조항 포함

**과제 C: 온톨로지 기반 검증 메커니즘**

LLM의 생성 답변을 온톨로지로 후처리 검증하는 메커니즘을 설계하세요:

예: LLM이 "아스피린과 혈액 희석제는 함께 복용해도 안전합니다"라고 답변했을 때:
- 온톨로지에서 아스피린과 일반적인 혈액 희석제(와파린 등)의 `interactsWith` 관계를 조회
- 위험도 레벨이 "HIGH"라면 자동으로 LLM 답변을 차단하고 경고 메시지로 대체
- 안전 정보 출처 문서 첨부

이런 "온톨로지 가드레일(Ontology Guardrail)" 시스템의 장단점을 분석하세요.

## 종합 성찰 질문

실습을 완료한 후 다음 질문에 대해 생각해보세요:

1. **온톨로지의 한계**: 온톨로지가 "알 수 없는 것(Unknown Unknowns)"은 어떻게 처리할 수 없는가? 즉, 온톨로지에 정의되지 않은 새로운 상황이 발생하면 어떻게 되는가?

2. **스케일의 문제**: Wikidata는 1억 개 이상의 항목을 가진 초대형 지식 그래프입니다. 이런 규모에서 SPARQL 쿼리를 효율적으로 수행하기 위해 어떤 기술적 접근이 필요한가?

3. **한국어 특수성**: 한국어 NLP와 온톨로지 통합에서 영어 중심 시스템과 달리 어떤 특수한 도전이 있을까? (조사, 형태소, 존댓말 등)

4. **윤리적 고려**: 의료나 법률 분야에서 온톨로지 기반 AI가 잘못된 판단을 했을 때의 책임 소재는 어디에 있는가? 이를 어떻게 다루어야 하는가?

5. **미래 전망**: 향후 5년 내에 Graph RAG와 LLM의 결합이 어떻게 발전할 것이라고 생각하는가? 온톨로지의 역할은 강화될 것인가, 약화될 것인가?
