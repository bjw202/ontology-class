> **왜 필요한가? - Graph RAG가 필요한 이유**
> ChatGPT, Claude, Gemini 같은 LLM은 놀라운 언어 능력을 보여주지만, 근거 없는 답변을 만들어내고(환각), 2023년 이후 사건은 모르며, 왜 그런 답을 했는지 설명하지 못합니다. Graph RAG는 구조화된 지식 그래프와 온톨로지를 결합하여 이 세 가지 문제를 동시에 해결합니다.

## 배경: LLM의 등장과 한계

### LLM의 혁명적 등장

2022년 11월 ChatGPT의 출시는 AI 역사에서 하나의 분기점이 되었습니다. 불과 2개월 만에 1억 명의 사용자를 확보한 이 서비스는 사람들이 AI와 소통하는 방식을 근본적으로 바꿨습니다.

대형 언어 모델(LLM, Large Language Model)은 수천억 개의 파라미터를 가진 신경망이 수조 개의 텍스트 토큰으로 훈련된 것입니다. 이 모델들은 번역, 요약, 코드 작성, 창작, 질문 답변 등 다양한 언어 작업에서 놀라운 능력을 보여줍니다.

그러나 놀라운 능력과 함께 세 가지 심각한 한계도 함께 드러났습니다.

### 한계 1: 환각(Hallucination) 문제

<strong>환각(Hallucination)</strong>은 LLM이 실제로는 존재하지 않거나 사실이 아닌 내용을 자신감 있게 생성하는 현상입니다.

실제 사례들:
- 존재하지 않는 논문을 인용하는 AI 법률 보조 도구 (2023년 미국 법원 사례)
- 실제로 없는 의약품 상호작용을 설명하는 의료 AI
- 실존하지 않는 회사나 인물을 마치 실재하는 것처럼 기술

왜 환각이 발생하는가? LLM은 텍스트의 통계적 패턴을 학습합니다. 모델은 "그럴듯한(plausible)" 답변을 생성하도록 훈련되어 있는데, 때로는 사실에 근거하지 않고도 그럴듯한 답변을 만들어냅니다.

환각 문제가 특히 심각한 분야:
- 의학/약학: 잘못된 의료 정보는 생명에 위험
- 법률: 잘못된 법적 조언은 심각한 손해 초래
- 금융: 허위 정보 기반 투자 결정
- 학술 연구: 존재하지 않는 참고 문헌 인용

> **왜 필요한가? - 환각 문제 해결의 중요성**
> Stanford 대학의 연구에 따르면, 의료 도메인에서 테스트한 LLM은 최대 30%의 비율로 잘못된 의료 정보를 자신감 있게 제공했습니다. 이런 환각 문제를 해결하지 않으면 LLM을 전문 도메인에서 안전하게 활용할 수 없습니다. Graph RAG는 이 문제에 대한 가장 유망한 해결책 중 하나입니다.

### 한계 2: 지식 최신성(Knowledge Cutoff) 문제

LLM은 훈련 데이터의 특정 시점(Knowledge Cutoff)까지의 정보만 알고 있습니다. 예를 들어 훈련 데이터가 2023년 1월까지라면, 2023년 2월 이후에 일어난 일은 전혀 모릅니다.

이 문제가 야기하는 현실적 어려움:
- 최신 법령 개정 사항 반영 불가
- 새로 승인된 의약품이나 치료법 모름
- 최근 기업 동향이나 재무 정보 파악 불가
- 현재진행형 사건이나 뉴스에 대한 답변 불가

파인튜닝(Fine-tuning)으로 일부 해결할 수 있지만, 파인튜닝은 비용이 많이 들고 매일 변하는 정보를 실시간으로 반영하기 어렵습니다.

### 한계 3: 불투명한 추론 과정(Black Box)

LLM이 특정 답변을 생성한 이유를 설명하기 어렵습니다. 모델 내부에서 어떤 정보를 참고하여 어떤 추론 과정을 거쳐 그 답변에 도달했는지 알 수 없습니다.

이것이 문제가 되는 상황:
- 의사가 AI의 진단 근거를 환자에게 설명해야 할 때
- 판사나 변호사가 AI의 법적 해석 근거를 제시해야 할 때
- 금융 규제 기관이 AI 기반 투자 결정의 근거를 요구할 때
- 학생이 AI 답변의 출처를 확인하고 싶을 때

EU의 AI Act, 미국의 AI Executive Order 등 전 세계 규제 기관들이 AI 시스템의 설명 가능성(Explainability)을 요구하고 있습니다.

## RAG(Retrieval-Augmented Generation)란?

### 기본 RAG의 개념

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM의 한계를 극복하기 위해 2020년 Facebook AI Research가 제안한 패러다임입니다.

핵심 아이디어: LLM이 모든 지식을 내부에 저장하려 하지 말고, 질문에 맞는 관련 정보를 외부 데이터베이스에서 검색(Retrieve)하여 LLM에 제공하면 더 정확한 답변을 생성(Generate)할 수 있다.

기본 RAG 프로세스:
1. 사용자 질문 입력
2. 임베딩(Embedding)으로 질문을 벡터로 변환
3. 벡터 데이터베이스에서 유사한 문서 검색
4. 검색된 문서를 컨텍스트로 LLM에 제공
5. LLM이 컨텍스트를 참조하여 답변 생성

기본 RAG의 장점:
- 최신 정보 반영 가능 (데이터베이스만 업데이트하면 됨)
- 환각 감소 (검색된 실제 문서를 참조)
- 출처 제공 가능

### 벡터 RAG의 한계

그러나 벡터 기반 RAG에도 중요한 한계가 있습니다.

**의미론적 깊이 부족**: 벡터 유사도는 표면적 의미 유사성을 잡아내지만, 복잡한 관계나 다단계 추론이 필요한 경우에는 부족합니다.

예시: "A 회사의 CEO가 설립한 또 다른 회사의 주요 투자자는 누구인가?"
이런 다단계 관계 질문에 벡터 검색은 적절한 문서를 찾기 어렵습니다.

**맥락 없는 유사도 검색**: 벡터 유사도가 높다고 해서 항상 관련성이 높은 것은 아닙니다. 표면적으로 유사한 단어를 사용하지만 전혀 다른 맥락의 문서가 검색될 수 있습니다.

**관계 정보 손실**: 문서를 벡터로 변환하는 과정에서 엔티티 간의 구조적 관계 정보가 손실됩니다. "A가 B를 인수했다"는 관계는 벡터에서 제대로 표현되지 않습니다.

**중복 정보 처리**: 같은 사실이 여러 문서에 다르게 표현된 경우, 모순된 정보를 통합하기 어렵습니다.

> **왜 필요한가? - Graph RAG의 등장 배경**
> 기본 벡터 RAG는 단순한 사실 확인에는 효과적이지만, 복잡한 도메인 질문에는 한계가 있습니다. 의료, 법률, 제조, 금융 같은 전문 도메인에서는 엔티티 간의 복잡한 관계와 다단계 추론이 필수적입니다. Graph RAG는 이런 요구를 충족합니다.

## Graph RAG의 등장

### Graph RAG란?

Graph RAG는 지식 그래프(Knowledge Graph)와 온톨로지를 RAG 파이프라인에 통합한 접근법입니다. 벡터 유사도 검색 대신 또는 함께, 구조화된 그래프에서 서브그래프(Subgraph)를 검색하여 LLM에 컨텍스트로 제공합니다.

### Microsoft Research의 GraphRAG (2024)

2024년 Microsoft Research는 "GraphRAG: Unlocking LLM discovery on narrative private data"라는 논문을 발표하며 Graph RAG를 대중화했습니다. 이 연구는 특히 대규모 비정형 텍스트에서 지식을 추출하고 계층적 그래프 구조로 조직화하여 복잡한 질문에 더 나은 답변을 제공할 수 있음을 보여줬습니다.

Microsoft의 GraphRAG 핵심 혁신:
- 텍스트에서 자동으로 엔티티와 관계를 추출하여 지식 그래프 구성
- 커뮤니티 탐지(Community Detection) 알고리즘으로 관련 엔티티 클러스터링
- 로컬 검색(특정 엔티티 중심)과 글로벌 검색(전체 그래프 요약) 결합
- 각 답변에 사용된 그래프 경로 제공으로 설명 가능성 향상

### Neo4j + LLM 패턴

Neo4j (가장 널리 사용되는 그래프 데이터베이스)는 LLM과의 통합을 위한 다양한 패턴을 제공합니다.

**Cypher Query Generation**: 사용자의 자연어 질문을 Neo4j의 쿼리 언어인 Cypher 쿼리로 자동 변환합니다.

**GraphRAG 패턴**: 그래프에서 관련 서브그래프를 추출하여 LLM 프롬프트에 삽입합니다.

**Knowledge Graph QA**: 지식 그래프 기반 질의응답 시스템을 구성합니다.

## Graph RAG 아키텍처

### 전체 파이프라인

Graph RAG의 전체 처리 과정을 단계별로 살펴봅시다.

**단계 1: 엔티티 추출 (Entity Extraction)**
사용자 질문에서 핵심 엔티티를 추출합니다.

질문: "삼성전자가 개발한 반도체 칩의 주요 고객사는 어디인가?"
추출된 엔티티: "삼성전자"(기업), "반도체 칩"(제품 카테고리)

**단계 2: 온톨로지 기반 엔티티 정규화**
추출된 엔티티를 온톨로지의 공식 개념과 매핑합니다. "반도체 칩"이 온톨로지에서 어떤 클래스에 해당하는지, "삼성전자"의 URI가 무엇인지 확인합니다.

**단계 3: 서브그래프 검색 (Subgraph Retrieval)**
지식 그래프에서 추출된 엔티티와 관련된 서브그래프를 검색합니다. 직접 연결된 엔티티부터 시작하여 N-hop 이웃(Neighborhood)까지 확장합니다.

**단계 4: 관련성 필터링**
검색된 서브그래프에서 질문과 관련된 부분만 선택합니다. 온톨로지의 관계 타입을 사용하여 "개발", "공급", "고객사" 관계에 해당하는 경로를 우선 선택합니다.

**단계 5: 컨텍스트 생성 (Context Generation)**
선택된 서브그래프를 LLM이 이해할 수 있는 자연어 텍스트로 변환합니다.

예: "삼성전자는 DRAM, NAND 플래시 등의 반도체 칩을 제조합니다. 주요 고객사로는 Apple(매출의 약 20%), 구글, 퀄컴 등이 있습니다. Apple은 iPhone, MacBook 등에 삼성 메모리를 사용합니다."

**단계 6: LLM 응답 생성**
생성된 컨텍스트를 LLM 프롬프트에 삽입하고 답변을 생성합니다. LLM은 내부 지식이 아닌 제공된 컨텍스트를 기반으로 답변하도록 유도됩니다.

**단계 7: 출처 및 근거 제공**
최종 답변과 함께 답변의 근거가 된 그래프 경로와 출처 문서를 제공합니다.

### 실제 구현 패턴 (수도 코드)

다음은 Graph RAG의 기본 패턴을 보여주는 수도 코드입니다:

```python
# 수도 코드: Graph RAG 기본 패턴
def graph_rag_query(question, ontology, knowledge_graph, llm):
    # 1. 질문에서 엔티티 추출 (NER + Entity Linking)
    entities = extract_entities(question, ontology)
    # entities = [{"uri": "ex:SamsungElectronics", "type": "Company"}, ...]

    # 2. 관련 서브그래프 검색 (2-hop 이웃 탐색)
    subgraph = knowledge_graph.get_neighborhood(entities, hops=2)
    # subgraph = [(삼성전자, 개발, DRAM), (DRAM, 사용고객, Apple), ...]

    # 3. 온톨로지로 관련성 필터링
    relevant_triples = ontology.filter_relevant(subgraph, question)

    # 4. 서브그래프를 자연어 컨텍스트로 변환
    context = subgraph_to_text(relevant_triples)

    # 5. LLM에 컨텍스트와 함께 질문 전달
    prompt = f"""
    다음 지식 그래프 정보를 참고하여 질문에 답하세요:

    [지식 그래프 컨텍스트]
    {context}

    [질문]
    {question}

    컨텍스트에 없는 내용은 추측하지 마세요.
    """
    answer = llm.generate(prompt)

    # 6. 출처 정보와 함께 반환
    return {"answer": answer, "sources": relevant_triples}
```

이 수도 코드는 Graph RAG의 핵심 아이디어를 보여줍니다:
- 질문을 구조화된 그래프 쿼리로 변환
- 그래프에서 관련 사실을 추출
- LLM에게 "근거 있는 답변"만 생성하도록 유도

## 온톨로지가 Graph RAG에서 하는 역할

온톨로지는 Graph RAG 시스템에서 세 가지 핵심 역할을 담당합니다.

### 역할 1: 스키마(Schema)로서의 온톨로지

온톨로지는 지식 그래프의 스키마를 정의합니다. 어떤 종류의 엔티티가 있는지(클래스), 어떤 관계가 가능한지(속성), 어떤 제약이 있는지(공리)를 규정합니다.

Graph RAG에서의 역할:
- **엔티티 타입 규정**: 추출된 "삼성전자"가 `Company` 타입인지 `Person` 타입인지 결정
- **관계 타입 검증**: "삼성전자 개발 DRAM"에서 "개발"이 `develops` 속성인지 `manufactures` 속성인지 구분
- **질문 의도 분류**: "어디서 만들어지나?" → `manufatureLocation` 속성 조회, "누가 사용하나?" → `customer` 속성 조회

온톨로지 없이 Graph RAG를 구현하면, 서로 다른 관계 표현이 혼재하여 시스템이 일관성을 잃게 됩니다.

### 역할 2: 추론 능력 제공

온톨로지의 공리와 추론 규칙은 지식 그래프에 명시되지 않은 사실을 도출할 수 있게 합니다.

예시:
- 지식 그래프에는 "(삼성전자, 자회사, 삼성디스플레이)"와 "(삼성전자, 자회사, 삼성SDI)"가 있습니다.
- 온톨로지에는 "자회사의 자회사도 자회사이다"라는 규칙이 있습니다.
- 만약 "(삼성디스플레이, 자회사, A사)"가 있다면, 온톨로지 추론으로 "(삼성전자, 자회사, A사)"를 자동 도출할 수 있습니다.

이런 추론 능력은 그래프에 직접 명시되지 않은 정보도 답변에 활용할 수 있게 해줍니다. 이것이 벡터 RAG와 Graph RAG의 핵심적인 차이점입니다.

> **연결 포인트:** 8단계에서 배울 OWL 추론(Reasoning)과 SPARQL 추론 쿼리가 바로 이 역할을 수행합니다. `rdfs:subClassOf`, `owl:TransitiveProperty` 같은 공리가 Graph RAG에서 자동 추론을 가능하게 합니다.

### 역할 3: 설명 가능성(Explainability) 보장

온톨로지 기반 Graph RAG는 답변의 근거를 명시적으로 제시할 수 있습니다.

전통적 LLM 답변: "삼성전자의 주요 고객사는 Apple, Google, Qualcomm 등입니다."
(왜 이 답변을 했는지 알 수 없음)

Graph RAG 답변:
"삼성전자의 주요 고객사는 Apple, Google, Qualcomm 등입니다.
[근거 경로]
- 삼성전자 → (supplies:DRAM) → Apple (출처: 삼성전자 2023 사업보고서)
- 삼성전자 → (supplies:NAND) → Google (출처: 공급계약 발표 뉴스 2023.05)
- 삼성전자 → (supplies:Snapdragon용DRAM) → Qualcomm (출처: 반도체 업계 분석 보고서)"

이 설명 가능성은 의료, 법률, 금융 같은 고위험 도메인에서 필수적입니다.

> **왜 필요한가? - 설명 가능한 AI의 중요성**
> EU AI Act(2024년 발효)는 고위험 AI 시스템에 대해 의사결정 근거를 설명할 것을 요구합니다. 한국의 AI 산업 진흥법도 유사한 방향으로 나아가고 있습니다. Graph RAG는 규제 요구사항을 충족하면서도 강력한 AI 능력을 제공하는 유망한 접근법입니다.

## 사례 연구: 한국 법령 지식 그래프

### 왜 법령인가?

한국 법령은 Graph RAG의 이상적인 응용 분야입니다. 이유는 다음과 같습니다:
- 법조문 간 복잡한 참조 관계 (A법 제3조는 B법 제7조를 준용)
- 개정 이력 관리 (특정 날짜 시점의 법령 내용 조회)
- 전문 용어와 법적 개념의 정확한 정의 필요
- 답변의 근거(법조문)를 명시해야 하는 특성

### 법령 온톨로지 설계

법령 지식 그래프를 위한 온톨로지는 다음과 같은 클래스와 관계를 포함합니다:

핵심 클래스:
- `법령 (Legislation)`: 법률, 시행령, 시행규칙, 고시
- `조문 (Article)`: 개별 법조문
- `항 (Paragraph)`: 조문의 세부 항목
- `법적개념 (LegalConcept)`: 법에서 정의된 개념

핵심 관계:
- `준용 (applies-mutatis-mutandis)`: A조문이 B조문을 준용
- `정의 (defines)`: 조문이 법적 개념을 정의
- `개정 (amends)`: 개정 전후 관계
- `규율 (governs)`: 법령이 규율하는 대상

```
ex:개인정보보호법_제17조 a ex:조문 ;
    rdfs:label "제17조 (개인정보의 제공)" ;
    ex:소속법령 ex:개인정보보호법 ;
    ex:준용 ex:개인정보보호법_제15조 ;
    ex:개정일 "2023-03-14"^^xsd:date .
```

### 조문 간 참조 관계 추출

법령 텍스트에서 "제OO조 제O항"과 같은 참조 패턴을 자동으로 추출하여 지식 그래프에 저장합니다.

이를 통해 다음과 같은 질문에 답할 수 있습니다:
- "이 법조문이 참조하는 다른 법조문은 무엇인가?"
- "이 법조문을 참조하는 다른 법조문은 무엇인가?"
- "이 법적 개념이 정의된 조문은 어디인가?"
- "이 법조문의 최신 개정 내용은 무엇인가?"

### LLM + Graph RAG로 법률 Q&A

법령 지식 그래프 + Graph RAG로 구현한 법률 Q&A 시스템의 예시:

질문: "개인정보 보호법에서 개인정보를 제3자에게 제공할 때 어떤 조건이 필요한가?"

Graph RAG 처리 과정:
1. 엔티티 추출: "개인정보 보호법", "개인정보 제공", "제3자 제공"
2. 온톨로지 기반 법적 개념 매핑: "제3자 제공" → `개인정보제공` 클래스
3. 서브그래프 검색: 개인정보보호법 제17조(제공), 제18조(목적 외 이용), 제22조(동의)와의 관계
4. 컨텍스트 생성: 관련 법조문 내용과 참조 관계를 텍스트로 변환
5. LLM 응답: 법조문을 근거로 정확한 조건 설명
6. 근거 제시: 제17조 제1항, 제2항, 관련 시행령 조문 인용

이 방식은 순수 LLM 답변보다 정확도가 높고, 근거 법조문을 제시할 수 있어 법적 신뢰성을 확보합니다.

> **연결 포인트:** 한국 법령 지식 그래프 사례에서 사용되는 `rdfs:label`, `xsd:date`, 그리고 준용 관계 정의는 3단계에서 배운 RDF/RDFS 문법을 직접 활용합니다. 5단계에서 배운 OWL 공리를 통해 "A법이 B법을 준용한다면, B법의 의무는 A법의 맥락에도 적용된다"와 같은 복잡한 법적 추론도 가능합니다.

## 한계와 도전

### 도전 1: 지식 그래프 구축 비용

Graph RAG의 가장 큰 장벽은 고품질 지식 그래프를 구축하는 데 드는 비용과 시간입니다.

도메인 전문가의 참여: 의학, 법률, 공학 등 전문 도메인의 지식 그래프는 해당 분야 전문가가 설계하고 검증해야 합니다. 이것은 시간과 비용이 많이 드는 작업입니다.

자동화의 한계: 텍스트에서 자동으로 추출한 지식 그래프는 오류와 불완전성이 있어 전문가 검토가 필요합니다.

최신성 유지: 지식이 계속 변화하는 분야(법령 개정, 최신 연구 등)에서는 지식 그래프를 지속적으로 업데이트해야 합니다.

### 도전 2: 도메인별 온톨로지 부재

모든 도메인에 적합한 공개 온톨로지가 존재하지 않습니다. 의학의 SNOMED CT, 생물학의 Gene Ontology처럼 잘 정립된 분야도 있지만, 많은 산업 도메인에서는 표준 온톨로지가 없어 처음부터 구축해야 합니다.

한국 특화 온톨로지의 부족: 영어권 도메인에는 다양한 공개 온톨로지가 있지만, 한국어 도메인 온톨로지는 상대적으로 부족합니다. 이것이 한국에서 Graph RAG 도입을 어렵게 만드는 요인 중 하나입니다.

### 도전 3: 실시간 업데이트 어려움

뉴스, 주가, 법령 개정 등 실시간으로 변하는 정보를 지식 그래프에 즉시 반영하는 것은 기술적으로 도전적입니다.

**스트리밍 지식 그래프 업데이트**: 새로운 정보가 입력되면 자동으로 지식 그래프를 갱신하는 시스템이 필요합니다.

**버전 관리**: 지식 그래프의 변경 이력을 관리하여 특정 시점의 상태를 조회할 수 있어야 합니다. 법령 지식 그래프에서는 특히 중요합니다.

### 도전 4: 그래프와 벡터 검색의 통합

최적의 성능을 위해서는 그래프 검색과 벡터 검색을 효과적으로 결합해야 합니다. 두 검색 결과를 어떻게 통합하고 순위를 매길지는 아직 활발히 연구 중인 주제입니다.

## 흔한 오해

### 오해 1: "Graph RAG는 벡터 RAG의 완전한 대체재다"

Graph RAG는 벡터 RAG의 대체재가 아니라 보완재입니다. 단순한 의미적 유사도 검색에는 벡터 RAG가 효율적이고, 복잡한 관계 추론이 필요할 때는 Graph RAG가 필요합니다. 실제 운영 시스템에서는 두 가지를 하이브리드로 사용하는 경우가 많습니다.

### 오해 2: "Graph RAG를 사용하면 환각이 완전히 사라진다"

Graph RAG는 환각을 크게 줄이지만 완전히 없애지는 못합니다. LLM이 여전히 제공된 컨텍스트를 잘못 해석하거나, 지식 그래프 자체에 오류가 있을 수 있습니다. 또한 지식 그래프에 없는 정보에 대한 질문에는 여전히 한계가 있습니다.

### 오해 3: "온톨로지는 Graph RAG의 선택적 요소다"

온톨로지 없이도 그래프 기반 RAG를 구현할 수 있습니다. 그러나 온톨로지 없이는 엔티티 타입 규정, 추론, 설명 가능성이 크게 제한됩니다. 특히 도메인 전문 지식이 필요한 분야에서는 온톨로지가 Graph RAG의 필수 구성 요소입니다.

## 요약

이번 핵심 세션에서 우리는 다음을 학습했습니다:

1. **LLM의 세 가지 한계**: 환각(사실 오류), 지식 최신성 한계(Knowledge Cutoff), 불투명한 추론(Black Box)은 전문 도메인 활용을 어렵게 합니다.

2. **RAG의 진화**: 기본 벡터 RAG가 최신성과 환각 문제를 일부 해결하지만, 복잡한 관계 추론에는 한계가 있습니다. Graph RAG는 이 한계를 극복합니다.

3. **Graph RAG 아키텍처**: 엔티티 추출 → 서브그래프 검색 → 컨텍스트 생성 → LLM 응답 → 근거 제시의 파이프라인으로 구성됩니다.

4. **온톨로지의 핵심 역할**: 스키마 제공, 추론 능력 부여, 설명 가능성 보장의 세 가지 핵심 역할로 Graph RAG를 강화합니다.

5. **한국 법령 사례**: 복잡한 참조 관계를 가진 한국 법령 지식 그래프가 법률 Q&A에서 Graph RAG의 효과적인 응용 분야임을 이해했습니다.

6. **현실적 한계**: 구축 비용, 온톨로지 부재, 실시간 업데이트의 어려움은 여전히 극복해야 할 과제입니다.

Graph RAG와 온톨로지의 결합은 2025-2026년 현재 AI 분야에서 가장 활발히 연구되는 주제 중 하나입니다. 다음 회차에서는 이런 기술들이 제조업이라는 실제 산업 환경에서 어떻게 적용되는지 살펴봅니다.
