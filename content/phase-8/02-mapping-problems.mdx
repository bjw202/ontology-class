# 2회차: 온톨로지 매핑 문제

> "서로 다른 온톨로지를 통합하는 것은 서로 다른 언어를 사용하는 두 사람이 대화하는 것과 같다. 단어가 같아도 의미가 다를 수 있다."

## 왜 매핑 문제가 중요한가?

> "단일 온톨로지 구축도 어렵지만, 기존에 존재하는 여러 온톨로지를 통합하는 것은 훨씬 더 어렵습니다."

실제 프로젝트에서 온톨로지를 처음부터 만드는 경우는 드뭅니다. 대부분의 경우 다음 상황이 발생합니다:

- 기존의 여러 온톨로지를 통합해야 하거나
- 외부 표준 온톨로지와 내부 온톨로지를 연결해야 하거나
- 레거시 데이터 모델을 온톨로지로 변환해야 합니다

이 모든 상황에서 **온톨로지 매핑(Ontology Mapping/Alignment)** 문제가 발생합니다.

## 온톨로지 매핑이란?

**온톨로지 매핑(Ontology Mapping)** 또는 <strong>온톨로지 정렬(Ontology Alignment)</strong>은 두 개 이상의 온톨로지에서 의미적으로 대응하는 요소들을 찾아 연결하는 과정입니다.

핵심 질문들:
- 온톨로지 A의 `Car` 클래스와 온톨로지 B의 `Automobile` 클래스가 같은 개념인가?
- 온톨로지 A의 `hasEngine` 관계와 온톨로지 B의 `hasPowerUnit` 관계는 동일한가?
- A의 `Person`은 B의 `Individual`과 얼마나 다른가?

## 이질성(Heterogeneity) 문제의 세 가지 유형

### 1. 명명 이질성 (Naming Heterogeneity)

같은 개념을 서로 다른 이름으로 표현하는 문제입니다.

**동의어 문제 (Synonymy) — 같은 개념, 다른 이름:**

| 온톨로지 A | 온톨로지 B | 실제 개념 |
|---------|---------|---------|
| Car | Automobile | 자동차 |
| Doctor | Physician | 의사 |
| MyocardialInfarction | HeartAttack | 심근경색 |
| Purchase | Acquisition | 구매/취득 |

**다의어 문제 (Polysemy) — 같은 이름, 다른 개념:**

`Bank`라는 단어 하나를 예로 들면:
- 금융 온톨로지: "은행" (금융기관)
- 지형 온톨로지: "강둑" (지형적 특성)
- 혈액 온톨로지: "혈액 은행" (보관 시설)

### 2. 구조적 이질성 (Structural Heterogeneity)

동일한 도메인을 서로 다른 계층 구조로 표현하는 문제입니다.

예를 들어 자동차 도메인에서 두 온톨로지 A와 B가 있다고 가정합니다.

온톨로지 A의 구조에서는 `Vehicle` 아래 `Car`와 `Truck`이 있고, `Car` 아래 `ElectricCar`와 `GasCar`가 있습니다.

온톨로지 B의 구조에서는 `Transportation` 아래 `MotorVehicle`과 `ElectricVehicle`이 별도로 있습니다. `ElectricCar`는 `ElectricVehicle`에 속하면서 동시에 `MotorVehicle`의 하위인 `PassengerVehicle`과 관련됩니다.

이처럼 두 온톨로지에서 `Car`와 `ElectricCar`의 관계가 완전히 다릅니다. 단순한 클래스 이름 매핑으로는 해결할 수 없습니다.

### 3. 의미적 이질성 (Semantic Heterogeneity)

가장 해결하기 어려운 유형으로, 같은 용어를 실질적으로 다른 의미로 사용하는 경우입니다.

**의료 온톨로지 사례 — `Patient`의 세 가지 의미:**

- **병원 A의 `Patient`**: 현재 입원 치료를 받고 있는 환자만 포함
- **병원 B의 `Patient`**: 외래 환자를 포함한 모든 의료 서비스 이용자
- **보험사의 `Patient`**: 보험 계약자와 그 가족 전체

세 기관이 모두 `Patient`라는 용어를 쓰지만, 각각의 집합이 다릅니다. 자동 도구는 이 차이를 감지하기 어렵습니다.

## 자동 매핑 도구: 기대와 현실

> "자동 매핑 도구들은 분명 도움이 됩니다. 하지만 완전한 자동화는 아직 불가능하며, 전문가 검토는 피할 수 없습니다."

### PROMPT (Protege 플러그인)

Protege IDE와 통합된 시각적 매핑 도구입니다.

**강점:**
- 비교적 사용하기 쉬운 시각적 인터페이스
- Protege 워크플로우와 통합
- 소규모 온톨로지에서 효과적

**한계:**
- 수만 개 클래스의 대규모 온톨로지에서 성능 저하
- 의미적 이질성 처리 능력이 제한적
- 전문가 수동 검토가 여전히 필수

### LogMap

대규모 온톨로지 매핑에 특화된 도구입니다.

**강점:**
- 100만 개 이상의 엔티티를 가진 대규모 온톨로지 처리 가능
- OWL 추론 엔진과 통합되어 논리적 일관성 검증
- OAEI(Ontology Alignment Evaluation Initiative) 경연에서 꾸준히 상위 성능

**한계:**
- 복잡한 n-대-n 매핑 표현 어려움
- 도메인 지식 없이는 결과 해석 한계
- 결과 신뢰도 평가에 전문 지식 필요

### AgreementMaker

다양한 매핑 전략을 지원하는 연구 지향 도구입니다.

**강점:**
- 여러 매핑 전략 조합 가능 (문자열 유사도, 구조적 유사도, 의미론적 유사도)
- 생명과학 도메인에서 강점
- 시각화 기능으로 결과 이해 용이

**한계:**
- 설정이 복잡하고 파라미터 튜닝 필요
- 특정 도메인에 편향된 성능

### 자동 매핑의 현실적 성능

최신 자동 매핑 도구들도 일반적으로:
- **정밀도(Precision)**: 70~85%
- **재현율(Recall)**: 60~80%

수준에 머뭅니다. 의료, 법률 같은 고정밀 요구 분야에서는 충분하지 않습니다. 잘못된 매핑 하나가 심각한 오류로 이어질 수 있습니다.

## 반자동 매핑의 현실적 프로세스

실제 프로젝트에서 매핑은 다음 단계로 진행됩니다:

**1단계: 자동 후보 생성**

도구를 사용해 매핑 후보 목록을 생성하고 각 후보에 신뢰도 점수(0~1)를 부여합니다.

**2단계: 전문가 검토**

- 신뢰도 0.9 이상: 자동 수락 (약 30%)
- 신뢰도 0.5~0.9: 전문가 검토 필요 (약 50%)
- 신뢰도 0.5 미만: 수동 처리 또는 거부 (약 20%)

**3단계: 반복 및 정제**

전문가 피드백을 학습에 반영하고 전체 일관성을 검증합니다.

**이 과정에서 드는 실제 시간:**

| 온톨로지 규모 | 매핑 소요 기간 |
|------------|-------------|
| 소규모 (100~500 클래스) | 1~4주 |
| 중규모 (500~5,000 클래스) | 1~6개월 |
| 대규모 (5,000 이상 클래스) | 6개월~2년 |

## 온톨로지 매핑의 오픈 문제들

현재까지 해결되지 않은 근본적인 문제들이 있습니다:

**1. 의미론적 동치의 정의 문제**

두 개념이 "같다"는 것이 정확히 무엇을 의미하는가? 완전한 동치(`owl:equivalentClass`)인지, 상위 개념 포함 관계(`rdfs:subClassOf`)인지, 단순히 유사한 개념인지를 자동으로 판단하기 어렵습니다.

**2. 매핑의 정확성 검증 문제**

생성된 매핑이 올바른지 어떻게 검증하는가? 전문가 합의도 항상 일치하지 않습니다.

**3. 매핑의 버전 관리 문제**

온톨로지가 업데이트되면 매핑도 업데이트해야 합니다. 이 유지보수 체인은 아직 충분히 해결되지 않았습니다.

**4. 대규모 스케일 문제**

수만 개의 클래스를 가진 대형 온톨로지 간의 매핑은 계산 비용이 폭발적으로 증가합니다.

## 연결 포인트

> 매핑 문제는 온톨로지의 상호운용성(Interoperability)과 직결됩니다. 이 어려움을 이해하면, 다음 회차에서 배울 벡터 임베딩이 왜 일부 시나리오에서 매력적인 대안인지 이해됩니다. 벡터 공간에서는 유사도가 수학적으로 자동 계산되기 때문입니다.

> 이 문제는 비용 문제(1회차)와도 연결됩니다. 매핑에 드는 시간과 전문가 비용은 상당합니다. 이를 무시하고 프로젝트를 시작하면 예상 비용을 크게 초과하게 됩니다.

## 흔한 오해

### 오해 1: "온톨로지 매핑은 한번만 하면 된다"

온톨로지는 살아있는 시스템입니다. 어느 한 온톨로지가 업데이트되면 매핑도 재검토해야 합니다. 특히 의료 온톨로지처럼 자주 변하는 분야에서는 매핑 유지보수가 지속적인 부담이 됩니다.

### 오해 2: "충분히 잘 만든 온톨로지는 다른 온톨로지와 자동으로 통합된다"

아무리 잘 설계된 온톨로지도 다른 온톨로지와의 통합은 추가 작업이 필요합니다. OWL 표준을 따른다고 해서 자동 통합이 되는 것이 아닙니다. 표준 온톨로지(Gene Ontology, SNOMED CT 등)를 기반으로 설계하면 통합이 쉬워지지만, 완전한 자동화는 현재 기술 수준에서 불가능합니다.

### 오해 3: "자동 도구가 70~80%를 처리하니까 나머지 20~30%만 하면 된다"

나머지 20~30%는 보통 가장 어렵고 중요한 부분입니다. 자동 도구가 처리 못한 케이스는 의미적 이질성이나 구조적 복잡성이 높은 경우이기 때문에, 전문가 작업량이 단순히 20~30%인 것이 아닙니다.

## 매핑 문제를 줄이는 사전 전략

매핑 문제를 완전히 피할 수는 없지만, 사전에 줄이는 전략이 있습니다:

### 표준 온톨로지에서 시작하기

새 온톨로지를 처음부터 만들기보다 기존 표준 온톨로지를 기반으로 확장합니다:

- **의료 분야**: SNOMED CT, ICD-11, LOINC
- **생물학**: Gene Ontology, ChEBI
- **일반 상위 온톨로지**: BFO(Basic Formal Ontology), DOLCE

표준 온톨로지에서 출발하면 같은 표준을 사용하는 다른 시스템과 매핑이 훨씬 쉬워집니다.

### 공용 URI와 명명 규칙

국제적으로 공인된 URI 체계를 사용하면 이질성을 줄일 수 있습니다:

- `http://purl.obolibrary.org/obo/` 체계를 사용하는 OBO Foundry 온톨로지들
- Schema.org의 표준 어휘
- DBpedia의 공용 URI

같은 실세계 개체에 같은 URI를 사용하면 매핑이 자동화됩니다.

### 설계 시 매핑 고려

온톨로지를 설계할 때부터 다른 온톨로지와의 매핑을 고려합니다:

- 주요 외부 온톨로지와 어떻게 연결될 것인지 문서화
- `owl:equivalentClass`, `owl:sameAs`, `skos:exactMatch` 등을 적극 사용
- 매핑 의도와 근거를 주석(Annotation)으로 기록

## OAEI — 온톨로지 매핑의 올림픽

<strong>OAEI(Ontology Alignment Evaluation Initiative)</strong>는 매년 온톨로지 매핑 도구들의 성능을 평가하는 국제 경연입니다. 다양한 도메인(의료, 생물학, 지형학 등)에서 도구들의 정밀도, 재현율, F1 점수를 측정합니다.

2023년 OAEI 결과에서 최고 성능 도구들도 의미적 이질성이 높은 트랙에서는 F1 점수가 50% 아래로 떨어졌습니다. 이것이 현재 기술 수준의 한계를 보여줍니다.

OAEI 참여는 연구자들에게 매핑 도구를 현실적으로 평가하는 기회를 제공합니다. 도구를 선택할 때는 OAEI 결과를 참고하면 유용합니다.

## 요약

온톨로지 매핑 문제는 세 가지 이질성(명명, 구조, 의미)에서 발생합니다. 자동 도구들(PROMPT, LogMap, AgreementMaker)이 도움을 주지만 완전한 자동화는 불가능하며, 전문가 검토가 반드시 필요합니다. 매핑 비용은 종종 과소평가되는 온톨로지 프로젝트의 숨은 비용입니다. 표준 온톨로지에서 시작하고, 공용 URI를 사용하며, 설계 단계에서 매핑을 고려함으로써 이 비용을 줄일 수 있습니다. OAEI 경연은 현재 도구들의 성능 한계를 객관적으로 보여주는 중요한 참고 자료입니다.

## 도구 워크스루: PROMPT를 활용한 매핑 실습

> "이론적 이해만으로는 부족합니다. 실제 도구를 사용해 매핑 과정을 체험해야만, 온톨로지 매핑의 현실적인 어려움을 제대로 이해할 수 있습니다."

이 섹션에서는 온톨로지 매핑 도구 **PROMPT**를 사용하여 실제 매핑 과정을 단계별로 수행하는 방법을 배웁니다. 이 워크스루는 매핑 도구의 능력과 한계를 실제로 체험하고, 반자동 매핑 프로세스를 이해하는 데 목적이 있습니다.

### PROMPT 도구 소개

**PROMPT** (Protege Mapping Plugin)은 온톨로지 통합 도구로, Protégé IDE와 직접 통합되어 시각적 인터페이스를 제공합니다.

**핵심 기능:**
- 두 온톨로지 간의 매핑 후보 자동 생성
- 문자열 유사도, 구조적 유사도 기반 매칭
- `owl:equivalentClass`, `owl:equivalentProperty`, `rdfs:subClassOf` 매핑 지원
- 시각적 인터페이스로 직관적인 매핑 검토

**다운로드 및 설치:**
1. Protégé 5.x 버전이 설치되어 있어야 합니다
2. Protégé 메뉴에서 `Help → Check for plugins...` 선택
3. `Mapping` 탭에서 `PROMPT` 플러그인을 찾아 설치
4. Protégé 재시작

### 워크스루 시나리오: 병원 데이터 통합

두 개의 가상 병원 온톨로지를 통합하는 시나리오를 통해 실습합니다:

**병원 A 온톨로지 (HospitalA.owl):**
```turtle
@prefix ha: <http://hospital-a.org/ontology#> .

ha:Patient a owl:Class ;
    rdfs:label "Patient"@en ;
    rdfs:comment "A person receiving medical care"@en .

ha:Doctor a owl:Class ;
    rdfs:label "Doctor"@en ;
    rdfs:comment "A medical practitioner"@en .

ha:treats a owl:ObjectProperty ;
    rdfs:domain ha:Doctor ;
    rdfs:range ha:Patient ;
    rdfs:label "treats"@en .
```

**병원 B 온톨로지 (HospitalB.owl):**
```turtle
@prefix hb: <http://hospital-b.org/ontology#> .

hb:Physician a owl:Class ;
    rdfs:label "Physician"@en ;
    rdfs:comment "A person qualified to practice medicine"@en .

hb:Client a owl:Class ;
    rdfs:label "Client"@en ;
    rdfs:comment "A person receiving healthcare services"@en .

hb:providesCareTo a owl:ObjectProperty ;
    rdfs:domain hb:Physician ;
    rdfs:range hb:Client ;
    rdfs:label "provides care to"@en .
```

### 단계별 매핑 과정

#### 단계 1: 온톨로지 로드

1. Protégé를 시작합니다
2. `File → Open`을 선택하여 `HospitalA.owl`을 엽니다
3. `Refactor → Create Mapping...`을 선택합니다
4. 대상 온톨로지로 `HospitalB.owl`을 선택합니다

PROMPT는 두 온톨로지를 나란히 표시하는 매핑 인터페이스를 엽니다.

#### 단계 2: 자동 매핑 실행

**PROMPT의 자동 매핑 알고리즘:**

PROMPT는 다음 전략들을 조합하여 매핑 후보를 생성합니다:

1. **문자열 유사도 매칭:**
   - `ha:Doctor` vs `hb:Physician` → 낮은 유사도 (0.3)
   - `ha:Patient` vs `hb:Client` → 낮은 유사도 (0.2)
   - 동의어 사전이 없으면 단어 기반 매칭은 한계가 있습니다

2. **구조적 유사도 매칭:**
   - `ha:Doctor`의 프로퍼티 `ha:treats` 분석
   - `hb:Physician`의 프로퍼티 `hb:providesCareTo` 분석
   - 도메인과 레인지의 구조적 유사성 계산 (0.6)

3. **설명(Comment) 매칭:**
   - `rdfs:comment`의 텍스트 분석
   - `"medical practitioner"` vs `"qualified to practice medicine"` → 중간 유사도 (0.5)

**자동 매핑 결과:**

PROMPT는 다음 매핑 후보를 생성합니다 (신뢰도 점수 포함):

| 소스 | 타겟 | 매핑 유형 | 신뢰도 |
|------|------|-----------|-------|
| `ha:Doctor` | `hb:Physician` | `owl:equivalentClass` | 0.65 |
| `ha:Patient` | `hb:Client` | `owl:equivalentClass` | 0.45 |
| `ha:treats` | `hb:providesCareTo` | `owl:equivalentProperty` | 0.58 |

#### 단계 3: 전문가 검토 및 조정

이제 **전문가 검토**가 필요합니다:

**검토 과정:**

1. **신뢰도 0.65 이상 (자동 수락):**
   - `ha:Doctor` ↔ `hb:Physician` (0.65)
   - 전문가 판단: 두 용어는 실제로 동일한 개념을 지칭함
   - 조치: 매핑 **수락**

2. **신뢰도 0.5~0.65 (신중 검토):**
   - `ha:treats` ↔ `hb:providesCareTo` (0.58)
   - 전문가 판단: 두 프로퍼티는 의미적으로 유사하지만, 약간의 뉘앙스 차이
   - "treats"는 치료 행위에 집중, "provides care to"는 더 포괄적
   - 조치: `owl:equivalentProperty` 대신 `rdfs:subPropertyOf`로 **수정**

3. **신뢰도 0.5 미만 (거부 또는 수동 처리):**
   - `ha:Patient` ↔ `hb:Client` (0.45)
   - 전문가 판단: 두 클래스의 집합이 완전히 다름
   - `ha:Patient`는 현재 입원/치료 중인 환자만 포함
   - `hb:Client`는 외래 환자를 포함한 모든 의료 서비스 이용자
   - 조치: 매핑 **거부**, 대신 `rdfs:subClassOf` 관계를 맺을지 고려

#### 단계 4: 매핑 저장 및 내보내기

검토가 완료되면 매핑을 저장합니다:

```turtle
# 매핑 결과를 별도 파일로 저장
@prefix ha: <http://hospital-a.org/ontology#> .
@prefix hb: <http://hospital-b.org/ontology#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .

ha:Doctor owl:equivalentClass hb:Physician .
ha:treats rdfs:subPropertyOf hb:providesCareTo .
# ha:Patient와 hb:Client는 매핑하지 않음
```

Protégé에서 `File → Save As...`를 선택하여 매핑을 `.pom` 파일(PROMPT mapping format) 또는 OWL 파일로 저장합니다.

### 실제 매핑 과정에서의 문제들

**문제 1: 거짓 긍정 (False Positive):**

PROMPT는 다음 매핑을 제안할 수 있습니다:
- `ha:Doctor` ↔ `hb:Client` (신뢰도 0.35)
- 근거: 두 클래스 모두 "person" 관련 키워드가 설명에 포함

**현실:** 이것은 명백한 오류입니다. 자동 도구는 의미적 이질성을 완전히 해결하지 못합니다.

**해결:** 전문가가 명시적으로 매핑을 거부하고, `owl:disjointWith` 제약을 추가할 수 있습니다.

**문제 2: 거짓 부정 (False Negative):**

PROMPT는 다음 매핑을 놓칠 수 있습니다:
- `ha:treats` ↔ `hb:providesCareTo`는 제안하지만
- `ha:Doctor`와 `hb:Physician`의 상위 개념으로서 `ha:MedicalStaff` ↔ `hb:HealthcareWorker` 매핑을 놓침

**현실:** 문자열 기반 알고리즘은 직접적인 이름 유사성에 의존합니다.

**해결:** 전문가가 수동으로 상위 클래스 매핑을 추가합니다.

**문제 3: n-대-n 매핑의 복잡성:**

다음과 같은 상황에서:
- 병원 A: `ha:Inpatient` (입원 환자), `ha:Outpatient` (외래 환자)
- 병원 B: `hb:Patient` (모든 환자)

PROMPT는 다음 매핑을 생성할 수 있습니다:
- `ha:Inpatient` `rdfs:subClassOf` `hb:Patient`
- `ha:Outpatient` `rdfs:subClassOf` `hb:Patient`

하지만 다음 매핑은 생성하지 못합니다:
- `hb:Patient` `owl:unionOf` (`ha:Inpatient`, `ha:Outpatient`)

**현실:** 복잡한 OWL 구성(unionOf, intersectionOf)을 자동으로 생성하는 것은 PROMPT의 능력을 벗어납니다.

**해결:** 전문가가 수동으로 OWL 구성을 추가합니다.

### PROMPT 대신 LogMap 사용하기

대규모 온톨로지(5,000개 이상의 클래스)에서는 **LogMap**이 더 적합합니다.

**LogMap 사용 방법:**

1. 명령행에서 LogMap을 실행합니다:
```bash
java -jar logmap.jar HospitalA.owl HospitalB.owl -output mappings.rdf
```

2. LogMap은 다음 특징을 가집니다:
- 대규모 온톨로지 처리에 최적화 (100만 개 이상의 엔티티)
- OWL 추론 엔진과 통합된 논리적 일관성 검증
- 명령행 기반이라 배치 처리에 적합

3. LogMap의 출력을 Protégé에서 검토합니다:
```bash
# 생성된 매핑을 Protégé에서 열어 검토
protégé mappings.rdf
```

### 매핑 품질 평가

생성된 매핑의 품질을 평가하는 지표:

**정밀도 (Precision):**
- 정밀도 = 올바른 매핑 수 / 전체 매핑 수
- PROMPT 자동 매핑: 정밀도 ≈ 0.75 (75%)
- 전문가 검토 후: 정밀도 ≈ 0.95 (95%)

**재현율 (Recall):**
- 재현율 = 발견한 올바른 매핑 / 실제 존재하는 매핑
- PROMPT 자동 매핑: 재현율 ≈ 0.65 (65%)
- 전문가 수동 추가 후: 재현율 ≈ 0.85 (85%)

**F1 점수:**
- F1 = 2 × (정밀도 × 재현율) / (정밀도 + 재현율)
- PROMPT만: F1 ≈ 0.70
- 반자동 프로세스: F1 ≈ 0.90

### 연결 포인트

> 이 워크스루는 온톨로지 매핑의 **현실적 어려움**을 보여줍니다. 자동 도구가 70~80%를 처리할 수 있지만, 나머지 20~30%는 전문가 작업이 필수적입니다. 이것이 매핑 비용이 종종 과소평가되는 이유입니다.

> PROMPT와 LogMap은 도구일 뿐입니다. 실제 프로젝트에서는 **사용 사례에 맞는 도구 선택**과 **도메인 전문가와의 협업**이 성공의 핵심입니다.
