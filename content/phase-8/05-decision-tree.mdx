# 5회차: 의사결정 트리 — 기술 선택의 나침반

## 각 결정 지점 상세 설명

> "의사결정 트리를 올바르게 사용하려면 각 질문의 의미를 정확히 이해해야 합니다."

### 질문 1: "도메인이 복잡하고 형식적 추론이 필요한가?"

이것이 가장 첫 번째이자 가장 중요한 질문입니다.

**"도메인이 복잡하다"는 것은:**
- 100개 이상의 구분되는 개념이 있다
- 개념 간 관계가 단순한 계층(is-a)을 넘어서 복잡한 제약이 있다
- 같은 개체가 다양한 관점에서 다르게 분류될 수 있다

**"형식적 추론이 필요하다"는 것은:**
- 명시되지 않은 사실을 논리적으로 도출해야 한다
- 데이터의 논리적 일관성을 자동으로 검증해야 한다
- "만약 A이면 반드시 B이다" 같은 규칙 기반 추론이 필요하다

**예시: 의약품 상호작용 시스템**

어떤 약이 다른 약과 함께 복용하면 위험한지 추론해야 합니다. 수백만 개의 약물 조합을 모두 명시할 수 없으므로, "약물 A가 효소 X를 억제하고, 약물 B가 효소 X에 의해 대사된다면, A와 B를 함께 복용하면 위험하다"는 규칙에서 자동으로 추론해야 합니다. 이 경우 형식적 추론이 필요합니다.

**반면 예시: 전자상거래 제품 카탈로그**

단순히 제품을 카테고리로 분류하고 속성(가격, 색상, 크기)을 저장하면 됩니다. 논리적 추론이 필요하지 않습니다. 이 경우 RDBMS나 SKOS가 충분합니다.

### 질문 2: "표준 공유 및 상호운용성이 필요한가?"

**"예"에 해당하는 경우:**
- 여러 조직이 같은 온톨로지를 공유해야 함
- 국제 표준(OBO, W3C 등)을 따라야 함
- 나중에 다른 시스템과 연동할 계획이 있음

예: 의료 데이터를 여러 병원이 공유하는 시스템 → OWL 2 DL 선택

**"아니오"에 해당하는 경우:**
- 내부 시스템에서만 사용
- 외부와 공유 계획 없음
- 빠른 개발이 우선

예: 내부 연구 프로젝트의 지식 관리 → 더 유연한 접근법 고려

### 질문 3: "대규모 데이터이고 추론이 단순한가?"

**OWL 2 EL 선택 기준:**
- 수백만 개 이상의 개체(instance)
- 추론이 필요하지만 복잡한 OWL DL 표현력은 불필요
- 빠른 추론 성능이 필요

Gene Ontology, SNOMED CT 같은 생물정보학 온톨로지가 대표적 사례입니다. OWL 2 EL은 다항식 시간 복잡도의 추론이 가능해 대규모에서도 효율적입니다.

**OWL 2 DL 선택 기준:**
- 복잡한 표현력(수량 제한, 복잡한 속성 체인 등)이 필요
- 데이터 규모가 관리 가능한 수준

### 질문 4: "주요 작업이 그래프 탐색인가?"

**속성 그래프 선택 기준:**
- "A와 3단계 이내로 연결된 모든 사람은?"
- "이 제품을 구매한 사람들이 함께 구매한 다른 제품은?"
- "이 오류의 근본 원인까지 역추적하라"

이런 다중 홉(multi-hop) 그래프 탐색에는 Neo4j 같은 속성 그래프가 최적입니다.

**속성 그래프가 아닌 경우:**
- 단순한 단일 테이블 조회
- 집계 통계 쿼리
- 관계보다 속성 중심 쿼리

### 질문 5: "정형 데이터이고 ACID가 필요한가?"

**RDBMS 선택 기준:**
- 스키마가 안정적이고 잘 정의되어 있음
- 금융 거래처럼 "모 아니면 도" 트랜잭션이 필요
- 복잡한 집계 쿼리(SUM, GROUP BY 등)가 많음
- 팀에 SQL 전문성이 있음

### 질문 6: "단순 분류 체계 또는 메타데이터인가?"

**SKOS/RDFS 선택 기준:**
- 계층적 분류만 필요 (국가 > 지역 > 도시)
- 태그 시스템
- 도서관 주제 분류
- 간단한 메타데이터 스키마

**벡터 임베딩/하이브리드 선택 기준:**
- 의미 기반 검색이 필요
- 유사도 기반 추천 시스템
- 비정형 텍스트와 구조화 지식을 함께 처리
- 규칙으로 표현하기 어려운 복잡한 패턴

## 실제 사례와 연결

### 사례 1: 병원 의료 정보 시스템

**상황**: 3개 병원이 환자 데이터를 공유하고, 약물 상호작용을 자동으로 경고해야 합니다.

**의사결정 과정**:
1. 형식적 추론 필요? **예** (약물 상호작용 추론)
2. 상호운용성 필요? **예** (3개 병원 공유)
3. 대규모이고 단순 추론? **아니오** (복잡한 의약학 지식 필요)

**결론**: OWL 2 DL 온톨로지, SNOMED CT 기반

### 사례 2: 소셜 미디어 플랫폼 친구 추천

**상황**: 사용자의 소셜 그래프를 분석해 친구를 추천합니다.

**의사결정 과정**:
1. 형식적 추론 필요? **아니오** (통계적 패턴)
2. 그래프 탐색이 주요 작업? **예** (공통 친구, 친구의 친구)

**결론**: 속성 그래프 (Neo4j) + 벡터 임베딩 (관심사 유사도)

### 사례 3: 전자상거래 주문 관리

**상황**: 주문, 결제, 배송을 추적하는 시스템이 필요합니다.

**의사결정 과정**:
1. 형식적 추론 필요? **아니오** (단순 CRUD)
2. 그래프 탐색 주요 작업? **아니오**
3. ACID 필요? **예** (결제 트랜잭션)

**결론**: RDBMS (PostgreSQL)

### 사례 4: 정부 공공 데이터 포털

**상황**: 정부 데이터셋에 표준화된 분류 체계와 키워드 태그를 붙입니다.

**의사결정 과정**:
1. 형식적 추론 필요? **아니오**
2. 그래프 탐색 주요 작업? **아니오**
3. ACID 필요? **아니오**
4. 단순 분류 체계? **예**

**결론**: SKOS (EuroVoc 어휘 기반)

## 잘못 선택하면 어떻게 되는가?

> "기술 선택 실수는 프로젝트 실패의 주요 원인 중 하나입니다."

### 시나리오 A: 단순 문제에 온톨로지를 적용했을 때

회사 내부 FAQ 시스템에 OWL 온톨로지를 구축했습니다. 결과:
- 구축에 6개월 소요
- 검색 엔진(Elasticsearch)로 2주 만에 해결 가능했던 문제
- 유지보수 담당자를 찾기 어려움
- 결국 방치되어 사용 중단

### 시나리오 B: 복잡한 추론 문제에 RDBMS를 사용했을 때

규제 준수(Regulatory Compliance) 시스템을 관계형 DB로 구현했습니다. 결과:
- 규칙 추론을 SQL로 구현하려다 복잡도 폭발
- 새로운 규정이 추가될 때마다 대규모 코드 수정
- 규칙 간 충돌 감지 불가능
- 결국 온톨로지 기반으로 재개발

### 시나리오 C: 소셜 그래프에 RDBMS를 사용했을 때

"6단계 분리" 분석을 SQL JOIN으로 구현했습니다. 결과:
- 6홉 JOIN 쿼리가 수 분에서 수 시간 소요
- 사용자 수 증가에 따라 성능 급격히 저하
- Neo4j로 마이그레이션 후 쿼리 시간 99% 단축

## 연결 포인트

> 이 의사결정 트리는 1~4회차의 모든 내용을 통합한 실용적 도구입니다. 다음 회차(6회차)에서는 "온톨로지를 사용하지 말아야 할 7가지 상황"을 구체적으로 살펴보아 이 트리를 보완합니다.

> 실제 프로젝트에서는 이 트리를 시작점으로 사용하고, 팀의 상황과 제약에 따라 조정하십시오. 어떤 도구도 모든 상황에 완벽하지 않습니다.

## 흔한 오해

### 오해 1: "의사결정 트리가 하나의 정답을 제시한다"

의사결정 트리는 가이드라인이지 알고리즘이 아닙니다. 각 질문에 대한 답이 프로젝트마다, 팀마다 다를 수 있습니다. 트리는 구조적으로 생각하도록 돕는 도구입니다.

### 오해 2: "한번 선택하면 바꿀 수 없다"

기술 선택은 고정적이지 않습니다. 프로젝트 초기에는 RDBMS로 시작하고, 요구사항이 명확해지면 일부 모듈에 온톨로지를 도입하는 점진적 접근법이 가능합니다.

### 오해 3: "하나의 기술만 선택해야 한다"

현실에서는 여러 기술을 조합하는 폴리글롯(polyglot) 아키텍처가 자주 사용됩니다. 거래 데이터는 RDBMS에, 관계 탐색은 속성 그래프에, 개념 정의는 SKOS에 저장하는 방식입니다.

## 요약

이 회차의 의사결정 트리는 6개의 핵심 질문을 통해 4가지 기술 중 최적을 선택하도록 안내합니다. 실제 사례와 연결하고, 잘못된 선택의 결과를 이해함으로써 더 신중하고 정보에 기반한 기술 선택을 할 수 있습니다. 이 트리는 이 코스 전체의 핵심 정리 도구로서, 실무에서 반복적으로 사용하게 될 것입니다.
