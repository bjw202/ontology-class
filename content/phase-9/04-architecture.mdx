# 9단계 4회차: 전체 아키텍처 -- Foundry + AIP 스택과 보안 거버넌스

> "복잡한 시스템의 단순함은 좋은 아키텍처에서 나온다. 각 계층이 자신의 역할만 잘 하면, 전체는 스스로 작동한다."

Palantir 플랫폼을 처음 접하면 수많은 제품명에 압도되기 쉽습니다. Foundry, AIP, Apollo, Workshop, Quiver, OSDK -- 이것들이 어떤 관계인지 모르면 개별 기능을 배워도 전체 그림이 안 보입니다.

이해를 돕기 위해 **도시 비유**를 사용하겠습니다. Palantir 플랫폼은 하나의 스마트 도시와 같습니다. 도시가 작동하려면 기반 인프라(도로, 상하수도), 교통 규칙과 지도, AI 안내 시스템, 전력 배급 체계가 필요합니다. Palantir의 3층 아키텍처가 정확히 이 구조입니다.

이 회차는 세 가지를 명확히 합니다. 첫째, 전체 아키텍처의 3층 구조와 각 계층의 역할. 둘째, 데이터가 들어오고 변경이 적용되는 읽기/쓰기 경로. 셋째, 이 모든 계층에 일관되게 적용되는 보안 및 거버넌스 모델.

## 학습 목표

이 회차를 마치면 다음을 할 수 있습니다:

1. **3층 아키텍처 설명**: Foundry, AIP, Apollo 각 계층의 역할과 상호 관계를 설명한다
2. **온톨로지 계층의 위치 파악**: 전체 스택에서 온톨로지가 어디에 위치하고 왜 핵심인지 설명한다
3. **읽기/쓰기 경로 추적**: 데이터 조회 요청과 변경 요청이 각각 어떤 단계를 거치는지 설명한다
4. **보안 계층 구분**: 스키마 보안과 데이터 보안의 차이, 행/열/셀 수준 접근 제어를 설명한다
5. **Granular Policy 이해**: 동적 접근 제어가 AI 에이전트에도 동일하게 적용되는 이유를 설명한다

## 1. 3층 아키텍처 -- 도시 비유로 이해하기

### 1-1. FOUNDRY -- 도시의 기반 인프라

> **왜 필요한가?** 도시에서 도로, 상하수도, 건물 없이 생활이 불가능하듯, 데이터 운영에도 기반 인프라가 필요합니다. Foundry는 원시 데이터를 받아들이고, 정제하고, 비즈니스가 이해할 수 있는 형태(온톨로지)로 만드는 모든 기반 시설을 제공합니다.

Foundry 안에는 네 개의 하위 계층이 있습니다. 도시 비유를 계속 사용하면:

**원시 데이터 소스 계층 = 도시 외부에서 들어오는 원자재**

외부에서 들어오는 모든 것입니다. 관계형 DB, REST API, IoT 스트림, 파일 시스템, ML 모델 출력까지 모든 형태의 데이터를 수용합니다. 아직 가공되지 않은 상태입니다.

**데이터 통합 계층 = 정수장, 제련소**

Pipeline Builder(ETL 도구)가 원시 데이터를 정제합니다. 더러운 물이 정수장을 거쳐 깨끗한 수돗물이 되듯, 원시 데이터가 정제되어 Object Storage에 저장됩니다.

**온톨로지 계층 = 도시의 지도와 교통 규칙**

Foundry의 핵심입니다. 지도가 "이 건물이 무엇이고 어떤 도로로 연결되는가"를 정의하듯, 온톨로지는 Object Type, Link Type, Action Type, Function, Interface, Security Policy를 정의합니다. 이 계층이 "비즈니스의 언어"입니다.

**애플리케이션 계층 = 도시의 주민과 서비스**

Workshop(대시보드), Quiver(분석), Object Explorer, OSDK 커스텀 앱이 여기 해당합니다. 주민들이 도로와 규칙을 따라 생활하듯, 모든 애플리케이션이 온톨로지를 통해 데이터에 접근합니다.

**Before/After 대비:**

| Before (온톨로지 없이) | After (온톨로지 있을 때) |
|----------------------|------------------------|
| 앱 A는 DB에 직접 SQL 쿼리 | 모든 앱이 온톨로지 계층을 통해 접근 |
| 앱 B가 보안 필터를 빠뜨리면 데이터 유출 | 보안 정책이 온톨로지에 중앙화, 자동 적용 |
| DB 스키마 바뀌면 앱 A, B, C 모두 수정 | DB가 바뀌어도 온톨로지 스키마가 유지되면 앱은 무관 |
| 새 앱 D를 만들면 보안 로직을 처음부터 구현 | 온톨로지의 보안이 자동 적용되어 추가 구현 불필요 |

### 1-2. AIP -- 도시의 AI 안내원

> **왜 필요한가?** 도시에 기반 인프라와 지도만 있으면 충분할까요? 아닙니다. 관광객이 "가장 가까운 병원이 어디야?"라고 물으면, 지도를 직접 읽는 것보다 AI 안내원에게 물어보는 것이 훨씬 빠릅니다. AIP는 온톨로지라는 지도 위에서 작동하는 AI 안내원입니다.

AIP(AI Platform)는 Foundry 없이는 존재할 수 없습니다. 온톨로지를 통해서만 데이터를 읽고 Action을 실행합니다.

AIP는 세 가지 구성요소를 가집니다:

- **AIP Logic**: 코드 없이(no-code) LLM 기반 로직을 구성하는 도구. "어떤 도구를 쓸 수 있는지, 어떤 순서로 판단할지"를 정의합니다.
- **Agent Studio**: 더 복잡한 AI 에이전트를 구성하는 환경. 멀티턴 대화, 복잡한 판단 흐름, 여러 도구의 조합이 필요할 때 사용합니다.
- **AIP Evals**: 에이전트의 성능을 평가하고 모니터링합니다. "이 에이전트가 올바른 Action을 선택했는가"를 측정합니다.

**Before/After 대비:**

| Before (LLM 단독) | After (AIP + 온톨로지) |
|-------------------|----------------------|
| "M-14 위험해 보입니다" -- 텍스트 답변으로 끝남 | M-14 사전점검 작업지시를 ERP에 자동 생성 |
| 사용자가 직접 대시보드를 넘기며 분석 | 자연어 질문 하나로 객체 탐색 + Function 계산 + Action 제안 |
| LLM이 임의의 DB에 접근할 수 있어 보안 위험 | LLM은 온톨로지 계층을 통해서만 접근, 동일한 보안 정책 적용 |

### 1-3. APOLLO -- 도시의 전력 배급 시스템

> **왜 필요한가?** 도시 중심부에서 새 교통 규칙이 정해지면 외곽 마을에도 동일하게 적용되어야 합니다. Apollo는 온톨로지 변경사항을 클라우드, 엣지(공장 현장), 온프레미스(군사 시설) 등 모든 환경에 자동 배포합니다. 전력 배급소가 발전소의 전력을 각 가정에 안정적으로 공급하듯, Apollo는 변경사항을 모든 노드에 일관되게 전파합니다.

대형 제조사나 국방기관은 데이터가 중앙 클라우드에만 있지 않습니다. 공장 현장 서버, 함정 내부 시스템, 원격 의료 시설 -- 이런 환경에 온톨로지 변경사항을 일관되게 배포하는 것이 Apollo의 역할입니다.

**Before/After 대비:**

| Before (수동 배포) | After (Apollo 자동 배포) |
|-------------------|------------------------|
| 온톨로지 변경 후 각 환경에 수동으로 반영 | 변경사항이 자동으로 모든 환경에 전파 |
| 엣지 환경과 클라우드 간 버전 불일치 | 모든 노드가 동일한 온톨로지 버전 유지 |
| 배포 실패 시 수동 롤백 | 자동 롤백 및 배포 상태 모니터링 |

> **연결 포인트 → Phase 8**: Phase 8에서 배운 온톨로지 스케일링의 한계 중 "변경 관리의 복잡성"이 Apollo가 해결하는 문제입니다. 분산 환경에서 스키마 동기화를 자동화합니다.

## 2. 읽기/쓰기 경로 -- 택배 비유로 이해하기

### 2-1. 읽기 경로 = 택배 조회

택배를 추적할 때를 떠올려 보세요. "내 택배 지금 어디야?"라고 물으면, 택배 시스템은 (1) 송장번호 확인 (2) 이 사람이 조회 권한이 있는지 확인 (3) 물류센터에서 위치 조회 (4) 관련 배송 기사 정보 연결 (5) 예상 도착 시간 계산 후 결과를 반환합니다. 읽기 경로도 동일한 구조입니다:

주목할 점은 **보안 정책 검사가 반드시 온톨로지 계층을 거친다**는 것입니다. Object Storage에 직접 접근하는 경로는 없습니다. 택배 시스템에서 송장번호 없이 물류창고에 직접 들어갈 수 없는 것과 같습니다.

### 2-2. 쓰기 경로 = 택배 발송

택배를 보내는 것은 조회보다 절차가 복잡합니다. "보내고 싶습니다"라고 하면 (1) 택배 접수 (2) 물품 검사 (3) 발송인 신원 확인 (4) 보험/특수 취급 필요 시 승인 (5) 실제 발송 (6) 송장 기록 (7) 수신자에게 알림. 쓰기 경로도 같은 구조입니다:

```
1. 사용자/에이전트 Action 실행 요청 (파라미터 포함) -- 택배 접수
2. Action Type 스키마 조회 -- 이 종류의 택배가 존재하는가?
3. 파라미터 유효성 검사 -- 물품 검사 (위험물인가? 규격에 맞는가?)
   → 실패 시 즉시 거부 + 이유 반환
4. 권한 검사 -- 이 사람이 이 택배를 보낼 수 있는가?
5. 승인 워크플로우 필요 시 → 대기 상태 전환 -- 고가 물품은 상위 승인 필요
6. 승인 완료 또는 즉시 실행 → Object Storage 업데이트 -- 실제 발송
7. 부수 효과 실행 (외부 시스템 API 호출) -- 보험 처리, 외부 알림
8. 감사 로그 자동 기록 -- 송장 기록 (누가, 언제, 무엇을, 왜)
9. 영향받는 모든 애플리케이션에 변경 전파 -- 수신자에게 알림
```

> **왜 필요한가?** 왜 직접 데이터베이스를 업데이트하지 않고 Action을 거치는가? 위 경로의 3단계(유효성 검사), 4단계(권한 검사), 5단계(승인 워크플로우), 8단계(감사 로그)를 보십시오. 택배 시스템 없이 직접 물류창고에 물건을 놓으면 추적이 불가능한 것처럼, Action 없이 DB를 직접 수정하면 누가, 왜, 언제 바꿨는지 알 수 없습니다. Action 하나에 이 모든 통제가 내장됩니다.

> **연결 포인트 → Phase 8**: Phase 8에서 배운 온톨로지 스케일링의 한계 중 하나인 "변경 관리의 복잡성"이 바로 이 Action 기반 쓰기 경로로 해결됩니다.

## 3. 보안 및 거버넌스 모델 -- 아파트 비유로 이해하기

보안은 Palantir 온톨로지의 핵심 차별점입니다. 이해를 위해 **아파트 건물**을 떠올려 보세요. 같은 건물이지만 열쇠(보안 등급)에 따라 접근할 수 있는 층이 다릅니다.

### 3-1. 보안의 두 계층

**계층 1: 스키마 보안 = 건물 설계도 접근 권한**

"이 건물의 설계도를 누가 볼 수 있고 수정할 수 있는가?" 건축가(온톨로지 관리자)만 설계도를 수정할 수 있고, 입주민(일반 사용자)은 설계도를 변경할 수 없습니다. 즉, 누가 새 Object Type을 만들 수 있는지, 누가 Action Type을 수정할 수 있는지 제어합니다.

**계층 2: 데이터 보안 = 층별/호실별 열쇠 시스템**

같은 건물에 살지만, 내 열쇠로는 내 집만 열 수 있습니다. 세 가지 수준으로 세분화됩니다:

```
행 수준 (Object-level) = 층 접근 권한:
  예: 각 병원 직원은 자신이 담당하는 환자 데이터만 볼 수 있다
  비유: 3층 열쇠를 가진 사람은 3층 호실만 접근 가능
  → 같은 Object Type이지만 인스턴스마다 접근 제어

열 수준 (Property-level) = 방 안의 금고 접근 권한:
  예: 일반 직원은 Employee.salary를 볼 수 없다. HR만 가능.
  비유: 방에 들어갈 수 있지만, 금고는 별도 열쇠가 필요
  → 같은 Object이지만 속성마다 접근 제어

셀 수준 (Cell-level) = 특정 호실의 특정 금고:
  행 + 열 조합으로 특정 셀 접근 제어
  예: 경쟁사 고객의 연락처 정보는 특정 역할만 접근 가능
  비유: 5층 302호의 금고 -- 특정 조합만 열 수 있음
```

> **왜 필요한가?** 전통적인 데이터베이스 보안은 "테이블 A에 접근 가능/불가능"만 제어합니다. 이것은 건물 입구에서 "이 건물에 들어갈 수 있는가/없는가"만 검사하는 것과 같습니다. 하지만 현실에서는 더 세밀한 제어가 필요합니다. 병원에서 간호사는 자신이 담당하는 병동 환자의 임상 정보는 볼 수 있지만, 다른 병동 환자의 정보나 급여 정보는 볼 수 없어야 합니다. 행/열/셀 수준 보안이 이를 가능하게 합니다.

### 3-2. Granular Policy -- 동적 출입증 시스템

Granular Policy(세분화 정책)는 정적 역할 기반이 아닌 **동적 조건 기반** 접근 제어입니다. 아파트 비유를 확장하면, 고정된 열쇠 대신 **상황에 따라 바뀌는 스마트 출입증**입니다.

```
Granular Policy 예시 (제조 도메인):
  정책명: "담당 공장 설비 접근"
  규칙: Machine.factoryId in current_user.authorizedFactoryIds

  → 수원 공장 담당자는 수원 공장 설비 데이터만 볼 수 있다
  → 글로벌 관리자는 모든 공장 설비를 볼 수 있다
  → 이 정책은 Workshop, OSDK, AIP 에이전트 모두에 동일하게 적용된다
```

**Before/After 대비:**

| Before (정적 역할 기반) | After (Granular Policy) |
|----------------------|------------------------|
| 담당 공장이 바뀌면 권한 역할을 재할당해야 함 | `authorizedFactoryIds`만 업데이트하면 자동 반영 |
| 역할이 10개, 조합이 100가지 -- 관리 불가 | 정책 규칙은 하나, 데이터(속성값)만 변경 |
| 새 앱을 만들면 역할 매핑을 다시 구현 | 온톨로지에 한 번 정의하면 모든 앱에 자동 적용 |

### 3-3. AI 에이전트에도 동일한 보안이 적용된다

이것이 Palantir 보안 모델의 가장 중요한 속성입니다:

```
중요: AIP 에이전트가 온톨로지에 접근할 때도
      인간 사용자와 동일한 보안 정책이 적용된다.

→ 에이전트가 "다른 부서 데이터를 몰래 훔쳐보는" 일이 구조적으로 불가능하다.
→ LLM에게 "권한 없는 초능력"을 주지 않는다.
→ AI 거버넌스 컴플라이언스 달성을 시스템 수준에서 보장한다.
```

> **왜 필요한가?** LLM에게 데이터베이스 접근 권한을 주면 어떤 일이 생길까요? 프롬프트 인젝션 공격, 권한 범위를 초과한 데이터 접근, 의도치 않은 정보 유출이 가능합니다. Palantir의 접근법은 LLM이 직접 데이터에 접근하지 않고 반드시 온톨로지 계층을 거치게 함으로써 이 위험을 구조적으로 차단합니다. 아파트의 스마트 출입증 시스템이 AI 로봇에게도 동일하게 적용되는 것과 같습니다.

> **연결 포인트 → Phase 7**: Phase 7에서 배운 LLM + Graph RAG 통합의 보안 과제가 여기서 해결책을 만납니다. Palantir의 온톨로지 계층이 LLM과 데이터 사이의 보안 경계 역할을 합니다.

## 4. 아키텍처의 핵심 원칙 -- 온톨로지가 중심에 있다

전체 아키텍처를 다시 보면 한 가지 패턴이 명확합니다: **모든 것이 온톨로지 계층을 통한다**. 도시 비유로 돌아가면, 온톨로지는 도시의 지도이자 교통 규칙이자 법률 체계입니다. 모든 주민(애플리케이션), 방문자(AI 에이전트), 공무원(관리자)이 이 규칙을 따릅니다.

```
데이터 통합 계층 → 온톨로지에 매핑    (원자재가 도시 규격에 맞게 가공됨)
애플리케이션 계층 → 온톨로지를 소비    (주민이 도시 서비스를 이용함)
AIP 에이전트 → 온톨로지를 통해 읽고 씀 (AI 안내원이 지도와 규칙을 따름)
보안 정책 → 온톨로지 계층에 정의      (법률이 도시 차원에서 적용됨)
Apollo 배포 → 온톨로지 변경을 전파     (새 규칙이 외곽까지 전달됨)
```

> **왜 필요한가?** 왜 이렇게 중앙화를 했는가? 분산 시스템에서는 같은 "고객"이 서로 다른 시스템에서 서로 다른 스키마로 존재합니다. 온톨로지를 중심에 두면 "고객이란 무엇인가"에 대한 단일 정의가 모든 시스템에 일관되게 적용됩니다. 도시에서 "주민"의 법적 정의가 하나이듯, 조직에서도 핵심 개념의 정의는 하나여야 합니다. 이것이 Palantir가 "운영 공통 언어"라고 부르는 개념입니다.

## 5. 실제 배포 사례 -- NHS England

NHS(National Health Service) England의 연방 데이터 플랫폼(FDP)은 Palantir 아키텍처가 실제 의료 현장에서 어떻게 생명을 살리는지 보여주는 사례입니다.

**문제 상황을 구체적으로 그려보겠습니다:**

런던의 한 병원에서 무릎 수술을 기다리는 환자 A씨. 대기 명단에 올라간 지 6개월입니다. 그런데 같은 병원 다른 과에서 취소된 수술 슬롯이 있습니다. 하지만 시스템이 분리되어 있어 아무도 이 빈 슬롯을 모릅니다. 환자 A씨는 계속 기다립니다.

이런 일이 NHS 전역에서 매일 수천 건 발생하고 있었습니다.

**온톨로지 계층 구성:**

```
Object Types:
  Patient Pathway, Procedure, Theatre Session, Clinician, Bed, Waitlist Entry

Granular Policy:
  각 Trust는 자신의 환자 데이터만 접근 가능
  NHS England 중앙은 집계 통계만 접근 가능

Functions:
  비어있는 Theatre Slot 자동 탐지
  대기 환자-빈 슬롯 매칭 추천
  당일 취소분 대체 환자 추천
```

**결과 -- 숫자가 말하는 변화:**

FDP 도입 후, 2025년 9월 말 기준 누적 추가 시술 환자 수는 **99,690명**에 달했습니다. 이것은 온톨로지가 단순한 데이터 통합 이상의 운영 변화를 만들어낸 증거입니다. 빈 수술실 슬롯을 자동으로 찾아내고, 대기 환자와 매칭하는 것 -- 분산된 데이터를 연결하는 것만으로 거의 10만 명이 더 빨리 치료를 받았습니다.

이 사례에서 보안 모델이 어떻게 작동하는지 주목하십시오. 각 병원(Trust)은 자신의 환자 데이터만 볼 수 있지만, 공통 온톨로지 스키마를 공유합니다. Granular Policy가 "내 병원 환자만 보이되, 분석 기능은 공유"하는 구조를 가능하게 합니다.

## 흔한 오해

> **흔한 오해**: "Palantir는 클라우드 데이터 웨어하우스와 같은 것이다"

> **실제로는**: 데이터 웨어하우스는 분석을 위한 읽기 최적화 저장소입니다. 도시 비유로 말하면 데이터 웨어하우스는 도서관(읽기 전용 아카이브)이고, Palantir Foundry는 살아있는 도시(읽기, 쓰기, 규칙, 보안이 통합된 운영 체계)입니다. 데이터를 저장하는 것뿐만 아니라 변경을 제어하고, 보안을 일관되게 적용하고, AI 에이전트가 안전하게 실행할 수 있는 환경을 제공합니다. 이것은 BI 툴이나 데이터 웨어하우스와 근본적으로 다른 범주의 시스템입니다.

## 요약

- Palantir는 **Foundry**(도시 기반 인프라), **AIP**(AI 안내원), **Apollo**(전력 배급 시스템) 3층 구조
- Foundry 안에서 **온톨로지 계층이 핵심** -- 도시의 지도이자 교통 규칙이자 법률 체계
- **읽기 경로**(택배 조회): 요청 → 스키마 확인 → 보안 검사 → 데이터 조회 → 그래프 탐색 → Function 계산 → 반환
- **쓰기 경로**(택배 발송): Action 요청 → 유효성 검사 → 권한 검사 → 승인 → 실행 → 감사 로그 → 변경 전파
- 보안은 **아파트 비유**: 스키마 보안(설계도 권한)과 데이터 보안(층별/호실별 열쇠)으로 구분
- **Granular Policy**(스마트 출입증)는 동적 조건 기반 -- 사용자와 AI 에이전트 모두에 동일 적용
- NHS FDP 사례: 분산 데이터 연결만으로 **99,690명** 추가 시술 -- 온톨로지의 운영 변화 증거
