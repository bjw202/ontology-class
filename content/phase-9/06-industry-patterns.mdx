# 산업별 사례와 설계 원칙

> "데이터를 가진 조직이 강한 것이 아니라, 데이터로 결정을 내리는 조직이 강하다."

온톨로지 이론과 Palantir 아키텍처를 배웠습니다. 하지만 진짜 질문은 이것입니다: **실제 현장에서 무엇이 달라지는가?**

이 세션은 세 가지를 합니다. 첫째, 제조/의료/군사 세 영역에서 "온톨로지 도입 전"의 실패와 "도입 후"의 변화를 생생하게 보여줍니다. 둘째, 이 사례들에서 플랫폼과 무관하게 적용할 수 있는 5가지 설계 원칙을 추출합니다. 셋째, Palantir의 한계와 대안을 균형 있게 평가합니다.

## 학습 목표

이 세션을 완료하면 다음을 할 수 있습니다:

1. **산업별 온톨로지 설계**: 제조/의료/군사 도메인에서의 Object, Link, Action 패턴을 설명한다
2. **Before/After 대비**: 온톨로지 도입 전후의 운영 변화를 구체적 사례로 설명한다
3. **설계 원칙 적용**: 5가지 핵심 원칙의 나쁜 패턴과 좋은 패턴을 구분할 수 있다
4. **한계와 대안 평가**: Palantir와 경쟁 솔루션의 트레이드오프를 비교한다
5. **실습 프레임워크 활용**: 결정 카탈로그 → 온톨로지 스케치 → PoC 구현 순서를 따른다

## 산업별 실전 설계 패턴

### 제조업 -- 스마트 팩토리

#### 온톨로지 없던 시절의 실패 이야기

수원의 한 반도체 공장에서 **3일 연속 불량률이 급증**했습니다. 현장 엔지니어는 문제를 알고 있었지만 원인을 찾기까지 **2주**가 걸렸습니다. 왜 그렇게 오래 걸렸을까요?

```
ERP 시스템:     "Lot 2847의 상태는 '생산 완료'"
MES 시스템:     "Machine M-14에서 3일간 알람 47건"
품질 시스템:    "불량 유형: edge burr, 비율 4.7%"
설비 로그:      "Tool T-33의 진동값 0.8mm (정상 범위: 0.5mm 이하)"
정비 시스템:    "M-14 최근 정비일: 45일 전"
```

데이터는 다 있었습니다. 하지만 **5개 시스템이 서로 연결되어 있지 않았습니다.** 엔지니어는 각 시스템에 로그인해서 수동으로 데이터를 모으고, 엑셀에 붙여넣고, 상관관계를 직접 분석해야 했습니다. "M-14의 불량이 T-33 공구 마모 때문인지, 레시피 변경 때문인지, 재료 이슈인지"를 파악하는 데 2주가 걸린 겁니다.

**그 2주 동안 불량 Lot는 계속 생산되었습니다.**

#### 온톨로지 도입 후의 변화

같은 상황이 온톨로지 도입 후에 발생하면:

```
자연어 질문: "최근 3일간 불량률이 급증한 설비와 원인을 분석해줘"

30분 안에 나오는 답:
  Machine M-14 → Tool T-33 (진동 drift 감지)
  → Lot 2847, 2848, 2849 (동일 공구로 가공)
  → Recipe R-12 (공차 민감도 높음)
  → 권장 Action: T-33 교체 + 첫 5개 Lot 전수검사
```

**2주가 30분으로.** 차이를 만든 것은 AI가 아닙니다. **연결**입니다. `Lot → processed_on → Machine → mounted_with → Tool → used_recipe → Recipe` -- 이 Link 체인이 존재하기 때문에 원인 추적이 자동화됩니다.

> **왜 필요한가?** 온톨로지가 없으면 "이번 주 불량률이 몇 %냐?"라는 BI 질문밖에 할 수 없습니다. 온톨로지가 있으면 "이 불량 Lot를 살리려면 어디를 건드려야 하나?"라는 **운영 질문**으로 전환됩니다. 질문의 종류가 바뀌면 현장의 의사결정 속도와 품질이 근본적으로 달라집니다.

#### 온톨로지 구성

**Object Types:** Plant, Process, Machine, Tool, Recipe, Lot, Measurement, Defect, Operator, Supplier

**Link Types:**
- `Lot → processed_on → Machine`
- `Tool → mounted_on → Machine`
- `Defect → observed_in → Lot`
- `Recipe → applied_to → Process`
- `Supplier → provides → Material`

**Functions (도메인 판단 로직):**
- 특정 Lot 불량의 원인 기여도 계산
- 설비 이상 조짐 점수 계산 (진동/온도/공구 수명 종합)
- 공정 조건 변경 시 품질 리스크 예측

**Actions (운영 개입 수단):**
- 작업 지시 생성
- 레시피 변경 승인
- Lot 격리
- 정비 요청 생성
- 공급사 이슈 에스컬레이션

### 의료/공공 -- NHS 연방 데이터 플랫폼

#### 온톨로지 없던 시절의 실패 이야기

런던 근교 병원의 수술 대기 환자 B씨. 무릎 관절 치환술을 기다린 지 8개월입니다. 통증은 점점 심해지고, 진통제 복용량도 늘었습니다.

그런데 **같은 병원 정형외과에서 오후 2시 수술이 취소**되었습니다. 환자가 감기에 걸려 수술 연기를 요청한 것입니다. 수술실, 마취과 의사, 간호사 -- 모든 자원이 준비되어 있지만, **빈 슬롯을 아는 사람이 아무도 없습니다.**

왜? 수술 스케줄은 Theatre Management 시스템에, 대기자 명단은 별도 시스템에, 의료진 가용 현황은 또 다른 시스템에 있었기 때문입니다.

**B씨는 빈 수술실을 모른 채 3개월을 더 기다렸습니다.**

이런 일이 NHS 전역에서 매일 수백 건 발생하고 있었습니다.

#### 온톨로지 도입 후의 변화

NHS England의 연방 데이터 플랫폼(FDP)이 도입된 후:

```
자동 탐지: Theatre Session TS-1142 취소 감지
  → Function 실행: 빈 슬롯에 매칭 가능한 대기 환자 탐색
  → Patient Pathway 우선순위 재평가
  → 환자 B씨 매칭: 동일 수술 유형, 사전 검사 완료, 즉시 가능
  → Action 제안: 수술 일정 재배치 + 환자 연락 + 의료진 확인

결과: 취소 발생 후 2시간 내에 대체 환자 수술 진행
```

**숫자가 말하는 변화:** 2025년 9월 말 기준, FDP theatre 관련 모듈 사용 Trust들에서 누적 추가 시술 환자 수는 **99,690명**. 거의 10만 명이 분산 데이터 연결만으로 더 빨리 치료를 받았습니다. 이것은 새로운 의사를 고용하거나 병원을 더 지은 것이 아닙니다. **이미 있는 자원의 빈 틈을 자동으로 찾아낸 것**입니다.

> **왜 필요한가?** 의료 시스템에서 자원 배분 비효율은 환자 생명과 직결됩니다. 수술실이 비어있는데 환자가 대기하는 모순 -- 이것은 데이터 부족이 아니라 **데이터 연결 부재**의 문제입니다. 온톨로지가 `Theatre Session → staffed_by → Clinician`, `Patient Pathway → requires → Procedure`를 연결하는 순간, 빈 틈이 보이기 시작합니다.

#### 온톨로지 구성

**Object Types:** Patient Pathway, Procedure, Theatre Session, Clinician, Bed, Waitlist Entry, Hospital Site

**Link Types:**
- `Patient Pathway → requires → Procedure`
- `Procedure → scheduled_in → Theatre Session`
- `Theatre Session → staffed_by → Clinician`

**Functions:**
- 대기자 우선순위 재평가
- 사용되지 않는 Theatre Slot 탐지
- 당일 취소분 대체 추천

**Actions:**
- 환자 예약 확정
- 대기자 우선순위 변경
- 수술 일정 재배치 제안

### 군사/국방 -- NATO 사례

#### 온톨로지 없던 시절의 실패 이야기

NATO 다국적 훈련 중 상황. 정찰 드론이 적 차량 이동을 탐지했습니다. 하지만 이 정보가 지상군 지휘관에게 도달하기까지 **47분**이 걸렸습니다.

왜? 정찰 데이터는 ISR(정보/감시/정찰) 시스템에, 부대 배치 현황은 C2(지휘통제) 시스템에, 보급 상태는 물류 시스템에 있었기 때문입니다. 각 시스템의 데이터를 수동으로 취합하고, 표준화하고, 해석하는 데 시간이 걸렸습니다.

```
ISR 시스템:     "Grid AB-1247에서 차량 3대 이동 탐지"
C2 시스템:      "가용 대응 부대: Alpha 중대 (Grid AB-1300)"
물류 시스템:    "Alpha 중대 연료 잔량: 72시간분"
지형 시스템:    "AB-1247 → AB-1300 이동 시간: 25분"
```

데이터는 있었지만 **통합된 상황 인식(situational awareness)**이 없었습니다. 지휘관은 "상황판"의 숫자를 보는 것이지, "운영 가능한 세계"를 보는 것이 아니었습니다.

#### 온톨로지 도입 후의 변화

2025년 4월 Palantir Maven Smart System NATO가 Allied Command Operations에 도입된 후:

```
자동 탐지: Sensor S-22가 Target T-0891 탐지 (Grid AB-1247, 차량 3대)
  → 즉시 Link 탐색: Target T-0891 → nearest → Unit (Alpha 중대)
  → Function 실행: 위협 우선순위 점수 계산, 보급 지속 가능 시간, 경로 리스크
  → 통합 상황: "Alpha 중대, 25분 이동거리, 연료 충분, 경로 리스크 낮음"
  → Action 제안: 대응 명령 초안 자동 생성 + 지휘관 승인 대기

결과: 탐지-판단-대응 체인이 47분 → 수 분으로 단축
```

**분산된 정보가 하나의 운영 세계로 통합**되면, 지휘관은 각 시스템을 번갈아 보는 것이 아니라 **연결된 객체 세계에서 바로 판단하고 행동**합니다.

> **왜 필요한가?** 군사에서 핵심은 **데이터를 전장 객체(battlefield objects)로 번역**하는 일입니다. 센서가 보내는 좌표와 숫자는 "데이터"이지만, 그것이 Unit, Target, Mission, Supply Node라는 객체로 연결되는 순간 "운영 가능한 세계"가 됩니다. 지휘관이 "상황판"이 아니라 "운영 가능 세계"를 보게 만드는 것이 온톨로지의 역할입니다.

#### 온톨로지 구성

**Object Types:** Unit, Platform, Target, Sensor, Route, Area of Interest, Supply Node, Mission

**Link Types:**
- `Sensor → detects → Target`
- `Unit → assigned_to → Mission`
- `Mission → depends_on → Supply Node`

**Functions:**
- 위협 우선순위 점수 계산
- 보급 지속 가능 시간 계산
- 경로 리스크 평가

**Actions:**
- 관심 구역 변경, 자산 배치 변경, 경보 발행, 임무 계획 수정

## 완전 시나리오 -- 5회차 참조

> **연결 포인트 → 5회차 (AIP -- 온톨로지 위의 AI)**: "자연어 질문에서 운영 변화까지"의 7단계 완전 시나리오(질문 해석 → Ontology Query → Function 실행 → 문서 컨텍스트 결합 → LLM 종합 판단 → Action 실행 → Ontology 반영)는 5회차에서 상세히 다루었습니다. 여기서는 위 세 산업 사례가 모두 동일한 7단계 루프를 따른다는 점만 확인하고 넘어갑니다. 핵심 통찰은: **일반 챗봇은 답하고 끝나지만, 운영형 Ontology + LLM은 답한 뒤 세계를 바꾼다**는 것입니다. 이 닫힌 루프(closed loop)가 단순 정보 시스템과 운영 지능 시스템의 근본적 차이입니다.

## 5가지 핵심 설계 원칙

*Palantir 사례에서 플랫폼과 무관하게 추출할 수 있는 설계 원칙들. 각 원칙마다 나쁜 패턴과 좋은 패턴을 대비합니다.*

### 원칙 1: 데이터가 아닌 결정을 설계하라

> **왜 필요한가?** 많은 조직이 "우리가 가진 데이터를 정리하자"에서 출발합니다. 하지만 데이터부터 시작하면 "정리는 했는데 쓸모가 없다"는 결과로 끝나기 쉽습니다. 출발점을 바꿔야 합니다.

**나쁜 패턴:**
```
1. "우리 DB에 테이블이 200개 있으니 200개 Object Type을 만들자"
2. 모든 컬럼을 Property로 매핑
3. 완성 후 "그래서 이걸로 뭘 하지?" -- 쓰는 사람 없음
```

**좋은 패턴:**
```
1. "공장장이 매일 아침 내리는 결정 3가지가 뭐지?"
   - 오늘 어떤 라인을 우선 가동할까?
   - 어제 불량이 터진 설비를 돌릴까 말까?
   - 긴급 주문을 기존 일정에 끼울 수 있을까?
2. 이 결정을 지원하는 Object/Link/Function만 먼저 설계
3. 공장장이 실제로 사용 → 피드백 → 확장
```

**실습 프레임워크 -- 결정 카탈로그 작성 (1일):**
도메인에서 매일/매주 내려지는 중요 결정 10개를 나열하고, 각 결정에 대해 (1) 누가 내리는가, (2) 어떤 정보가 필요한가, (3) 결정 후 무엇이 변경되는가를 정의합니다.

### 원칙 2: 쓰기는 반드시 통제 지점을 통과하게 하라 (Action Pattern)

> **왜 필요한가?** 데이터 변경이 통제되지 않으면 "누가 언제 왜 바꿨는지" 추적이 불가능합니다. 규제 산업(의료, 금융, 군사)에서는 이것이 법적 문제가 됩니다.

**나쁜 패턴:**
```python
# 직접 DB 수정 -- 유효성 검사 없음, 감사 불가
@app.post("/defects/{defect_id}/escalate")
async def escalate(defect_id: str, body: dict):
    db.execute(f"UPDATE defects SET status='escalated' WHERE id='{defect_id}'")
    return {"ok": True}
    # 문제: SQL 인젝션 취약, 권한 검사 없음, 감사 로그 없음
    # 문제: 이미 처리된 불량도 에스컬레이션 가능
```

**좋은 패턴:**
```python
# Action Pattern -- 유효성 검사 → 상태 변경 → 감사 로그 3단계
class EscalateDefectAction(BaseModel):
    defect_id: str
    reason: str  # 최소 20자 유효성 검사
    severity: Literal["low", "medium", "high", "critical"]

@app.post("/actions/escalate-defect")
async def escalate_defect(
    action: EscalateDefectAction,
    user: User = Depends(get_current_user)
):
    defect = db.query(Defect).get(action.defect_id)

    # 1단계: 유효성 검사
    if defect.status != "open":
        raise HTTPException(400, "이미 처리된 불량입니다")
    if len(action.reason) < 20:
        raise HTTPException(400, "사유는 20자 이상이어야 합니다")

    # 2단계: 상태 변경
    defect.status = "escalated"
    defect.escalated_at = datetime.now()

    # 3단계: 감사 로그 자동 기록
    audit = AuditLog(
        action="EscalateDefect", actor=user.id,
        target=defect.id, params=action.dict()
    )
    db.add(audit)
    db.commit()
```

핵심: 모든 상태 변경이 **유효성 검사 → 상태 변경 → 감사 로그**의 3단계를 반드시 거칩니다. AI 에이전트도 인간과 동일한 경로를 통합니다.

### 원칙 3: Golden Record -- 하나의 정의, 여러 소비자

> **왜 필요한가?** 여러 팀이 각자 "설비"를 정의하면 같은 단어가 다른 의미를 갖게 됩니다. 이것이 데이터 사일로의 근본 원인입니다.

**나쁜 패턴:**
```
영업팀:    Machine = { id, name, sales_region, contract_date }
정비팀:    Equipment = { equip_no, type, last_maintenance }
품질팀:    설비 = { 설비코드, 라인, 불량이력 }

→ 같은 물리적 설비가 3가지 이름, 3가지 스키마로 존재
→ "M-14의 정비 이력과 불량 이력을 같이 보려면?" -- 불가능
```

**좋은 패턴:**
```
중앙 온톨로지:
  Object Type: Machine
    - machineId (PK)
    - name, status, location, lastMaintenance, defectRate

  모든 팀이 이 하나의 정의를 참조:
    영업팀 앱 → Machine + sales-specific views
    정비팀 앱 → Machine + maintenance-specific views
    품질팀 앱 → Machine + quality-specific views

→ "M-14의 정비 이력과 불량 이력을 같이 보려면?" -- 즉시 가능
```

- **Palantir 구현:** endorsed Object Type + 모든 앱이 동일 온톨로지 소비
- **자체 구축 (OWL):** 단일 온톨로지 파일 + `owl:imports`로 팀별 확장

### 원칙 4: 보안은 데이터 레벨에서, 애플리케이션 레벨이 아니라

> **왜 필요한가?** 앱에서 보안을 구현하면, 앱이 10개일 때 보안 구멍도 10배로 늘어납니다. 데이터 레벨에서 한 번 정의하면 어떤 앱을 통해도 동일하게 적용됩니다.

**나쁜 패턴:**
```
앱 A (Workshop):
  if user.role == "admin": show_salary()
  else: hide_salary()

앱 B (커스텀 대시보드):
  # 개발자가 salary 필터를 깜빡함
  SELECT * FROM employees  -- salary 컬럼이 그대로 노출!

앱 C (OSDK 앱):
  # 또 다른 개발자가 다른 방식으로 구현
  if user.department == "HR": ...  -- role이 아니라 department로 체크

→ 앱마다 보안 로직이 다름, 한 군데만 빠뜨려도 데이터 유출
```

**좋은 패턴:**
```
데이터 레벨 보안 (온톨로지에 한 번 정의):
  Property "salary": visible_to(role: "HR", "Executive")

  → 앱 A든, 앱 B든, 앱 C든, AI 에이전트든
  → salary 속성은 HR과 Executive 역할만 볼 수 있음
  → 개발자가 필터를 빠뜨려도 데이터가 보이지 않음
```

자체 구축 시 Row-level security + JWT claim 기반 필터로 구현합니다.

### 원칙 5: 온톨로지 생명주기 관리

> **왜 필요한가?** 온톨로지도 소프트웨어처럼 진화합니다. 사용하지 않는 Object Type이 쌓이면 혼란이 생기고, 갑자기 삭제하면 의존하는 앱이 깨집니다.

**나쁜 패턴:**
```
1월: Machine_v1 생성
3월: Machine_v2 생성 (v1과 겹치는 속성 70%)
6월: "v1 쓰는 데 있나?" -- 아무도 모름
9월: v1 삭제 → 정비팀 대시보드 깨짐 → 긴급 복구
```

**좋은 패턴:**
```
experimental (개발) → active (운영) → deprecated (폐기 예고) → 삭제

폐기 예고 시 반드시:
  1. 이유 문서화: "Machine_v1은 v2에 통합됨"
  2. 마감 기한 명시: "2024년 6월 30일까지 마이그레이션"
  3. 대체 리소스 안내: "Machine_v2의 동일 속성 매핑표 첨부"
  4. 영향받는 소비자 목록: "정비팀 대시보드, 품질 보고서, OSDK 앱 3개"
  5. 사전 공지: 최소 90일 전 공지
```

### 학문적 온톨로지(OWL/RDF)가 유리한 경우

1. **논리적 일관성이 생사와 연결될 때** -- 의약품 상호작용, 항공기 시스템 인증 → OWL DL + Reasoner로 모순 자동 탐지
2. **다른 조직의 온톨로지와 직접 연결해야 할 때** -- 학술 데이터 공유, 정부 데이터 연계 → RDF Linked Data, OWL/SPARQL 표준
3. **복잡한 서브클래스 추론이 필요할 때** -- Gene Ontology, SNOMED CT → Description Logic Reasoner

## 핵심 통찰

> **왜 필요한가?** **운영형 온톨로지의 본질은 데이터 모델링이 아닌 운영 모델링입니다.** 객체와 관계만 정의하는 것이 아니라, 그 위에 Function(판단 로직)과 Action(개입 수단)과 Security(통제)를 얹을 때 진정한 "실행 가능한 온톨로지"가 됩니다.

> **왜 필요한가?** **Palantir의 강점은 "똑똑한 AI" 자체보다, 구조화된 운영 세계 위에 AI를 안전하게 붙이는 방식에 있습니다.** LLM이 온톨로지에 직접 접근하지 않고 허용된 tool을 통해 "요청"만 하는 구조가 운영 안전성의 핵심입니다.

> **왜 필요한가?** 세 산업(제조/의료/군사)의 공통점은 **"데이터는 있었지만 연결이 없었다"**는 것입니다. 온톨로지가 하는 일의 80%는 "새로운 데이터 수집"이 아니라 "기존 데이터의 연결"입니다.

## 흔한 오해

> **흔한 오해**: "Palantir 온톨로지 = Graph RAG"

> **실제로는**: Palantir를 단지 "Graph RAG 회사"로 보면 절반만 보는 것입니다. Graph RAG는 지식 검색 및 응답 생성에 초점을 맞추지만, Palantir 온톨로지는 **운영 실행**에 초점을 맞춥니다. 가장 큰 차이는 쓰기 능력입니다 -- Graph RAG는 읽기만 가능하지만, Palantir는 Action을 통해 실제 시스템 상태를 바꿀 수 있습니다. 거버넌스(권한/감사/유효성 검사)와 비즈니스 로직(Function)이 내장되어 있다는 점도 근본적 차이입니다. Palantir의 본질은 **"지식 검색 시스템"이 아니라 "운영 실행 시스템"**에 더 가깝습니다.

## 요약

이 세션에서 배운 핵심 내용:

1. **산업별 Before/After**: 제조(2주 → 30분 원인 분석), 의료(빈 슬롯 자동 탐지로 99,690명 추가 시술), 군사(47분 → 수 분 상황 인식) -- 차이를 만든 것은 AI가 아니라 **데이터 연결**
2. **5가지 설계 원칙**: (1) 결정을 설계하라, (2) 쓰기 통제 지점, (3) Golden Record, (4) 데이터 레벨 보안, (5) 생명주기 관리 -- 각각 나쁜 패턴과 좋은 패턴으로 구분
3. **한계 인식**: 벤더 종속성, 높은 비용, OWL이 더 적합한 상황 등 트레이드오프를 균형 있게 평가
4. **플랫폼 독립 원칙**: 5가지 설계 원칙은 Palantir 없이도 FastAPI + Pydantic + SQLAlchemy로 구현 가능

> "데이터를 운영 가능한 세계로 번역하는 것, 그것이 운영형 온톨로지의 본질이다."
