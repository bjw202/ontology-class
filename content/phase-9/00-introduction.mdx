# 9단계: 왜 팔란티어 온톨로지인가?

> "데이터를 가진 조직은 많다. 데이터로 결정하는 조직은 드물다. 결정에서 배우는 조직은 거의 없다."
> — Palantir 플랫폼 설계 철학

지금까지 8단계에 걸쳐 온톨로지의 이론적 기반을 쌓았습니다. RDF 트리플의 구조부터 OWL의 논리적 추론, 그리고 SPARQL 질의까지 학습했습니다. 이제 9단계에서는 그 모든 이론이 실제 엔터프라이즈 환경에서 어떻게 구현되는지 살펴봅니다.

Palantir는 전 세계 수십 개 정부기관, 군사 조직, 대형 기업에 데이터 플랫폼을 납품하면서 **공통된 실패 패턴**을 발견했습니다. 그리고 그 해법으로 온톨로지를 플랫폼의 핵심 계층으로 채택했습니다. 이것은 이론적 선택이 아니라, 수천 번의 배포 경험에서 나온 **실증적 결론**입니다.

이 단계는 두 가지 질문에 동시에 답합니다.

- *"팔란티어 온톨로지는 개념적으로 어떻게 설계되었는가?"* — 아키텍처, 구성 요소, OWL 비교
- *"팔란티어 온톨로지는 실제 운영에서 어떻게 동작하는가?"* — 운영 루프, 산업 사례, LLM 통합

## 학습 목표

이 단계를 완료하면 다음을 할 수 있습니다:

1. **문제 진단**: 기존 데이터 아키텍처가 왜 의사결정 지원에 실패하는지 세 가지 구조적 원인을 설명한다
2. **철학 이해**: Palantir의 "결정 중심(Decision-centric)" 설계 철학과 결정 데이터(Decision Data) 개념을 정의한다
3. **아키텍처 파악**: Foundry + AIP 스택의 레이어 구조와 각 레이어의 역할을 설명한다
4. **개념 연결**: 학문적 온톨로지(OWL/RDF)와 Palantir 온톨로지의 공통점과 핵심 차이를 비교한다
5. **실용 평가**: Palantir 온톨로지가 적합한 상황과 그렇지 않은 상황을 구분한다

## 1. 문제 진단: 왜 기존 데이터 아키텍처가 실패하는가

Palantir가 온톨로지를 플랫폼의 핵심으로 채택한 것은 이론적 선택이 아니라 수십 개 고객사 배포 경험에서 나온 결론이다. Gotham(국방·정보 분석)과 Foundry(민간 기업 운영)를 반복 배포하면서 동일한 실패 패턴을 마주쳤다.

> **왜 필요한가?** 아무리 강력한 BI 도구나 데이터 레이크가 있어도, 조직의 서로 다른 팀이 동일한 개념을 다르게 정의하면 통합 자체가 불가능해진다. 이 근본 문제를 해결하지 않으면 기술 도입은 오히려 복잡성만 증가시킨다.

### 문제 1: 데이터 사일로와 의미의 파편화

조직의 각 부서는 동일한 단어를 다르게 정의한다.

```
영업팀의 "고객"  ≠  물류팀의 "고객"  ≠  재무팀의 "고객"
같은 단어, 다른 스키마, 다른 시스템 → 통합 불가
```

이것은 기술적 문제가 아니라 **의미론적 문제(semantic problem)**다. 스키마를 맞추는 ETL 작업으로는 해결할 수 없다. 영업팀의 "고객"이 계약 체결 시점의 법인을 의미하고, 물류팀의 "고객"이 배송지 주소를 가진 수령인을 의미한다면, 이 두 개념은 기술적으로 연결될 수 없다.

Phase 2에서 배운 RDF/OWL이 바로 이 의미론적 문제를 다루는 이유다.

> **연결 포인트 → Phase 2**: RDF의 URI 기반 리소스 식별과 OWL의 클래스 정의는 "의미의 파편화" 문제를 정확히 겨냥한 기술이다. Palantir의 Object Type은 이 개념을 엔터프라이즈 운영 환경에 맞게 재구현한 것이다.

### 문제 2: 분석은 되지만 실행이 안 된다

현대 기업의 데이터 스택은 분석 능력에 집중되어 있다. 대시보드는 현황을 보여주지만 "그래서 무엇을 해야 하는가"로 연결되지 않는다.

```
현황 파악 (BI Dashboard)
    ↓
분석 결과 확인
    ↓
??? 수동 작업 필요 ???
    ↓
실제 운영 시스템(ERP, CRM, SCADA)에 반영
```

이 "마지막 마일(Last Mile)" 문제가 핵심이다. 분석 시스템과 실행 시스템 사이의 단절이 데이터 주도 의사결정을 막는다.

### 문제 3: AI가 맥락을 모른다

LLM(Large Language Model)이 아무리 강력해도, 기업의 "Customer"가 무엇인지, "공정 이상"이 어떻게 정의되는지 모른다. 데이터 레이크에 쌓인 테이블과 컬럼은 기계가 읽을 수 있지만 **이해**할 수 없다.

```
데이터 레이크의 테이블 구조:
  orders.customer_id   → 이것이 법인인가? 개인인가?
  process_logs.status  → "ERROR"가 어떤 심각도인가?
  machine_data.temp    → 정상 범위는 무엇인가?

LLM은 컬럼 이름을 볼 수 있지만
  도메인 의미, 비즈니스 규칙, 조직별 정의를 알 수 없다.
```

이 세 가지 문제는 모두 같은 뿌리에서 나온다. **의미의 부재(Lack of Semantics)**다.

## 2. 핵심 철학: 데이터 중심에서 결정 중심으로

Palantir는 조직이 존재하는 이유를 "결정을 내리는 것"으로 정의한다. 이 관점에서 데이터 시스템의 목적도 재정의된다.

| 기존 관점 | Palantir의 관점 |
|-----------|----------------|
| 데이터를 어떻게 저장할 것인가 | 어떤 결정을 지원할 것인가 |
| 쿼리 성능 최적화 | 의사결정 속도 최적화 |
| 스키마 설계 | 결정 시나리오 설계 |
| 데이터 정합성 | 결정의 일관성과 감사 가능성 |

> **왜 필요한가?** 데이터 중심 설계는 "무엇이 있는가"에 집중하고, 결정 중심 설계는 "무엇을 해야 하는가"에 집중한다. 이 철학적 전환이 온톨로지 구조 전체에 영향을 미친다. Object Type의 설계 단위가 "테이블"이 아니라 "결정에 필요한 개체"가 되고, Action Type이 "업데이트 쿼리"가 아니라 "운영 개입 수단"이 되는 이유다.

### 결정 데이터(Decision Data)의 개념

Palantir의 온톨로지는 전통적 데이터(구조화·비정형·스트리밍)와 함께 **결정이 내려지는 과정에서 생성되는 데이터**도 포함한다.

```
전통적 데이터:
  측정값, 트랜잭션, 이벤트 로그, 문서

결정 데이터(Decision Data):
  - 어떤 맥락에서 결정이 내려졌는가
  - 어떤 옵션들을 검토했는가
  - 무엇을 최종 선택했는가
  - 그 결과는 무엇이었는가
  - 다음 유사 상황에서 무엇을 달리 해야 하는가
```

이것이 AI가 단순 데이터 조회를 넘어 **의사결정 패턴을 학습**할 수 있게 하는 기반이다. 과거의 결정과 그 결과가 온톨로지에 보존되기 때문에, AI 에이전트는 "이 상황에서 과거에 어떻게 결정했고 그 결과가 어땠는가"를 참조할 수 있다.

> **왜 필요한가?** 전통적 Machine Learning은 과거 데이터 패턴에서 예측 모델을 만든다. 결정 데이터는 한 걸음 더 나아가 "왜 그런 결정을 했는가"의 이유와 맥락까지 보존한다. 이것이 설명 가능한 AI(Explainable AI)를 구현하는 구조적 기반이다.

## 3. Palantir 온톨로지의 위치: 학문과 실무 사이

이 그래프가 보여주는 핵심 통찰은 **의도적 트레이드오프**다. Palantir는 논리적 완전성을 포기하는 대신 운영 현장 채택 가능성을 극대화했다. 이것은 결함이 아니라 설계 선택이다.

> **왜 필요한가?** OWL DL은 완전한 논리적 추론이 가능하지만, 실시간 대규모 데이터에 연결하고 비개발자가 구축하며 밀리초 단위로 응답하는 운영 시스템을 만들기 어렵다. Palantir는 "추론의 완전성"보다 "운영의 실행 가능성"을 선택했다.

> **연결 포인트 → Phase 6**: Phase 6에서 배운 표준 온톨로지(SNOMED CT, Gene Ontology)는 논리적 일관성이 핵심이다. 이런 도메인에서는 OWL DL + Reasoner가 여전히 최적이다. Palantir 방식이 항상 우월한 것이 아니라, 목적이 다른 것이다.

## 4. 왜 지금 이것을 배우는가

Palantir의 접근법은 엔터프라이즈 AI의 핵심 문제를 해결하는 하나의 완성된 사례다. 이 사례를 통해 다음을 이해할 수 있다.

**첫째, 온톨로지의 실용적 가치**

이론으로만 배운 온톨로지가 실제 수십 억 달러 규모의 플랫폼에서 어떻게 구현되는지 볼 수 있다.

**둘째, 설계 원칙 추출**

Palantir의 특정 기술을 쓰지 않더라도, 그 설계 원칙은 자신의 시스템에 적용할 수 있다. Action Pattern, Golden Record, 결정 중심 설계 등은 플랫폼 독립적 원칙이다.

**셋째, 비판적 평가 능력**

Palantir 온톨로지의 강점과 한계를 알아야 실제 프로젝트에서 올바른 기술 선택을 할 수 있다.

## 흔한 오해

> **흔한 오해**: "Palantir 온톨로지는 학문적 온톨로지(OWL/RDF)의 기업용 구현이다."

> **실제로는**: Palantir 온톨로지는 OWL/RDF에서 영감을 받았지만, 설계 목표가 근본적으로 다르다. OWL은 "세계를 논리적으로 표현하고 추론하는 것"이 목표이고, Palantir 온톨로지는 "조직의 운영 세계를 실행 가능하게 모델링하는 것"이 목표다. 추론 엔진 대신 Action 거버넌스를 핵심에 놓은 것이 그 차이를 잘 보여준다.

> **흔한 오해**: "Palantir는 그냥 고급 BI(Business Intelligence) 도구다."

> **실제로는**: BI 도구는 읽기 전용이다. 현황을 보여주는 것이 목적이다. Palantir 온톨로지는 Action을 통해 실제 운영 시스템을 변경하는 쓰기 가능한(writable) 운영 모델이다. "보는 것"과 "바꾸는 것"의 차이가 핵심이다.

## 요약

- Palantir가 온톨로지를 채택한 것은 세 가지 구조적 문제를 해결하기 위해서다: 의미의 파편화, 분석-실행 단절, AI의 맥락 부재
- 핵심 철학은 "데이터 중심"에서 "결정 중심"으로의 전환이며, 결정 데이터(Decision Data) 개념이 AI 학습의 기반이 된다
- Palantir 온톨로지는 논리적 완전성(OWL DL)보다 운영 실용성을 선택한 의도적 트레이드오프다
- 이 단계의 학습 목표는 Palantir 기술 습득이 아니라, 온톨로지 설계 원칙의 실전 적용 방식을 이해하는 것이다
- 다음 회차에서는 "디지털 트윈"과 "6단계 운영 루프"를 통해 Palantir 온톨로지가 실제로 어떻게 동작하는지 살펴본다
