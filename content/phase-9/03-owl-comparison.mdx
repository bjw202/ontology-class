# 9단계 3회차: 학문적 온톨로지 vs. Palantir — 개념 재매핑

> "이론과 실용 사이의 간극은 도구를 이해할 때가 아니라, 도구를 선택할 때 비로소 드러난다."

OWL과 RDF는 지식 표현의 학문적 정점입니다. 엄밀한 논리 체계, 형식 추론, 개방 세계 가정(OWA) — 이 모든 것이 완전하고 일관된 지식 시스템을 구축하기 위해 설계되었습니다. 반면 Palantir 온톨로지는 동일한 목표를 전혀 다른 방식으로 추구합니다. **실시간 운영, 비개발자 접근성, 거버넌스 내재화** — Palantir는 논리적 완전성보다 운영 현장 채택 가능성을 선택했습니다.

이 회차에서는 두 세계의 핵심 개념들을 1:1로 대응시켜 보고, 각각이 어떤 설계 철학에서 나왔는지 깊이 이해합니다. OWL이 더 낫거나 Palantir가 더 낫다는 이야기가 아닙니다. **서로 다른 문제를 풀기 위해 서로 다른 트레이드오프를 선택했다는 것** 을 이해하는 것이 이 회차의 핵심입니다.

이 분석은 단순한 학문적 비교를 넘어섭니다. 여러분이 나중에 자체 온톨로지 시스템을 설계할 때, 혹은 기존 OWL 기반 시스템을 운영 환경으로 확장할 때, 이 두 세계의 트레이드오프를 이해하고 있어야 현명한 설계 결정을 내릴 수 있습니다.

## 학습 목표

이 회차를 마치면 다음을 할 수 있습니다:

1. **개념 매핑 이해**: OWL/RDF의 주요 구성요소와 Palantir 대응 개념을 정확히 매핑한다
2. **OWA vs 거버넌스 모델 구분**: 개방 세계 가정과 Palantir의 쓰기 제어 모델의 철학적 차이를 설명한다
3. **표현력 vs 실용성 트레이드오프 분석**: 논리적 완전성을 희생하고 운영 채택성을 얻는 설계 선택의 의미를 평가한다
4. **추론 방식의 차이 이해**: Description Logic Reasoner와 AIP(LLM 기반) 추론의 근본적 차이를 설명한다
5. **적합한 도구 선택**: 언제 OWL을 써야 하고 언제 Palantir 방식이 더 적합한지 판단한다

## 1. 전체 개념 매핑 테이블

먼저 두 세계의 핵심 개념들을 한눈에 비교합니다:

| OWL/RDF 개념 | Palantir 대응 개념 | 핵심 차이 |
|---|---|---|
| `owl:Class` | Object Type | 추상 정의 vs. **실 데이터소스 바인딩** |
| `owl:Individual` | Object (인스턴스) | 수동 선언 vs. **파이프라인 자동 생성** |
| `owl:ObjectProperty` | Link Type | RDF Triple vs. **데이터셋 조인** |
| `owl:DatatypeProperty` | Property | XSD 타입 vs. **미디어·시맨틱 등 확장 타입** |
| `owl:Axiom` | Action Type + Function | 논리 공리 vs. **비즈니스 로직 + 트랜잭션** |
| `rdfs:subClassOf` | Interface (다형성) | 계층 상속 vs. **형태 기반 다형성** |
| Description Logic Reasoner | AIP (LLM 기반) | 형식 논리 추론 vs. **의미 기반 추론** |
| SPARQL | OSDK / 자연어 질의 | 기술 언어 vs. **개발자+비개발자 모두 접근** |
| Open World Assumption | Closed-action model | "모를 수 있다" vs. **"모르면 쓸 수 없다"** |

> **왜 필요한가?** 이 매핑 테이블은 단순한 용어 번역이 아닙니다. 각 대응 쌍에는 서로 다른 설계 철학이 숨어 있습니다. OWL이 "무엇을 알 수 있는가"에 집중한다면, Palantir는 "무엇을 할 수 있는가"에 집중합니다. 이 차이를 이해해야 두 시스템의 강점과 약점을 제대로 평가할 수 있습니다.

### 1-1. owl:Class vs. Object Type

`owl:Class`는 순수한 추상 정의입니다. `owl:Class :Machine`을 선언해도 실제 Machine 데이터가 어디서 오는지 OWL은 알지 못합니다. 인스턴스를 하나씩 수동으로 선언하거나, 별도 ETL 파이프라인으로 트리플을 생성해야 합니다.

Palantir의 Object Type은 다릅니다. Object Type을 정의하는 순간 **어떤 데이터셋의 어떤 컬럼이 이 타입의 속성이 되는지** 를 바인딩합니다. 파이프라인이 데이터를 갱신하면 Object 인스턴스도 자동으로 갱신됩니다.

```
OWL 방식:
  owl:Class :Machine
  :M14 rdf:type :Machine
  :M14 :vibration "2.3"^^xsd:float
  → 수동 선언, 갱신도 수동

Palantir 방식:
  Object Type: Machine
  → 데이터셋 machine_sensors.csv 바인딩
  → 파이프라인이 갱신하면 M-14 Object도 자동 갱신
```

### 1-2. rdfs:subClassOf vs. Interface (다형성)

`rdfs:subClassOf`는 계층 상속입니다. `:ElectricVehicle rdfs:subClassOf :Vehicle` — ElectricVehicle은 Vehicle의 모든 속성을 물려받습니다. 추론기(Reasoner)가 이 계층을 따라 추론합니다.

Palantir의 Interface는 **형태 기반 다형성(structural subtyping)** 에 가깝습니다. "이 Interface가 요구하는 속성과 Link Type을 갖추면, 어떤 Object Type이든 이 Interface를 구현할 수 있다." 계층 구조가 아니라 능력(capability)으로 다형성을 표현합니다.

> **왜 필요한가?** 계층 상속은 단일 분류 체계를 강제합니다. 현실의 엔터프라이즈 데이터는 다중 분류가 필요합니다. 동일한 Machine이 "유지보수 대상"이기도 하고 "생산 자산"이기도 합니다. Interface 방식은 이런 유연성을 허용하면서도 타입 안전성을 유지합니다.

## 2. 가장 중요한 차이 — OWA vs. 거버넌스 모델

이것이 두 시스템의 철학적 핵심 분기점입니다.

### 2-1. 개방 세계 가정(Open World Assumption)이란

학문적 온톨로지는 **OWA(Open World Assumption)** 를 따릅니다. 기록되지 않은 것은 "거짓"이 아니라 "알 수 없다"입니다.

```
OWA 세계에서:
  :M14 :hasDefect :D001 이 없다면
  → "M14에 결함이 없다"가 아니라
  → "M14의 결함 여부를 알 수 없다"

추론기는 이 열린 가능성을 고려하며 추론한다.
```

이 가정은 지식 공유와 통합에 강력합니다. 내가 모르는 사실을 타인이 보완할 수 있고, 모순 없이 지식을 병합할 수 있습니다.

> **왜 필요한가?** Gene Ontology, SNOMED CT 같은 생의학 온톨로지는 OWA 덕분에 전 세계 연구자가 지식을 분산 기여할 수 있습니다. OWA가 없다면 중앙화된 단일 권위체 없이는 지식 통합이 불가능합니다.

### 2-2. Palantir의 Closed-action Model

Palantir는 OWA 대신 **"쓰기는 반드시 Action을 통한다"** 는 원칙을 채택했습니다. 이는 CWA(Closed World Assumption)에 가깝지만, 데이터의 진실성보다 **변경의 통제** 에 초점이 있습니다.

```
OWL 세계:   누구나 트리플을 추가할 수 있다. 모순은 추론기가 사후 탐지.
Palantir:   변경은 반드시 사전 정의된 Action을 통해야 한다.
            Action에는 유효성 검사, 승인, 감사 추적이 내장된다.
```

이 차이는 단순히 기술적인 것이 아닙니다. **운영 환경에서의 책임 소재와 거버넌스 구조** 를 결정합니다.

| 관점 | OWA (OWL) | Closed-action (Palantir) |
|---|---|---|
| 데이터 추가 | 누구나 트리플 추가 가능 | 사전 정의된 Action만 허용 |
| 모순 처리 | 추론기가 사후 탐지 | Action 유효성 검사로 사전 차단 |
| 감사 추적 | 별도 구현 필요 | Action 실행마다 자동 기록 |
| 결함 감지 | 이론적으로 완전 | 사전 정의 범위 내에서만 |
| 적합 환경 | 지식 공유, 학술 | 운영 시스템, 의사결정 실행 |

> **왜 필요한가?** 병원 EMR 시스템에서 OWA를 따른다면, 의사가 처방을 입력하는 방식이 수십 가지가 될 수 있습니다. Closed-action model은 "처방 입력"이라는 Action 하나로 통일하고, 약물 상호작용 검사, 용량 범위 확인, 의사 서명 요구를 모두 그 안에 내장합니다.

## 3. 표현력 vs. 운영 실용성 트레이드오프

이것은 Palantir 온톨로지를 이해하는 가장 중요한 프레임입니다.

### 3-1. 표현력 스펙트럼

```
표현력 (무엇을 표현할 수 있는가)
높음  OWL Full   -- 추론 불가 (논리적 결정 불가능)
     OWL DL     -- 완전한 논리 추론 가능
     OWL Lite
낮음  Palantir Ontology -- 논리 추론 없음, 하지만 실시간 운영 가능

운영 실용성 (실제 조직에서 쓸 수 있는가)
낮음  OWL Full / DL
높음  Palantir Ontology -- 비개발자도 구축, 실시간 동기화, Action 거버넌스
```

**OWL Full**은 이론적으로 가장 표현력이 높지만, 추론 자체가 결정 불가능(undecidable)합니다. 어떤 추론도 완전히 수행할 수 없다는 의미입니다. **OWL DL**은 표현력을 제한하는 대신 완전한 논리 추론을 보장합니다.

Palantir는 이 스펙트럼에서 의도적으로 낮은 표현력을 선택합니다. `owl:complementOf`, `owl:allValuesFrom`, 복잡한 카디널리티 제약 — 이런 것들이 없습니다. 대신 **비개발자가 Ontology Editor에서 직접 Object Type을 구축하고, 데이터 파이프라인이 실시간으로 동기화하며, Action이 변경을 제어합니다.**

### 3-2. 이것은 결함인가, 설계 선택인가

> **흔한 오해**: "Palantir 온톨로지는 OWL보다 표현력이 낮으니 덜 완성된 시스템이다"

> **실제로는**: Palantir는 논리적 완전성을 포기하는 대신 운영 현장 채택 가능성을 극대화했다. 이것은 결함이 아니라 의도적 설계 선택이다. Gene Ontology를 구축하려면 OWL이 필요하다. NHS 전체 병원 운영을 실시간으로 조정하려면 Palantir 방식이 더 현실적이다.

실제 대기업에서 OWL DL 기반 시스템을 운영하다 실패하는 패턴은 반복됩니다:

1. 온톨로지 설계가 복잡해질수록 온톨로지 엔지니어만 이해할 수 있다
2. 비개발자 도메인 전문가가 기여하지 못한다
3. 추론 성능이 데이터 규모에 비례해 저하된다
4. 실시간 운영 데이터와의 동기화가 구조적으로 어렵다

Palantir는 이 네 가지 실패 패턴을 모두 아키텍처 수준에서 해결했습니다.

> **왜 필요한가?** 논리 추론 능력이 없다면 온톨로지가 아닌 것 아닌가? 이 질문에 답할 수 있어야 합니다. 온톨로지의 핵심은 도메인 개념을 명시적으로 공유하고, 그것을 기반으로 추론하는 것입니다. Palantir는 형식 논리 추론을 LLM 기반 의미 추론으로 대체했습니다. 다른 방법으로 같은 목적을 추구하는 것입니다.

## 4. 추론 방식의 근본적 차이

### 4-1. Description Logic Reasoner

OWL의 추론기는 수학적으로 엄밀합니다. Tableau 알고리즘이나 Resolution-based 방법으로, 주어진 공리(Axiom)에서 **모든 논리적 귀결을 빠짐없이 도출** 합니다. 같은 입력에 항상 같은 결과를 냅니다.

```
공리:
  :ElectricVehicle rdfs:subClassOf :Vehicle
  :Vehicle rdfs:subClassOf :TransportAsset
  :M14 rdf:type :ElectricVehicle

추론 결과 (자동):
  :M14 rdf:type :Vehicle
  :M14 rdf:type :TransportAsset
  → 완전하고 결정적이며 반복 가능
```

이 추론은 일관성 검사(Consistency Checking)도 수행합니다. 모순이 있으면 "Unsatisfiable"을 반환합니다.

### 4-2. AIP의 LLM 기반 추론

AIP(AI Platform)는 LLM을 추론 엔진으로 사용합니다. 이것은 확률적이고 의미론적입니다.

```
사용자 질문:
  "지금 가장 위험한 설비 5개와 이유를 보여줘"

AIP 추론 과정:
  → 질문 의도 파악 (LLM)
  → 관련 Object Type 식별 (Machine, Sensor, MaintenanceLog)
  → 적절한 Function 선택 (machine_quality_risk_score)
  → 결과 해석 및 설명 생성 (LLM)
```

LLM 추론은 수학적으로 완전하지 않습니다. 하지만 **자연어, 문서, 비정형 데이터를 구조화된 온톨로지 쿼리와 결합** 할 수 있습니다. DL Reasoner가 할 수 없는 일입니다.

> **연결 포인트 → Phase 3**: Phase 3에서 배운 개방 세계 가정(OWA)과 폐쇄 세계 가정(CWA)의 차이가 여기서 실질적 의미를 가집니다. Palantir의 Closed-action model은 CWA의 운영 버전입니다.

## 5. SPARQL vs. OSDK / 자연어 질의

### 5-1. SPARQL의 강점과 한계

SPARQL(SPARQL Protocol and RDF Query Language)은 RDF 그래프에 대한 표준 질의 언어입니다. SQL처럼 정확하고 표현력이 강합니다.

```sparql
SELECT ?machine ?vibration
WHERE {
  ?machine rdf:type :Machine .
  ?machine :hasVibration ?vibration .
  FILTER(?vibration > 2.0)
  ?lot :processed_on ?machine .
  ?lot :hasDefectRate ?defectRate .
  FILTER(?defectRate > 0.05)
}
```

강력하지만, 이것을 공장 현장 관리자가 직접 쓸 수 있을까요? 현실적으로 어렵습니다.

### 5-2. OSDK와 자연어 질의

OSDK(Ontology SDK)는 Object Type에서 자동 생성된 타입 안전 API입니다. TypeScript/Python 개발자가 익숙한 방식으로 온톨로지 데이터에 접근합니다.

```typescript
// OSDK 예시
const riskyMachines = await client.objects.Machine
  .filter(machine => machine.vibration.gt(2.0))
  .filter(machine => machine.recentDefectRate.gt(0.05))
  .orderBy(machine => machine.qualityRiskScore, "desc")
  .take(5);
```

AIP(AI Platform)가 결합되면 자연어로 같은 질의가 가능합니다:

```
"진동값이 2.0을 초과하고 최근 불량률이 5%를 넘는 설비 중 위험도 상위 5개를 보여줘"
```

> **연결 포인트 → Phase 4**: Phase 4에서 배운 OWL 표준과 SPARQL이 학문적 온톨로지의 상호운용성 기반이라면, OSDK는 Palantir 생태계 안의 상호운용성 기반입니다. 표준 여부는 다르지만, 추구하는 목적은 같습니다.

> **왜 필요한가?** 질의 언어의 선택은 단순한 기술 결정이 아닙니다. "온톨로지를 누가 사용할 수 있는가"를 결정합니다. SPARQL은 데이터 과학자와 온톨로지 엔지니어의 도구입니다. OSDK는 소프트웨어 개발자의 도구입니다. AIP 자연어 인터페이스는 도메인 전문가와 현장 관리자의 도구입니다. 이 세 계층을 모두 커버하는 것이 Palantir의 접근법입니다.

## 6. 언제 OWL을, 언제 Palantir를

이 질문에 답할 수 있어야 진정으로 두 시스템을 이해한 것입니다.

**OWL/RDF가 더 적합한 경우:**

```
1. 논리적 일관성이 생사와 연결될 때
   예: 의약품 상호작용 검사, 항공기 시스템 인증
   → OWL DL + Reasoner로 모순 자동 탐지

2. 다른 조직의 온톨로지와 직접 연결해야 할 때
   예: 학술 데이터 공유, 정부 데이터 연계
   → RDF Linked Data, OWL/SPARQL 표준

3. 복잡한 서브클래스 추론이 필요할 때
   예: Gene Ontology, SNOMED CT
   → Description Logic Reasoner
```

**Palantir 방식이 더 적합한 경우:**

```
1. 실시간 운영 데이터와 연결이 필요할 때
   예: 공장 센서 데이터, 병원 EMR, 물류 추적

2. 비개발자 도메인 전문가가 직접 기여해야 할 때
   예: 임상 의사가 환자 분류 체계를 유지보수

3. 변경 거버넌스와 감사 추적이 필수일 때
   예: 금융 규제 준수, 의료 기록 변경

4. LLM 기반 자연어 인터페이스가 중요할 때
   예: 비기술 사용자가 복잡한 쿼리를 자연어로
```

## 흔한 오해

> **흔한 오해**: "Palantir가 OWA를 거부했으니 온톨로지라고 부를 수 없다"

> **실제로는**: 온톨로지의 본질은 특정 세계에 대한 공유된 형식 명세(shared formal specification)입니다. OWA/CWA는 온톨로지의 구성 요소 중 하나이지, 온톨로지의 정의 자체가 아닙니다. Palantir는 Object Type, Link Type, 계층 구조, Interface 다형성을 통해 온톨로지의 핵심 목적 — 도메인 개념의 공유된 이해와 상호운용 — 을 달성합니다. 다만 형식 논리 추론 대신 Action 거버넌스와 LLM을 사용합니다.

## 요약

- OWL `owl:Class`는 추상 정의, Palantir Object Type은 실 데이터소스에 바인딩된 살아있는 정의
- `rdfs:subClassOf` 계층 상속과 달리 Interface는 형태 기반 다형성으로 유연한 분류를 허용
- OWA는 지식 공유와 분산 기여에 강점, Palantir Closed-action model은 변경 거버넌스와 감사 추적에 강점
- Description Logic Reasoner는 수학적으로 완전하지만 운영 데이터 규모에서 성능 문제 발생
- AIP LLM 추론은 확률적이지만 자연어와 비정형 데이터를 구조화 쿼리와 결합 가능
- SPARQL은 표현력 높은 기술 언어, OSDK는 개발자 친화, AIP 자연어는 비개발자까지 포용
- 두 방식 중 하나가 절대적으로 우월한 것이 아니라, 다른 문제를 위한 다른 설계 선택
