# 디지털 트윈과 6단계 운영 루프

> "디지털 트윈이란 물리 세계의 복사본이 아니다. 물리 세계를 변경하는 데 사용할 수 있는 살아있는 모델이다."
> — Palantir Foundry 문서

**현장 엔지니어 김 과장의 하루**를 따라가며, Palantir 온톨로지가 조직 운영을 어떻게 바꾸는지 체감해 보자.

김 과장은 반도체 공장에서 설비 관리를 담당한다. 매일 아침 8시에 출근하면 여러 시스템에 하나씩 로그인하고, 엑셀로 데이터를 옮기고, 보고서를 만든다. 어딘가에 문제가 숨어 있어도 발견이 늦고, 발견해도 조치가 느리다. 온톨로지가 도입되면 김 과장의 하루가 어떻게 달라지는지, 6단계를 하나씩 따라가 보자.

Palantir 온톨로지를 한 문장으로 정의하면 이렇다.

> 조직의 흩어진 데이터 자산을 현실 세계의 객체(Object)와 관계(Link)로 재구성하고, 그 위에 로직(Function), 행동(Action), 권한(Security)을 얹어서 사람과 소프트웨어와 AI가 같은 운영 세계를 공유하게 만드는 시스템

이 정의에서 핵심 단어는 "**운영 세계를 공유**"다. 온톨로지가 단순한 데이터 모델이나 지식 그래프가 아니라, 조직 전체가 동일한 현실을 보고 그 위에서 결정을 내리고 행동을 실행하는 **공유 운영 기반**이라는 것이다.

## 학습 목표

1. **디지털 트윈** 개념을 Palantir 온톨로지 맥락에서 정의하고, 기존 시뮬레이션 기반 디지털 트윈과의 차이를 설명한다
2. **6단계 운영 루프**의 각 단계를 순서대로 설명하고, 각 단계에서 온톨로지가 하는 역할을 이해한다
3. **닫힌 루프(Closed-loop)** 개념의 의의를 파악하고, 열린 루프 시스템과의 구조적 차이를 비교한다
4. 제조, 의료, 국방 등 다양한 도메인에서 6단계 루프가 어떻게 적용되는지 예시를 들어 설명한다

## 1. 디지털 트윈으로서의 온톨로지

디지털 트윈(Digital Twin)이라는 말을 들으면 보통 "3D 시뮬레이션"을 떠올린다. 자동차 엔진의 가상 모형을 만들어서 진동을 시뮬레이션하는 그런 이미지다. Palantir가 말하는 디지털 트윈은 범위가 다르다.

비유하자면 이렇다. 전통적 디지털 트윈이 **설비 하나의 정밀 모형**이라면, Palantir 온톨로지는 **공장 전체의 운영 지도**다. 지도에는 설비뿐 아니라 작업자, 자재, 공정, 불량 이력까지 모두 올라가 있고, 지도 위에서 바로 명령을 내릴 수 있다.

| 구분 | 전통적 디지털 트윈 | Palantir 온톨로지 트윈 |
|------|-------------------|----------------------|
| 범위 | 특정 설비나 공정 | 조직 전체 운영 세계 |
| 목적 | 시뮬레이션과 예측 | 실시간 운영과 의사결정 |
| 쓰기 | 없음 (읽기 전용) | Action을 통한 실제 변경 |
| 사용자 | 엔지니어 | 조직 전체 + AI 에이전트 |

실세계 조직과 온톨로지 표현의 매핑을 보자.

```
실세계 조직                         온톨로지 표현
─────────────────────────────────────────────────
공장, 설비, 제품          →    Object Type
이 설비가 저 공정에 사용됨  →    Link Type
가동 중단 시 에스컬레이션   →    Action Type
센서 측정값, 직원 이름     →    Property
최근 3일 평균 불량률 계산  →    Function
```

> **왜 필요한가?** 조직의 모든 구성원(영업사원, 엔지니어, 관리자, AI 에이전트)이 동일한 "현실의 표현"을 바라보는 공유 모델이 있어야 일관된 의사결정이 가능하다. 김 과장이 보는 설비 상태와 품질팀이 보는 설비 상태가 다르면 — 하나는 MES에서, 하나는 ERP에서 가져온 숫자라서 — 회의 시간의 절반은 "어느 숫자가 맞는지" 논쟁하는 데 쓰인다.

이 트윈이 **실시간으로 동기화**된 상태를 유지할 때, 인간과 AI 에이전트가 공유하는 "현실의 실행 가능한 표현"이 된다. 단순히 현실을 보여주는 것이 아니라, 그 현실을 변경하는 행동(Action)까지 포함하는 것이 핵심이다.

> **연결 포인트 → Phase 5**: Phase 5에서 배운 온톨로지 설계 방법론 — 특히 Competency Question(역량 질문) 기법 — 이 바로 "어떤 결정을 지원해야 하는가"를 정의하는 도구다. Palantir의 Object Type 설계는 이 방법론을 엔터프라이즈 규모로 확장한 것이다.

### 단계 1: 원천 데이터 수집 — "아침 8시, 김 과장의 로그인 지옥"

**Before 온톨로지**: 김 과장의 아침은 이렇다. MES에 로그인해서 어젯밤 생산 이력을 확인한다. ERP에 로그인해서 오늘 작업 지시를 본다. 설비 모니터링 시스템에 들어가서 알람 이력을 뒤진다. 품질 시스템에서 불량 데이터를 내려받는다. 네 개 시스템, 네 번의 로그인, 네 개의 엑셀 파일. 이걸 하나로 합치는 데만 한 시간이 걸린다.

**After 온톨로지**: 이 모든 원천 데이터가 온톨로지의 파이프라인(Pipeline)을 통해 자동으로 수집되고 동기화된다. 김 과장은 더 이상 시스템별로 로그인할 필요가 없다.

조직에는 이미 데이터가 여러 시스템에 흩어져 있다. 이 단계는 아직 "여러 데이터가 있음" 상태다. 즉 **현실이 아니라 시스템별 파편**이다.

| 도메인 | 원천 데이터 예시 |
|--------|----------------|
| 제조 | ERP(주문/BOM/원가), MES(생산 이력), 설비 로그(알람/센서), 품질 시스템, 공급망 |
| 의료 | 병원 운영 시스템, 대기자 명단, 인력 배치, 재정/예산, 기관별 행정 데이터 |
| 군사 | ISR 정찰 데이터, 위치 및 트랙 데이터, 임무 계획, 보급/정비 자산 |

> **왜 필요한가?** 데이터 수집 자체는 새로운 기술이 아니다. 핵심은 이 파편화된 데이터를 "그대로 이관"하는 것이 아니라, 다음 단계에서 의미 있는 객체로 재정의한다는 점이다. 김 과장이 엑셀로 수작업 통합하던 것을 시스템이 자동으로 해주되, 단순 취합이 아니라 **의미 구조를 입혀서** 통합한다.

### 단계 2: 현실 객체(Object Type)로 재정의 — "클릭 한 번에 모든 정보가 모인다"

**Before 온톨로지**: 김 과장이 3호기 설비 상태를 파악하려면? MES에서 가동 이력, ERP에서 정비 이력, 설비 시스템에서 센서값, 품질 시스템에서 불량률. 네 곳의 데이터를 머릿속에서 조합해야 했다. 마치 친구의 연락처, 생일, 취미, 최근 만난 날짜가 전부 다른 앱에 흩어져 있는 것과 같다.

**After 온톨로지**: 김 과장이 "Machine-003"을 클릭하면 하나의 객체 화면에 모든 것이 모여 있다. 현재 센서값, 최근 생산 이력, 불량 현황, 정비 이력, 장착된 공구 정보까지. 마치 스마트폰 연락처를 열면 전화번호, 이메일, 최근 통화, 메시지가 한 화면에 보이는 것과 같다.

여기서 온톨로지가 등장한다. Palantir는 데이터를 먼저 "테이블"이 아니라 **객체 타입(Object Type)**으로 재해석한다. 각 객체는 실제 데이터 소스에 연결(Backing Datasource)된다.

```
원래 상태                        Ontology 적용 후
──────────────────────────────────────────────
machine_log.csv        →    Machine 객체
erp_orders             →    Order 객체
mes_events             →    Production Run 객체
qa_results             →    Quality Incident 객체
```

이 변환이 단순한 이름 변경이 아닌 이유: Object Type에는 해당 개체를 정의하는 Property(속성, 즉 그 객체가 가지는 정보 항목들)가 있고, 실시간 데이터 소스와 동기화된다. Machine 객체를 조회하면 항상 최신 센서 값과 상태를 반환한다.

### 단계 3: 객체 간 관계(Link Type) 정의 — "이 설비에서 불량이 났던 Lot은?"

**Before 온톨로지**: 김 과장에게 급한 전화가 온다. "3호기에서 처리한 Lot 중에 불량 나온 거 있어?" 김 과장은 MES에서 3호기 가동 이력을 뽑고, 그 Lot 번호를 품질 시스템에서 하나씩 검색한다. SQL을 아는 동료에게 부탁하면 여러 테이블을 JOIN해서 쿼리를 짜야 한다. 30분 후에야 답할 수 있다.

**After 온톨로지**: 김 과장이 Machine-003 객체 화면에서 "processed_on" 링크를 따라가면 이 설비에서 처리된 모든 Lot이 보인다. 거기서 "observed_in" 링크를 따라가면 불량 이력이 바로 나온다. 마치 SNS에서 친구 프로필 클릭 → 친구의 친구 목록 클릭하듯, 관계를 따라 자연스럽게 탐색한다. 10초면 충분하다.

객체만 있으면 아직 "목록"이다. 운영은 관계에서 나온다.

```
SQL join  = 기술적 연결 (테이블 A의 외래키가 테이블 B를 가리킴)
Link Type = 업무 의미를 가진 연결 (이 설비가 이 공정에 사용됨)
```

제조업 예시:

- `Lot → processed_on → Machine` (이 롯트가 이 설비에서 가공됨)
- `Tool → mounted_on → Machine` (이 공구가 이 설비에 장착됨)
- `Defect → observed_in → Lot` (이 불량이 이 롯트에서 발견됨)

이 순간, SQL 조인이 **업무 관계 탐색**으로 바뀐다. "이 설비에서 처리된 롯트 중 불량이 발생한 것"을 SQL로 작성하면 여러 테이블의 조인이 필요하지만, Link Type을 통해서는 그래프 탐색으로 자연스럽게 연결된다.

> **연결 포인트 → Phase 7**: Phase 7(실전 응용)에서 배운 그래프 탐색 패턴이 바로 이 Link Type을 통한 탐색이다. SPARQL의 패턴 매칭이 Palantir에서는 OSDK의 객체 탐색으로 구현된다.

### 단계 4: 비즈니스 로직(Function) 작성 — "위험 설비가 알아서 빨간불을 켠다"

**Before 온톨로지**: 김 과장은 경험에 의존한다. "3호기 진동이 좀 높은 것 같은데..." 센서 데이터를 눈으로 보고, 과거 경험을 떠올리고, 감으로 판단한다. 어떤 날은 위험을 놓치고, 어떤 날은 괜한 걱정으로 불필요한 점검을 한다. 김 과장이 휴가를 가면 아무도 이 판단을 못 한다.

**After 온톨로지**: 화면을 열면 각 설비 옆에 건강 점수(Health Score)가 표시되어 있다. 진동, 온도, 불량률, 공구 수명, 작업 부하를 종합해서 자동 계산된 점수다. 빨간색(위험), 노란색(주의), 초록색(양호). 마치 스마트워치가 심박수, 산소포화도, 활동량을 종합해서 "오늘 건강 점수 85점"이라고 알려주는 것과 같다.

여기서부터 Palantir가 단순 그래프 플랫폼과 달라진다. Function(함수)은 **도메인 판단 로직**, 즉 도메인 전문가의 판단 기준을 코드로 표현한 것이다.

```
calculate_risk(machine)
→ 진동, 온도, 최근 불량률, 공구 수명, 작업 부하를 종합해서
→ 해당 machine이 다음 24시간 내 문제를 일으킬 가능성 반환
```

Function은 분석 쿼리가 아니다. "불량률 3% 초과 AND 진동값 임계치의 80% 이상 AND 최근 정비일로부터 90일 초과"라는 도메인 지식이 Function에 담긴다. 김 과장의 30년 경험이 코드가 되어, 김 과장이 휴가 중이어도 시스템이 같은 판단을 내린다.

> **왜 필요한가?** 사람의 머릿속에만 있는 판단 기준은 공유할 수 없고, 일관되지 않고, 확장할 수 없다. Function은 전문가의 판단을 조직 전체가 공유 가능한 코드로 만드는 장치다. 하나의 Function이 수천 대의 설비를 동시에 판단할 수 있다.

### 단계 5: 행동(Action)으로 실제 운영 변경 — "클릭 한 번으로 정비 요청, 감사 기록은 자동"

**Before 온톨로지**: 김 과장이 3호기에 문제가 있다고 판단하면? 정비 시스템에 로그인한다. 정비 요청서를 작성한다. 설비 번호, 증상, 긴급도를 수동으로 입력한다. 상사에게 메일로 승인을 요청한다. 승인 후 정비팀에 전달한다. 이 과정에 2시간이 걸리고, 중간에 정보가 누락되거나 잘못 전달되기 일쑤다.

**After 온톨로지**: Machine-003 화면에서 "정비 요청" 버튼을 클릭한다. 설비 정보, 현재 센서값, 건강 점수, 관련 불량 이력이 자동으로 채워진 정비 요청이 생성된다. 승인 워크플로가 자동으로 시작되고, 누가 언제 어떤 근거로 요청했는지 감사 로그(Audit Log)가 남는다. 3분이면 끝난다.

온톨로지는 읽기 전용 모델이 아니다. **쓰기(write-back) 가능한 운영 모델**이다.

```
Object   = 무엇을 다룰 것인가 (Machine, Lot, Employee)
Function = 어떻게 판단할 것인가 (건강 점수, 리스크 계산)
Action   = 그래서 무엇을 실행할 것인가 (정비 요청, Lot 격리)
```

예시 행동들:
- 작업 지시 생성
- 레시피 변경 승인
- Lot 격리
- 정비 요청 생성
- 경보 발행

> **왜 필요한가?** Action 없이는 온톨로지가 "좋은 대시보드"에 불과하다. 대시보드는 "여기 문제가 있어요"까지만 보여주고, 해결은 사람이 다른 시스템에서 해야 한다. Action이 있어야 온톨로지가 **보여주고 바로 실행까지 하는** 운영 주체가 된다. 이것이 Palantir를 BI 도구와 구분하는 가장 핵심적인 차이다.

### 단계 6: 보안(Security)과 감사(Audit) 적용 — "김 과장은 자기 공장만, 본사는 전체를"

**Before 온톨로지**: 보안이 시스템 단위로 되어 있다. MES에 접근 권한이 있으면 모든 공장의 모든 설비 데이터를 볼 수 있거나, 아예 접근 자체가 안 되거나. "수원 공장 설비 데이터는 보되, 평택 공장은 못 보게" 하려면 별도 시스템을 구축해야 했다.

**After 온톨로지**: 같은 온톨로지 화면이지만, 김 과장이 로그인하면 수원 공장 설비만 보인다. 본사 관리자가 로그인하면 전 공장 설비가 보인다. 공장장은 설비 데이터 + 인력 배치까지, 품질 감사관은 불량 데이터만 볼 수 있다. 마치 같은 건물인데 층마다 다른 카드키가 필요한 것과 같다.

현업에서 가장 중요한 것은 "누가 무엇을 볼 수 있고, 누가 무엇을 바꿀 수 있는가"다. 같은 `Patient`, `Asset`, `Mission` 객체를 보더라도:

- 어떤 사용자는 전체를 본다
- 어떤 사용자는 일부 속성만 본다
- 어떤 사용자는 집계값만 본다
- 어떤 사용자는 Action 실행 권한이 있다

> **왜 필요한가?** 온톨로지가 실제 조직 운영체계가 되려면 추론 능력보다 거버넌스가 더 중요할 때가 많다. 병원에서 환자 데이터, 군사 시스템에서 기밀 정보, 기업에서 급여 정보가 보안 없이 모든 사용자에게 노출된다면 온톨로지 도입 자체가 불가능해진다.

## 3. 닫힌 루프의 의미 — 김 과장의 하루가 끝나지 않는 이유

6단계 운영 루프의 완성은 **닫힌 루프(Closed-loop)**다. Action의 실행 결과가 다시 객체 상태에 반영되고, 그 변경된 상태가 다음 판단의 입력이 된다.

김 과장이 3호기 정비 요청을 실행하면 이런 일이 벌어진다:

1. 정비팀이 3호기를 수리한다
2. 수리 완료 기록이 정비 시스템에 입력된다
3. 그 데이터가 온톨로지의 Machine-003 객체에 자동 반영된다 (단계 1로 돌아감)
4. `lastMaintenanceDate`가 갱신되고, 건강 점수가 재계산된다 (단계 4)
5. 내일 아침 김 과장이 화면을 열면, 3호기는 초록색이다

이것이 "루프가 닫힌다"는 뜻이다. 행동의 결과가 다시 시작점으로 돌아와서 다음 판단을 더 정확하게 만든다.

| 시스템 유형 | 동작 방식 |
|------------|----------|
| 일반 챗봇 | 질문에 답하고 끝난다 |
| BI 대시보드 | 현황을 보여주고 끝난다 |
| Palantir 온톨로지 | 답한 뒤 세계를 바꾸고, 바뀐 세계를 다시 관찰한다 |

> **왜 필요한가?** 열린 루프 시스템에서는 AI가 추천을 해도 그 추천이 실행됐는지, 결과가 어땠는지 알 수 없다. 닫힌 루프에서는 모든 결정과 실행 결과가 온톨로지에 반영되어 다음 판단의 근거가 된다. 이것이 조직 지식이 누적되는 메커니즘이다. 김 과장이 한 번 정비 요청을 실행할 때마다, 시스템은 "이런 조건에서 정비하면 효과가 있었다"는 데이터를 축적한다.

## 4. 도메인별 6단계 루프 적용 예시

### 제조업 — 설비 이상 대응

```
수집: IoT 센서 → 진동, 온도, 전류
객체: Machine, Tool, Lot, ProductionLine
관계: Lot → processed_on → Machine
함수: machine_health_score(machine) → 0~100 점수
행동: create_maintenance_request(machine, urgency)
보안: 현장 엔지니어만 정비 요청 생성 가능
루프: 정비 완료 후 Machine.lastMaintenanceDate 갱신
      다음 점수 계산에 반영
```

### 의료 — 수술 일정 최적화

```
수집: 수술 예약 시스템, 인력 스케줄, 병상 현황
객체: Patient, TheatreSession, Clinician, Bed
관계: Patient → scheduled_in → TheatreSession
함수: waitlist_priority(patient) → 우선순위 점수
행동: reschedule_procedure(patient, new_slot)
보안: 주치의만 일정 변경 가능, 관리자는 전체 조회
루프: 재배치 결과가 대기자 현황에 즉시 반영
```

> **연결 포인트 → Phase 10**: Phase 10에서 다룰 AIP(AI Platform)에서는 이 6단계 루프 위에 LLM 기반 AI 에이전트가 올라간다. Function이 판단을 제공하고, AI 에이전트가 Action을 제안하며, 사람이 승인하는 구조다. 온톨로지 루프를 이해해야 AI 에이전트의 역할을 정확히 파악할 수 있다.

## 흔한 오해

> **흔한 오해**: "디지털 트윈은 물리 설비의 시뮬레이션 모델이다. Palantir가 말하는 디지털 트윈도 같은 것이다."

> **실제로는**: 전통적 디지털 트윈은 하나의 설비나 공정을 시뮬레이션하는 좁은 개념이다. Palantir의 디지털 트윈은 조직 전체의 운영 세계를 실시간으로 표현하며, 시뮬레이션이 아니라 실제 데이터에 연결된 살아있는 모델이다. 가장 큰 차이는 Action을 통해 실제 세계를 변경한다는 점이다. 비유하자면, 전통적 디지털 트윈이 비행 시뮬레이터라면, Palantir 온톨로지는 실제 관제탑이다.

> **흔한 오해**: "6단계 루프는 단방향 파이프라인이다. 데이터를 수집해서 처리하고 끝난다."

> **실제로는**: 6단계는 순환 루프다. 마지막 단계(Action 실행)의 결과가 첫 번째 단계(원천 데이터)로 돌아간다. 정비 요청이 실행되어 설비가 수리되면, 그 설비의 상태가 객체에 반영되고, 다음 번 건강 점수 계산에 영향을 준다. 이 순환이 없으면 시스템은 매번 제로에서 시작하는 것과 같다.

## 요약

- Palantir 온톨로지는 조직의 **디지털 트윈** — 실시간 동기화되고 Action으로 변경 가능한 운영 모델이다
- 6단계 운영 루프: 원천 수집 → 객체 정의 → 관계 정의 → 로직 작성 → 행동 실행 → 보안 적용
- 각 단계가 하는 일: 파편(데이터) → 개체(Object) → 관계(Link) → 판단(Function) → 변경(Action) → 통제(Security)
- **닫힌 루프**가 핵심: Action 결과가 다시 객체 상태에 반영되어 의사결정이 누적 개선된다
- 김 과장의 하루: 4개 시스템 로그인 → 1개 화면에서 모든 운영. 이것이 온톨로지가 만드는 변화다
- 다음 회차에서는 각 구성 요소(Object Type, Property, Link Type, Action Type, Function, Interface)를 상세히 분석한다
