# 2회차: 상호운용성 문제

## 학습 목표

이 세션이 끝나면 다음을 할 수 있습니다:

- 상호운용성(Interoperability)의 개념과 왜 중요한지 설명할 수 있다
- 구문론적(Syntactic) 상호운용성과 의미론적(Semantic) 상호운용성의 차이를 설명할 수 있다
- XML과 JSON 같은 데이터 포맷이 왜 의미론적 상호운용성을 보장하지 못하는지 설명할 수 있다
- 온톨로지가 어떻게 의미론적 상호운용성을 가능하게 하는지 개괄적으로 이해할 수 있다

## 이번 세션 전체 그림

두 시스템이 정보를 교환할 때 무슨 일이 일어나는지 살펴봅시다. 온톨로지 없이는 언어는 통하지만 의미는 전달되지 않는 상황이 발생합니다.

> **왜 필요한가? - 상호운용성이 없으면 디지털화는 의미가 없다**
> 많은 기관들이 막대한 비용을 들여 업무를 디지털화했습니다. 그런데 역설적이게도 디지털화된 이후에도 시스템끼리 소통하지 못하는 일이 빈번합니다. 상호운용성이 없으면 디지털 전환은 그저 종이 서류를 디지털 파일로 바꾼 것에 불과합니다. 온톨로지는 이 간격을 메우는 핵심 도구입니다.

## 상호운용성이란 무엇인가?

<strong>상호운용성(Interoperability)</strong>은 서로 다른 시스템, 조직, 또는 도구들이 데이터를 교환하고 공유하며, 그 과정에서 교환된 정보를 올바르게 사용하는 능력입니다.

미국 의료정보학회(HIMSS)는 상호운용성을 세 가지 수준으로 정의합니다:

1. **기술적 상호운용성(Technical Interoperability)**: 두 시스템이 물리적으로 연결되어 데이터를 주고받을 수 있는 능력
2. **구문론적 상호운용성(Syntactic Interoperability)**: 교환되는 데이터의 형식(Format)에 대한 합의
3. **의미론적 상호운용성(Semantic Interoperability)**: 교환되는 데이터의 의미(Meaning)에 대한 합의

### 레벨별 비유

인터넷 전화로 한국어를 모르는 외국인과 대화하는 상황을 상상해보세요:

- **기술적 상호운용성**: 전화가 연결되어 소리가 전달된다 (물리적 연결)
- **구문론적 상호운용성**: 음성이 명확하게 들린다, 잡음이 없다 (데이터 포맷 일치)
- **의미론적 상호운용성**: 서로가 하는 말의 의미를 이해한다 (공통 언어 또는 통역사)

현재 대부분의 IT 시스템들은 기술적, 구문론적 상호운용성은 달성했지만, 의미론적 상호운용성에서 막힙니다.

## 실제 실패 사례: 1999년 화성 기후 궤도선 사고

### 사건 개요

1999년 9월 23일, NASA의 화성 기후 궤도선(Mars Climate Orbiter)이 화성 대기권에 진입하면서 영원히 사라졌습니다. 프로젝트 예산은 약 3억 2천 7백만 달러(한화 약 4천억 원)였습니다.

사고의 원인은 충격적으로 단순했습니다: **단위계(Unit System)의 불일치**

- Lockheed Martin이 개발한 탐사선 소프트웨어는 추력 데이터를 <strong>영국식 단위(pound-force seconds)</strong>로 전송했습니다.
- NASA 제트추진연구소(JPL)의 항법 소프트웨어는 그 데이터를 <strong>미터법 단위(Newton-seconds)</strong>로 해석했습니다.

두 시스템은 완벽하게 데이터를 전송하고 수신했습니다. 기술적, 구문론적 상호운용성은 완벽했습니다. 그러나 "이 숫자가 어떤 단위를 의미하는가"에 대한 공통 합의, 즉 의미론적 상호운용성이 없었습니다.

> **왜 필요한가? - 단위 불일치 하나가 4천억을 날렸다**
> 이 사례는 의미론적 상호운용성의 부재가 단순한 불편함이 아니라 엄청난 손실로 이어질 수 있음을 보여줍니다. 데이터는 정확히 전송되었지만, 그 데이터가 무엇을 의미하는지에 대한 합의가 없었기에 3억 달러짜리 탐사선이 사라졌습니다. 온톨로지는 "pound-force seconds"와 "Newton-seconds"가 서로 다른 측정 단위 체계임을 명시적으로 정의하고, 이 둘이 어떻게 변환되는지 기술할 수 있습니다.

### 이 사건이 가르쳐 주는 것

화성 궤도선 사고는 단순한 엔지니어링 실수가 아닙니다. 이것은 두 팀이 공유한 "암묵적 가정"의 실패입니다. 각 팀은 자신의 단위계가 표준이라고 당연히 여겼고, 이를 명시적으로 문서화하거나 확인하지 않았습니다.

온톨로지적 관점에서 이 문제의 해결책은 명확합니다: "추력(Thrust)" 개념을 정의할 때, 반드시 측정 단위(Unit of Measurement)를 개념의 필수 속성으로 명시해야 합니다. "추력"이 영국식 단위로 측정됨을 명시한 온톨로지를 사용했다면, 시스템 간 데이터 교환 시 자동으로 경고를 발생시키거나 단위 변환을 수행할 수 있었을 것입니다.

## 의료 정보 시스템의 상호운용성 문제

### 전자 의무 기록(EMR) 시스템의 현실

한국의 병원들이 사용하는 전자 의무 기록(EMR, Electronic Medical Record) 시스템은 수십 개의 서로 다른 제품이 존재합니다. 각 제품은 자체적인 데이터 구조와 코드 체계를 사용합니다.

환자가 A 병원에서 B 병원으로 이송될 때, 이상적으로는 모든 의료 정보가 자동으로 전달되어야 합니다. 그러나 현실에서는:

- 의사들이 수동으로 기록을 출력하고 팩스로 전송합니다
- 환자 또는 보호자가 직접 서류를 들고 다닙니다
- 중요한 정보가 전달 과정에서 누락됩니다

이것은 단지 기술의 문제가 아닙니다. 각 시스템이 같은 개념을 다르게 표현하기 때문에 자동화된 정보 교환이 어렵습니다.

> **연결 포인트:** HL7 FHIR(Fast Healthcare Interoperability Resources)은 의료 데이터 교환을 위한 국제 표준입니다. 그러나 FHIR조차도 데이터 교환 형식만 정의합니다. 의미론적 상호운용성을 위해서는 SNOMED CT, LOINC, RxNorm 같은 의료 온톨로지를 함께 사용해야 합니다. 이 온톨로지들은 6단계에서 자세히 다룹니다.

## 구문론적 vs 의미론적 상호운용성

### XML과 JSON은 왜 충분하지 않은가?

XML(eXtensible Markup Language)과 JSON(JavaScript Object Notation)은 데이터 교환의 사실상 표준(De facto standard)이 되었습니다. 이 포맷들은 구문론적 상호운용성을 완벽하게 제공합니다.

그러나 다음 예시를 보면 한계가 명확합니다:

**시스템 A의 환자 기록 (JSON):**
```json
{
  "patient": "Kim Cheolsu",
  "primary_diagnosis": "HTN",
  "medication": "Amlodipine 5mg"
}
```

**시스템 B의 환자 기록 (JSON):**
```json
{
  "patient_name": "김철수",
  "main_condition": "Hypertension",
  "current_drug": "암로디핀 5mg qd"
}
```

두 JSON 파일은 동일한 환자의 동일한 진단과 처방을 기록하고 있습니다. 그러나 컴퓨터는 이것들이 같은 정보임을 자동으로 인식할 수 없습니다:

- `patient` vs `patient_name`: 같은 필드, 다른 이름
- `HTN` vs `Hypertension`: 같은 개념, 다른 표현
- `Amlodipine 5mg` vs `암로디핀 5mg qd`: 같은 약물과 용량, 다른 언어와 표기

### 온톨로지가 제공하는 해결책

온톨로지를 사용하면 각 데이터 요소에 URI(Uniform Resource Identifier)로 개념을 연결할 수 있습니다:

```json
{
  "@context": "http://example.org/medical-ontology",
  "patient": {
    "@type": "http://schema.org/Patient",
    "name": "김철수"
  },
  "diagnosis": {
    "@type": "http://snomed.info/id/38341003",
    "label": "HTN"
  }
}
```

`http://snomed.info/id/38341003`은 SNOMED CT에서 고혈압(Hypertension)을 가리키는 고유 식별자입니다. 이 URI를 사용하면, 어떤 시스템이 "HTN"을 쓰든 "Hypertension"을 쓰든 "고혈압"을 쓰든, 모두 같은 개념임을 자동으로 인식할 수 있습니다.

## 흔한 오해

### 오해 1: "API를 만들면 상호운용성이 해결된다"

REST API는 시스템 간 데이터 교환을 쉽게 만들지만, 의미론적 상호운용성을 자동으로 해결하지는 않습니다. API는 데이터를 전달하는 통로일 뿐, 데이터의 의미를 정의하지 않습니다.

예를 들어, 두 개의 병원이 각자 REST API를 개발했다고 해도, API가 반환하는 "진단 코드"의 체계가 서로 다르면 의미 있는 정보 교환은 불가능합니다.

### 오해 2: "구글 번역기처럼 자동 변환이 가능하다"

언어 번역과 의미론적 상호운용성은 다른 문제입니다. 언어 번역은 자연어에서 자연어로의 변환이지만, 의미론적 상호운용성은 서로 다른 개념 체계(Conceptual System) 사이의 매핑을 요구합니다.

더욱이 의료, 법률, 과학 데이터에서는 번역의 부정확성이 치명적인 결과를 낳을 수 있습니다. 이런 분야에서는 인간이 검토하고 승인한 명시적 온톨로지 매핑이 필수입니다.

### 오해 3: "표준 코드 시스템(ICD-10 등)을 쓰면 된다"

ICD-10, SNOMED CT, LOINC 같은 표준 코드 체계를 사용하는 것은 좋은 출발점입니다. 그러나 이것들은 코드의 목록을 제공할 뿐, 코드들 사이의 의미론적 관계(hierarchical relationships, part-of relationships, causal relationships 등)를 완전히 표현하지는 못합니다.

온톨로지는 단순한 코드 목록을 넘어, 개념들 사이의 풍부한 의미론적 관계를 형식적으로 표현합니다. 예를 들어, "당뇨병"이 "인슐린 분비 부족"을 원인으로 가질 수 있고, "고혈당"을 증상으로 가지며, "신장 질환"을 합병증으로 유발할 수 있다는 복잡한 관계를 기술합니다.

> **왜 필요한가? - 코드 시스템만으로는 추론이 불가능하다**
> 표준 코드 시스템은 개념의 "이름표"를 제공합니다. 온톨로지는 이름표뿐만 아니라 그 이름표가 가리키는 개념의 "본질(Essence)"과 "관계(Relations)"를 정의합니다. 이 차이가 컴퓨터가 단순 조회를 넘어 추론(Reasoning)을 할 수 있게 만드는 핵심입니다.

## 온톨로지 기반 의미론적 상호운용성

온톨로지를 사용한 시스템 간 상호운용성은 다음과 같이 작동합니다:

1. **공통 온톨로지 참조**: 두 시스템이 같은 온톨로지(예: SNOMED CT)를 참조합니다.
2. **개념 매핑**: 각 시스템의 로컬 표현(HTN, 고혈압, Hypertension)이 공통 URI로 매핑됩니다.
3. **자동 해석**: 데이터를 받는 시스템은 URI를 통해 개념을 정확히 식별하고, 자신의 로컬 표현으로 변환합니다.

> **연결 포인트:** 온톨로지를 통한 의미론적 상호운용성은 단순히 의료 분야에만 국한되지 않습니다. 전자 상거래에서는 제품 카탈로그 통합에, 법률 분야에서는 법령 데이터베이스 연계에, 과학 연구에서는 실험 데이터 공유에 활용됩니다. 7단계에서 구글 지식 그래프, DBpedia 등 실제 시스템에서 온톨로지가 어떻게 활용되는지 자세히 살펴봅니다.

## 요약

이번 세션에서 우리는 다음을 배웠습니다:

1. **상호운용성의 세 수준**: 기술적 - 구문론적 - 의미론적 상호운용성이 있으며, 현재 대부분의 시스템들은 의미론적 수준에서 실패합니다.

2. **화성 궤도선 사고**: 4천억 원짜리 탐사선을 잃은 원인은 단위계(Unit System)에 대한 의미론적 합의의 부재였습니다.

3. **XML/JSON의 한계**: 구조적 포맷은 구문론적 상호운용성을 제공하지만, 의미론적 상호운용성은 보장하지 않습니다.

4. **온톨로지의 역할**: 개념에 고유 URI를 부여하고, 로컬 표현을 공통 URI로 매핑함으로써 의미론적 상호운용성을 실현합니다.

다음 회차에서는 "온톨로지란 정확히 무엇인가?"에 대한 학문적 정의를 살펴봅니다. Tom Gruber의 1993년 정의를 분석하며, 온톨로지가 단순한 데이터베이스나 분류 체계와 어떻게 다른지 이해합니다.
