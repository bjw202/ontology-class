## Phase 1 — 왜 온톨로지가 필요한가?

> **학습 목표:** "이게 왜 존재하는지"를 이해한다. 동기 없이 개념부터 외우면 오래 못 간다.

### 1-1. 데이터 · 정보 · 지식의 차이

- 숫자 `38.5`는 데이터다. "체온이 38.5도"는 정보다. "38.5도면 발열이고 진료가 필요하다"는 지식이다.
- 컴퓨터가 다루기 쉬운 것은 데이터뿐이다. 지식을 기계가 다루게 하려면 무언가가 더 필요하다.
- **해설:** 온톨로지는 이 "무언가" — 즉 지식을 기계가 처리할 수 있는 형태로 명시화하는 수단이다.

### 1-2. 시스템 간 의사소통 실패 사례

- 병원 A의 EMR에서 "Patient"는 입원 환자만 의미하고, 병원 B에서는 외래 포함이다. 데이터를 합치면 오류가 난다.
- 쇼핑몰 A의 "상품 카테고리"와 쇼핑몰 B의 "상품 카테고리"는 계층 구조가 다르다. 검색 통합이 불가능하다.
- "사과"라는 단어가 과일인지, Apple Inc.인지, 사과(謝過) 행위인지 — 문맥 없이 기계는 구분하지 못한다.
- **해설:** 이것이 **상호운용성(Interoperability)** 문제다. 온톨로지는 이 문제를 해결하기 위해 등장했다.

### 1-3. "공유된 개념화의 명시적 명세" 해체하기

- Gruber(1993)의 정의: *"An ontology is an explicit specification of a conceptualization."*
- **명시적(Explicit):** 암묵적 가정을 없애고 문서화한다
- **명세(Specification):** 형식 언어로 기계가 읽을 수 있게 쓴다
- **개념화(Conceptualization):** 세계의 일부를 추상화한 모델
- **공유된(Shared):** 특정 개인이 아니라 커뮤니티가 합의한 것
- **해설:** 이 네 단어를 이해하면 온톨로지의 본질이 보인다. "공유"가 없으면 그냥 개인 메모고, "명시적"이 없으면 자연어 문서다.

### 1-4. 온톨로지 없이 해결하려 했던 방법들과 그 한계

- 데이터베이스 스키마 통일 → 도메인이 바뀌면 매번 재설계 필요
- 자연어 문서 → 기계가 처리 불가
- 분류 체계(Taxonomy) → 계층만 있고 관계 표현 불가
- **해설:** 각 방법의 한계가 온톨로지가 추가로 제공하는 것을 역으로 설명해준다.

### 🔬 실습 포인트

- 자신이 아는 도메인(예: 스마트폰 부품, 제조 공정)에서 "같은 단어가 다르게 쓰이는 사례" 3개를 찾아보기
- 그 사례에서 어떤 정보가 추가되면 기계가 구분할 수 있을지 자연어로 적어보기

### ✅ 핵심 질문 (Phase 1 통과 기준)

1. 데이터베이스가 이미 있는데 온톨로지가 왜 추가로 필요한가?
2. "공유된 개념화의 명시적 명세"에서 '공유'가 빠지면 어떤 문제가 생기는가?
3. 상호운용성 문제를 온톨로지 없이 해결하려면 어떤 비용이 드는가?

## Phase 2 — 온톨로지의 구성 요소

> **학습 목표:** 온톨로지를 구성하는 기본 재료를 읽고 쓸 수 있다.\
****Phase 1과의 연결:** 의사소통 실패의 원인은 "개념"과 "관계"가 명시되지 않아서다. 이 Phase는 그것을 명시하는 문법이다.

### 2-1. 클래스(Class) — 개념의 범주

- 클래스는 공통 특성을 가진 대상들의 집합이다. `동물`, `스마트폰`, `레이저 공정`이 모두 클래스다.
- 클래스는 실세계 대상이 아니라 **개념**이다. `iPhone 15`는 클래스가 아니라 인스턴스다.
- **해설:** 클래스를 잘못 설계하면 (너무 좁거나 너무 넓으면) 온톨로지 전체가 흔들린다. 범위를 정의하는 것이 설계의 핵심이다.

### 2-2. 인스턴스(Individual) — 실세계 대상

- 클래스의 구체적 사례다. `iPhone 15`는 `스마트폰` 클래스의 인스턴스다.
- 인스턴스는 속성값을 가진다. `iPhone 15`의 화면크기는 `6.1인치`다.
- **해설:** 클래스는 "틀"이고 인스턴스는 "틀로 찍은 것"이다. DB의 테이블(클래스) vs. 행(인스턴스)과 유사하지만, 온톨로지에서는 하나의 인스턴스가 여러 클래스에 동시에 속할 수 있다.

### 2-3. 속성(Property) — 두 종류

- **객체 속성(Object Property):** 개념과 개념을 잇는 관계
  - `제조공정 --사용하는재료--> 알루미늄`, `직원 --소속된--> 부서`
  - 방향이 있다. 역방향(inverse)도 정의할 수 있다.
- **데이터 속성(Data Property):** 개념에 값(리터럴)을 붙이는 방법
  - `스마트폰 --화면크기--> "6.1"^^xsd:float`
  - 값의 타입(정수, 문자열, 날짜 등)을 명시할 수 있다.
- **해설:** 객체 속성이 그래프의 "엣지"를 만들고, 데이터 속성이 노드에 "라벨"을 붙인다. 이 둘의 구분이 RDF 모델의 핵심이다.

### 2-4. 공리(Axiom) — 제약과 규칙

- "모든 스마트폰은 반드시 제조사를 가진다" → 존재 제약(existential restriction)
- "사람은 동시에 두 개의 주민등록번호를 가질 수 없다" → 기능적 속성(functional property)
- "A가 B의 부모이면 B는 A의 자녀다" → 역속성(inverse property)
- **해설:** 공리가 없으면 온톨로지는 단순 분류표다. 공리가 있어야 **추론**이 가능해진다.

### 2-5. 계층 구조와 상속

- `포유류 → 개 → 진돗개` : 하위 클래스는 상위 클래스의 속성을 상속한다.
- `SubClassOf` 관계와 `Type` 관계의 차이 — "진돗개는 개의 하위 클래스"와 "뽀삐는 진돗개 클래스의 인스턴스"는 다른 관계다.
- **해설:** 상속을 너무 깊게 만들면 유지보수가 어렵다. 실제 설계에서는 4\~5단계를 넘지 않는 것이 권장된다.

### 2-6. 온톨로지 vs. 데이터베이스 vs. 지식그래프

|  | 데이터베이스 | 온톨로지 | 지식그래프 |
| --- | --- | --- | --- |
| 구조 | 테이블/행 | 클래스/인스턴스/관계 | 노드/엣지 (대부분 온톨로지 기반) |
| 추론 | 불가 | 가능 | 부분적 |
| 스키마 변경 | 어려움 | 유연 | 유연 |
| 표준 언어 | SQL | OWL/RDF | 다양 |

- **해설:** 지식그래프는 온톨로지를 대규모로 구현한 것에 가깝다. Google Knowledge Graph도 내부적으로 온톨로지 기반 스키마를 사용한다.

### 🔬 실습 포인트

- 자신이 아는 도메인에서 클래스 5개, 인스턴스 3개, 객체 속성 3개, 데이터 속성 2개를 종이에 적어보기
- `A는 B다(is-a)`와 `A는 B를 가진다(has-a)`를 구분해서 각각 2가지씩 예시 만들기

### ✅ 핵심 질문 (Phase 2 통과 기준)

1. 클래스와 인스턴스의 차이를 예를 들어 설명하라.
2. 객체 속성과 데이터 속성은 왜 구분하는가?
3. 공리가 없는 온톨로지와 있는 온톨로지의 차이는 무엇인가?
4. `SubClassOf`와 `Type` 관계를 혼동하면 어떤 문제가 생기는가?

## Phase 3 — 온톨로지의 논리적 기반

> **학습 목표:** 온톨로지가 단순 분류표가 아니라 "추론 엔진"임을 이해한다.\
****Phase 2와의 연결:** 구성 요소를 알았다면, 이제 그것들이 어떻게 "생각"을 만들어내는지를 봐야 한다.

### 3-1. 기술 논리(Description Logic)의 직관적 이해

- 온톨로지의 수학적 기반은 1차 논리(First-Order Logic)의 결정 가능한 부분집합인 기술 논리다.
- 핵심 아이디어: **"클래스를 충분히 정의하면, 무엇이 그 클래스에 속하는지 기계가 스스로 판단한다"**
- 예: "심장을 가지고 젖을 분비하면 포유류다"라고 정의하면, 고래가 포유류임을 명시하지 않아도 추론된다.
- **해설:** 이것이 온톨로지가 데이터베이스와 근본적으로 다른 이유다. DB는 명시된 것만 알지만, 온톨로지는 정의에서 새로운 사실을 도출할 수 있다.

### 3-2. Open World Assumption (OWA) vs. Closed World Assumption (CWA)

- **CWA (DB의 세계):** "기록되지 않은 것은 거짓이다." 서울에 산다는 기록이 없으면 서울에 안 사는 것이다.
- **OWA (온톨로지의 세계):** "기록되지 않은 것은 알 수 없다." 서울에 산다는 기록이 없다고 해서 아닌 것은 아니다.
- **해설:** 이 차이가 온톨로지를 처음 접할 때 가장 혼란스러운 부분이다. OWA 때문에 온톨로지에서는 "이 값이 없다"는 것을 증명하기 어렵고, 제약을 다르게 설계해야 한다.

### 3-3. 추론(Reasoning)의 종류

- **일관성 검사(Consistency Checking):** 온톨로지에 논리적 모순이 없는지 확인
  - "독신자는 결혼하지 않은 사람"인데 "결혼한 독신자"가 정의되면 모순 → 추론기가 탐지
- **서브클래스 추론(Classification):** 명시하지 않은 클래스 계층을 자동으로 계산
- **인스턴스 분류(Instance Realization):** 인스턴스가 어떤 클래스에 속하는지 자동으로 판단
- **속성값 추론(Property Inference):** 역속성, 전이적 속성 등에서 새로운 사실 도출
  - "A가 B의 조상이고 B가 C의 조상"이면 "A가 C의 조상"임을 자동 추론 (전이적 속성)
- **해설:** 이 추론들이 실제로 동작하는 것을 Protégé + Reasoner로 확인하는 것이 Phase 3의 핵심 실습이다.

### 3-4. 추론기(Reasoner)의 역할

- 주요 추론기: HermiT, Pellet, FaCT++
- OWL로 작성된 온톨로지를 입력받아 추론 결과를 출력한다.
- 추론기는 완전성(Completeness)과 건전성(Soundness)을 보장한다 — 나올 수 있는 결론은 다 내고, 틀린 결론은 내지 않는다.
- **해설:** 추론기의 성능(속도, 표현력 한계)이 온톨로지 설계 선택에 영향을 준다. OWL Full은 추론이 불가능하고, OWL DL은 결정 가능하다.

### 🔬 실습 포인트

- Protégé를 설치하고 간단한 온톨로지(동물 분류 5개 클래스)를 만든 뒤 HermiT 추론기를 실행해보기
- "독신자는 결혼하지 않은 사람"을 OWL로 정의하고, 결혼한 독신자 인스턴스를 만들어서 모순이 탐지되는지 확인
- CWA/OWA 차이를 체감하기 위해: DB에서는 없으면 False, 온톨로지에서는 없으면 Unknown임을 직접 실험

### ✅ 핵심 질문 (Phase 3 통과 기준)

1. OWA와 CWA의 차이를 실제 예시로 설명하라. 온톨로지 설계에 어떤 영향을 주는가?
2. "분류(Classification)"와 "실현(Realization)"의 차이는 무엇인가?
3. 추론기가 없는 온톨로지는 어떤 능력을 잃는가?
4. OWL DL이 OWL Full보다 제한적인 이유는 무엇인가?

## Phase 4 — 표준과 언어 생태계

> **학습 목표:** 온톨로지 관련 표준 스택을 보고 무엇이 무엇인지 구분하고 선택할 수 있다.\
****Phase 3과의 연결:** 추론이 가능하다는 것을 알았다면, 이제 그것을 실제로 표현하는 언어를 배워야 한다.

### 4-1. RDF — 지식 표현의 기본 단위

- 모든 지식을 `주어(Subject) — 술어(Predicate) — 목적어(Object)` 세 토막(Triple)으로 표현한다.
- 예: `<iPhone15> <제조사> <Apple>`, `<Apple> <설립연도> "1976"`
- 모든 개체는 URI(고유 식별자)로 표현된다. 웹 상의 주소처럼 전 세계에서 유일하다.
- **해설:** RDF는 그래프 구조다. Triple들이 모이면 지식 그래프가 된다. RDF 자체는 추론 능력이 없다.

### 4-2. RDFS — 계층 구조를 추가하다

- RDF에 `rdfs:subClassOf`, `rdfs:subPropertyOf`, `rdfs:domain`, `rdfs:range` 등을 추가
- "개는 동물의 하위 클래스"처럼 계층 구조를 표현 가능
- 제한적 추론(상속)은 지원하지만 OWL보다 표현력이 훨씬 낮다
- **해설:** 단순한 분류 체계가 필요하다면 RDFS로 충분한 경우도 있다. OWL은 표현력이 높지만 그만큼 복잡성도 높다.

### 4-3. OWL — 본격적인 온톨로지 언어

- W3C 표준. 기술 논리(DL)에 기반하여 추론을 보장한다.
- **OWL Lite:** 단순 계층과 제약. 추론 비용 낮음
- **OWL DL:** 완전한 추론 보장. 결정 가능. 실무에서 가장 많이 사용
- **OWL Full:** 제약 없는 표현력. 하지만 추론 완전성 보장 불가
- 선택 기준: 추론이 필요하면 OWL DL, 단순 구조화면 RDFS, 웹 노출이 목적이면 [Schema.org](http://Schema.org) 고려
- **해설:** OWL 2는 OWL DL의 세 가지 프로파일(EL, QL, RL)을 추가로 정의한다. 용도에 따라 표현력과 성능을 트레이드오프한다.

### 4-4. SPARQL — 온톨로지에 질문하는 방법

- SQL의 RDF 버전. Triple 패턴을 기반으로 질의한다.
- 기본 구조: `SELECT ?x WHERE { ?x rdf:type :스마트폰 . ?x :제조사 :Apple }`
- SPARQL 1.1은 집계, 서브쿼리, 업데이트(SPARQL Update) 지원
- SPARQL Endpoint: URL로 공개된 온톨로지에 직접 질의 가능 (DBpedia, Wikidata 등)
- **해설:** SPARQL을 모르면 온톨로지를 "읽기 전용"으로밖에 쓸 수 없다. 실습에서 반드시 손으로 써봐야 하는 언어다.

### 4-5. 직렬화 포맷 — 같은 내용, 다른 표기

- **Turtle (.ttl):** 가장 사람이 읽기 좋은 형태. 학습용으로 적합
- **JSON-LD:** JSON 형식. 웹 개발자 친화적. [Schema.org](http://Schema.org)가 이 형식 권장
- **RDF/XML:** 초기 W3C 표준. 기계 처리엔 좋지만 가독성 낮음
- **N-Triples:** 가장 단순한 형태. 대용량 처리에 적합
- **해설:** 형식은 다르지만 표현하는 정보는 동일하다. 학습 초기엔 Turtle로 시작하는 것이 가장 좋다.

### 4-6. 주요 도구 소개

- **Protégé:** 온톨로지 설계 및 편집 GUI 툴. 추론기 내장. 무료
- **Apache Jena:** Java 기반 RDF/OWL 처리 프레임워크
- **RDFLib:** Python 기반 RDF 라이브러리. 스크립트로 온톨로지 처리 가능
- **GraphDB / Stardog / Blazegraph:** SPARQL Endpoint를 제공하는 트리플스토어(그래프 DB)
- **해설:** Protégé → RDFLib → 트리플스토어 순서로 익히는 것이 자연스럽다.

### 🔬 실습 포인트

- RDFLib(Python)으로 그 파일을 읽어서 SPARQL 질의 3개 수행하기
- Wikidata SPARQL Endpoint(<https://query.wikidata.org)에서> 실제 질의 실행해보기

## Phase 5 — 온톨로지 설계 방법론

> **학습 목표:** 스스로 작은 도메인 온톨로지를 체계적으로 설계할 수 있다.\
****Phase 4와의 연결:** 언어를 알았으니 이제 무엇을 어떻게 써야 할지 — 설계 방법론이 필요하다.

### 5-1. 온톨로지 개발 프로세스 개요

- **METHONTOLOGY (1997):** 소프트웨어 공학 방법론에서 영감받은 체계적 프로세스
- **Ontology 101 (Noy & McGuinness, 2001):** 가장 많이 인용되는 실용 가이드
- 공통 흐름: `범위 정의 → 재사용 가능한 온톨로지 탐색 → 클래스 열거 → 계층 정의 → 속성 정의 → 제약 정의 → 인스턴스 추가 → 검증`
- **해설:** 정해진 순서를 완벽히 따르기보다, 반복적(iterative)으로 정제하는 것이 현실적이다.

### 5-2. 범위 정의 — Competency Questions

- 온톨로지를 만들기 전에 "이 온톨로지로 뭘 물어볼 수 있어야 하는가"를 먼저 정의한다.
- 예 (스마트폰 부품 온톨로지):
  - "이 부품을 사용하는 모든 제품을 찾아라"
  - "이 공정에서 발생할 수 있는 불량 유형은 무엇인가"
  - "A 부품과 동일한 스펙을 가진 대체 부품은 무엇인가"
- **해설:** CQ가 명확할수록 설계 범위가 좁아지고 품질이 올라간다. CQ로 대답할 수 없는 것은 온톨로지에 넣지 않아도 된다.

### 5-3. 상향식 vs. 하향식 설계

- **하향식(Top-down):** 가장 일반적인 클래스부터 시작해서 세분화. 전체 그림이 보이지만 초반에 추상적
- **상향식(Bottom-up):** 구체적 인스턴스에서 시작해서 공통점을 묶어 클래스화. 실용적이지만 일관성 확보 어려움
- **중간 방식(Middle-out):** 가장 안정적인 핵심 개념부터 시작. 실무에서 권장
- **해설:** 대부분의 실제 프로젝트는 중간 방식을 사용한다. 도메인 전문가가 "가장 중요한 개념"을 먼저 꼽는 것이 출발점이 된다.

### 5-4. 기존 온톨로지 재사용

- 바퀴를 다시 발명하지 말 것. 이미 잘 만들어진 온톨로지를 import하거나 참조한다.
- **온톨로지 저장소:** BioPortal, LOV(Linked Open Vocabularies), OBO Foundry
- **owl:imports:** 다른 온톨로지의 전체를 현재 온톨로지에 포함
- **owl:equivalentClass / owl:sameAs:** 두 온톨로지의 개념을 연결(매핑)
- **해설:** 재사용은 상호운용성의 핵심이다. 단, 재사용한 온톨로지의 공리가 충돌하지 않는지 반드시 검증해야 한다.

### 5-5. 흔한 설계 실수와 안티패턴

- **너무 깊은 계층:** 5단계 이상의 계층은 관리가 어렵고 추론 성능에 영향
- **관계를 클래스로 만드는 실수:** "고용 관계"를 클래스로 만들면 → `고용` 클래스의 인스턴스로 연결하는 복잡한 구조가 됨. 대신 객체 속성 `고용하다`로 표현하는 것이 자연스럽다
- **이름 공간 혼용:** URI 체계를 일관되게 유지하지 않으면 온톨로지가 분열
- **인스턴스와 클래스 혼용:** "서울"을 클래스로 만들고 인스턴스로도 쓰는 혼용 오류
- **해설:** 이 실수들은 처음에는 자연스러워 보이기 때문에 위험하다. 설계 검토 체크리스트를 만들어두는 것이 좋다.

### 5-6. 온톨로지 품질 평가 기준

- **정확성(Accuracy):** 공리가 도메인 지식을 올바르게 반영하는가
- **완전성(Completeness):** CQ에 모두 답할 수 있는가
- **일관성(Consistency):** 논리적 모순이 없는가 (추론기로 자동 검사 가능)
- **간결성(Conciseness):** 불필요한 중복이 없는가
- **확장성(Extensibility):** 새로운 개념을 추가할 때 기존 구조를 크게 바꾸지 않아도 되는가
- **해설:** 추론기가 "일관성"만 자동 체크해준다. 나머지는 도메인 전문가의 검토가 필요하다.

### 🔬 실습 포인트

- 자신의 업무 도메인(예: 레이저 공정, 부품 관리)에서 CQ 5개를 먼저 작성하기
- Protégé로 그 CQ에 답하는 최소 온톨로지를 설계하고 SPARQL로 각 CQ에 답해보기
- 설계한 온톨로지에서 안티패턴이 있는지 체크리스트로 검토하기

### ✅ 핵심 질문 (Phase 5 통과 기준)

1. Competency Question이 왜 온톨로지 설계의 출발점이 되어야 하는가?
2. "관계를 클래스로 만드는 실수"의 구체적 예시를 들고 올바른 설계를 설명하라.
3. 기존 온톨로지를 재사용할 때 확인해야 할 사항은 무엇인가?
4. 설계한 온톨로지의 일관성을 검사하는 방법은?

## Phase 6 — 주요 표준 온톨로지 분석

> **학습 목표:** 실제로 쓰이는 온톨로지를 분석하고, 좋은 설계가 공유하는 원칙을 추출할 수 있다.\
****Phase 5와의 연결:** 설계 방법론을 배웠으니, 이제 전문가들이 실제로 어떻게 만들었는지를 분석한다.

### 6-1. FOAF (Friend of a Friend)

- 목적: 사람과 사람 사이의 관계를 표현하는 가장 단순한 온톨로지
- 핵심 클래스: `foaf:Person`, `foaf:Organization`
- 핵심 속성: `foaf:name`, `foaf:knows`, `foaf:mbox`
- **분석 포인트:** 극도로 단순하지만 소셜 네트워크 데이터를 연결하는 데 충분하다. "필요한 것만" 설계하는 원칙의 좋은 예.

### 6-2. Dublin Core

- 목적: 디지털 문서의 메타데이터 표준 (저자, 제목, 날짜, 주제 등 15개 요소)
- 특징: 어떤 형식의 문서에도 적용 가능한 범용 어휘
- **분석 포인트:** 온톨로지가 기술 표준이 되는 과정 — 커뮤니티 합의가 핵심이다.

### 6-3. [Schema.org](http://Schema.org)

- 목적: Google/Bing/Yahoo가 공동으로 만든 웹 문서 구조화 어휘
- 특징: JSON-LD로 HTML 페이지에 삽입. 검색 엔진 최적화(SEO)와 직결
- 규모: 800개 이상의 타입, 1400개 이상의 속성
- **분석 포인트:** 학문적 정확성보다 실용적 채택률을 우선한 설계. OWL 대신 단순한 계층 구조만 사용한다.

### 6-4. Gene Ontology (GO)

- 목적: 유전자 기능, 세포 구성요소, 생물학적 프로세스를 표준화
- 특징: 세 개의 독립된 계층(Directed Acyclic Graph)으로 구성
- **분석 포인트:** 다중 상속(하나의 개념이 여러 상위 개념을 가짐)을 실제로 사용하는 대표 사례. 생물정보학 연구의 기반 인프라.

### 6-5. SNOMED CT / HL7 FHIR

- 목적: 의료 용어와 임상 데이터 표준화
- SNOMED CT: 36만 개 이상의 의료 개념 정의
- FHIR: 의료 데이터 교환 표준 (온톨로지 + API)
- **분석 포인트:** 온톨로지가 생사와 직결되는 도메인에서 어떻게 설계되는지. 버전 관리와 변경 통제의 중요성.

### 6-6. 공통 설계 원칙 추출

- 모든 성공적 온톨로지가 공유하는 것:
  - 명확한 목적과 범위 (CQ 기반)
  - 커뮤니티의 합의와 지속적 관리
  - 재사용과 확장을 고려한 이름 공간 설계
  - 문서화 — 각 클래스와 속성에 자연어 설명 포함

### 🔬 실습 포인트

- [Schema.org](http://Schema.org)에서 자신의 도메인과 관련된 타입을 찾아보고 CQ와 대조해보기
- Wikidata SPARQL로 Gene Ontology 관련 질의 실행해보기
- FOAF 온톨로지 파일을 Protégé로 열어서 구조를 시각적으로 분석하기

### ✅ 핵심 질문 (Phase 6 통과 기준)

2. Gene Ontology에서 다중 상속이 필요한 이유를 생물학적 예로 설명하라.

## Phase 7 — 온톨로지의 응용

> **학습 목표:** 자신의 문제에 온톨로지를 적용할 수 있는 판단력을 갖는다.\
****Phase 6과의 연결:** 사례를 분석했으니, 이제 응용 패턴을 추상화한다.

### 7-1. 시맨틱 웹과 Linked Data

- Tim Berners-Lee의 비전: 웹의 데이터를 기계가 이해하는 공간으로
- Linked Data 4원칙: URI 사용, HTTP URI, URI로 유용한 정보 제공, 다른 URI로 연결
- LOD(Linked Open Data) 클라우드: 수천 개의 데이터셋이 RDF로 연결된 생태계
- **해설:** 시맨틱 웹의 완전한 실현은 아직 미완이지만, 부분적 구현([Schema.org](http://Schema.org), Wikidata)은 이미 일상적으로 사용되고 있다.

### 7-2. 지식 그래프(Knowledge Graph)

- Google Knowledge Graph: 검색 결과 우측 패널에 나오는 정보의 출처
- Wikidata: 위키피디아의 구조화 데이터 버전. SPARQL로 질의 가능
- DBpedia: 위키피디아를 자동으로 RDF로 변환한 데이터셋
- **구성 원리:** 온톨로지(스키마) + 인스턴스 데이터(사실) + 추론 규칙
- **해설:** 지식 그래프는 온톨로지를 대규모로 실용화한 것이다. 기업 내부의 "엔터프라이즈 지식 그래프"가 최근 트렌드.

### 7-3. 검색 및 추천 시스템

- 온톨로지 기반 확장 검색: "스마트폰"을 검색하면 "모바일 기기", "iPhone", "갤럭시"도 자동 포함
- 추천 시스템: 사용자와 상품의 속성을 온톨로지로 표현, 관계 기반 추천
- **해설:** 단순 키워드 매칭의 한계를 온톨로지가 보완한다. 의미 기반 검색의 핵심 인프라.

### 7-4. NLP와 온톨로지의 결합

- Named Entity Recognition(NER): 텍스트에서 개체를 추출하고 온톨로지 인스턴스로 연결
- 관계 추출(Relation Extraction): 텍스트에서 Triple을 추출
- 온톨로지 기반 텍스트 분류: 클래스 계층을 레이블로 활용
- **해설:** 비정형 텍스트를 구조화된 지식으로 변환하는 파이프라인의 핵심에 온톨로지가 있다.

### 7-5. LLM 시대의 온톨로지 — 가장 현재적인 응용

- **RAG(Retrieval-Augmented Generation) + 온톨로지:**
  - 단순 벡터 검색의 한계: 의미적 유사성만 보고 논리적 관계는 놓침
  - 온톨로지 + 벡터 하이브리드: 구조화 쿼리(SPARQL) + 의미 검색 결합
- **LLM 출력의 구조화:**
  - LLM이 생성한 텍스트를 온톨로지 스키마에 따라 Triple로 변환
  - 할루시네이션 탐지: 생성된 사실을 온톨로지 지식 그래프와 대조 검증
- **Graph RAG:** 지식 그래프를 컨텍스트로 LLM에 제공하여 추론 품질 향상
- **해설:** 온톨로지가 "AI 시대에 구식"이라는 오해와 달리, LLM의 약점(환각, 논리 오류)을 보완하는 수단으로 재조명되고 있다.

### 7-6. 제조/산업 도메인 응용

- **ISO 15926:** 석유/가스 플랜트의 생애주기 데이터 통합 표준
- **PDDL (Planning Domain Definition Language):** AI 플래닝에서 작업 도메인 정의
- **IFC (Industry Foundation Classes):** 건축/건설 BIM 데이터 표준
- **제조 공정 온톨로지 응용:**
  - 공정 파라미터와 품질 결과의 관계 모델링
  - 설비 고장 패턴의 지식화
  - AI 기반 공정 자동화에서 "판단 근거"의 명시화
- **해설:** 제조 도메인에서 온톨로지는 AI 모델의 블랙박스 문제를 해결하는 수단 — 왜 이 공정 파라미터를 선택했는지 설명 가능하게 한다.

### 🔬 실습 포인트

- Wikidata SPARQL로 실제 지식 그래프 질의 10개 수행해보기
- 자신의 업무 도메인(레이저 공정 등)에서 Graph RAG 적용 시나리오를 설계해보기
- LangChain + Neo4j로 간단한 지식 그래프 기반 QA 시스템 프로토타입 구성해보기

### ✅ 핵심 질문 (Phase 7 통과 기준)

## Phase 8 — 한계와 대안

> **학습 목표:** 온톨로지를 맹목적으로 쓰지 않고, 적재적소에 선택할 수 있는 판단력을 갖는다.\
****Phase 7과의 연결:** 응용을 알았다면, 언제 쓰지 말아야 하는지도 알아야 진짜 실력이다.

### 8-1. 온톨로지 구축의 현실적 비용

- 도메인 전문가와 온톨로지 엔지니어의 긴밀한 협력 필요 → 높은 인건비
- 초기 구축보다 **유지보수**가 더 어렵다. 도메인 지식이 변하면 공리를 수정해야 한다.
- 대규모 온톨로지는 추론 성능이 저하된다. SNOMED CT 전체를 실시간 추론하는 것은 비현실적.
- **해설:** "온톨로지를 만들어야 한다"는 결론에 도달하기 전에, 유지보수 비용을 감당할 수 있는지 먼저 평가해야 한다.

### 8-2. 온톨로지 매핑 문제

- 같은 개념이 두 온톨로지에서 다르게 표현될 때 연결하는 것 — 온톨로지 매핑
- 자동화 도구(LogMap, AgreementMakerLight)가 있지만 정확도가 완벽하지 않다.
- 매핑 자체가 새로운 온톨로지를 필요로 하는 "거북이 위의 거북이" 문제
- **해설:** 표준 온톨로지를 처음부터 재사용하는 것이 사후 매핑보다 훨씬 효율적인 이유.

### 8-3. 벡터 임베딩과의 비교

|  | 온톨로지 | 벡터 임베딩 |
| --- | --- | --- |
| 의미 표현 방식 | 명시적 규칙과 관계 | 통계적 분포 |
| 추론 능력 | 논리적 추론 가능 | 유사성 계산만 |
| 구축 비용 | 높음 | 낮음 (자동 학습) |
| 설명 가능성 | 높음 | 낮음 |
| 새로운 개념 추가 | 수동 작업 필요 | 재학습 필요 |

- **해설:** 둘은 경쟁 관계가 아니라 보완 관계다. 온톨로지의 구조 + 임베딩의 유연성을 결합하는 Neurosymbolic AI가 연구 방향.

### 8-4. 언제 온톨로지가 과한가?

- **JSON-LD만으로 충분한 경우:** 웹 페이지 SEO 목적. 추론이 필요 없고 [Schema.org](http://Schema.org) 어휘로 충분한 경우
- **Property Graph(Neo4j)로 대체 가능한 경우:** 추론보다 그래프 탐색과 분석이 주목적인 경우. 사이클 탐지, 최단 경로 등
- **관계형 DB가 더 나은 경우:** 데이터가 표 구조에 잘 맞고, 복잡한 관계 추론이 불필요한 경우
- **단순 분류 체계로 충분한 경우:** 계층만 필요하고 추론이 필요 없다면 RDFS나 SKOS로 충분
- **해설:** 도구는 문제에 맞게 선택해야 한다. 온톨로지는 강력하지만, 그 강력함이 필요한 문제인지 먼저 판단해야 한다.

### 8-5. 온톨로지 선택 의사결정 트리

```
추론이 필요한가?
├─ No → 그래프 탐색/분석이 주목적인가?
│        ├─ Yes → Property Graph (Neo4j)
│        └─ No → 계층 구조만 필요한가?
│                 ├─ Yes → RDFS or SKOS
│                 └─ No → 관계형 DB or JSON
└─ Yes → 도메인 표준 온톨로지가 있는가?
          ├─ Yes → 재사용 + 확장 (OWL DL)
          └─ No → 직접 설계 (OWL DL)
                   └─ 실시간 대규모 추론이 필요한가?
                       ├─ Yes → OWL 2 EL/RL 프로파일 고려
                       └─ No → OWL 2 DL
```

### 🔬 실습 포인트

- 자신이 알고 있는 3가지 프로젝트/문제에 위 의사결정 트리를 적용해보기
- Neo4j와 Protégé로 동일한 도메인을 각각 표현하고 장단점 비교해보기

### ✅ 핵심 질문 (Phase 8 통과 기준)

1. 온톨로지 대신 Property Graph를 선택해야 하는 기준은 무엇인가?
2. 벡터 임베딩과 온톨로지는 어떤 면에서 보완 관계인가?
3. 당신의 현재 프로젝트에서 온톨로지가 필요한지 아닌지를 결정하는 근거를 제시하라.

## 전체 학습 흐름 요약

```
Phase 1: 왜? (동기)
    ↓ 의사소통 실패 문제를 해결하려면 개념과 관계를 명시해야 한다
Phase 2: 무엇으로? (재료)
    ↓ 클래스·인스턴스·속성·공리로 구성된다
Phase 3: 어떻게 작동하나? (원리)
    ↓ 기술 논리와 OWA 기반 추론 엔진이다
Phase 4: 어떤 언어로? (도구)
    ↓ RDF → RDFS → OWL 스택, SPARQL로 질의
Phase 5: 어떻게 만드나? (설계)
    ↓ CQ → 클래스 설계 → 속성/공리 → 검증의 반복
Phase 6: 실제 사례는? (분석)
    ↓ 좋은 온톨로지의 공통 원칙을 추출
Phase 7: 어디에 쓰나? (응용)
    ↓ 지식 그래프, LLM 보완, 제조 AI 등
Phase 8: 언제 안 쓰나? (판단)
    → 도구를 선택하는 진짜 실력
```
